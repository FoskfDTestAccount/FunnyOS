# DOS 服务参考:PSP、环境块、程序装载

这份文件是 M5 及之后 **DOS 服务行为的依据**,和 [`dos-refs.md`](dos-refs.md) 是姊妹篇。那一份管**固件**(`INT 10h/11h/12h/13h/16h/1Ah` 和 BIOS 数据区);这一份管 **DOS 层**——一个 `.COM` 被装载时它的内存里有什么,以及 `INT 21h` 的那些功能。

分开的理由是**权威不同**:固件那些事实出自 IBM 1981 年的 BIOS,DOS 那些出自 MS-DOS。混在一份文件里会让标题变成谎话,而 `dos-refs.md` 第九节当时把「`INT 21h` 与整个 DOS 服务层」记成 M5 未覆盖,指的就是这份文件。

## 一、PSP 布局(256 字节,在程序段偏移 `0000h`)

DOS 在一个程序段的最前面造 256 字节的「程序段前缀」,把所有四个段寄存器指向它,然后从 `0100h` 开始放程序。下面这张表是**一个 `.COM` 装载完之后**应该长什么样。

| 偏移 | 长度 | 内容 |
|---|---|---|
| `00h` | 2 | **`CD 20`** —— 也就是 `INT 20h`,CP/M 风格的结束程序 |
| `02h` | 2 | **程序被分配到的段落之后那一段**。对 `.COM` 就是「第一个不属于这个程序的字节的段值」 |
| `04h` | 1 | 保留 |
| `05h` | 5 | **CP/M 风格的远调用入口**,字节是 `9A F0 FE 1D F0`,也就是 `CALL F01Dh:FEF0h` |
| `0Ah` | 4 | **原本的 `INT 22h`**(上一个程序被终止时该跳回的地址) |
| `0Eh` | 4 | **原本的 `INT 23h`**(Ctrl-Break 处理程序) |
| `12h` | 4 | **原本的 `INT 24h`**(严重错误处理程序) |
| `16h` | 2 | **父进程的 PSP 段** |
| `18h` | 20 | **JFT**(作业文件表),每字节一个句柄,`FFh` 表示空 |
| `2Ch` | 2 | **环境块的段** |
| `2Eh` | 4 | 上一次进 `INT 21h` 时的 `SS:SP`(内部) |
| `32h` | 2 | JFT 的**大小**(通常是 20) |
| `34h` | 4 | **指向 JFT 的指针**(通常是 `PSP:0018h`) |
| `38h` | 4 | 指向前一个 PSP 的指针(内部,SHARE 用) |
| `3Ch` | 4 | 保留 |
| `40h` | 2 | **要报告的 DOS 版本号**(DOS 5+ 起可被 `SETVER` 改写) |
| `42h` | 14 | 保留 |
| `50h` | 3 | **`CD 21 CB`** —— `INT 21h` 后面跟 `RETF`,一个 UNIX 风格的远调用入口 |
| `53h` | 2 | 保留 |
| `55h` | 7 | 保留(可被借用,把第一个 FCB 变成扩展 FCB) |
| `5Ch` | 16 | **第一个默认 FCB**,未打开 |
| `6Ch` | 20 | **第二个默认 FCB**,未打开 |
| `80h` | 1 | **命令行长度的字节数**(不含结尾的 `0Dh`) |
| `81h` | 127 | **命令行尾部**,以 `0Dh` 结尾 |

**三处值得单独说一句的。**

- **`02h` 那一格是「分配到的内存之后」,不是「程序映像之后」。** 一个 `.COM` 在 DOS 下会拿到**从它的 PSP 起到常规内存顶端为止的全部空间**,所以这一格是一个和机器内存大小有关的数,不是 `PSP + 0x1000`。程序读它是为了知道自己有多少堆可用,并用 `INT 21h AH=4Ah` 去缩。
- **`0Ah`/`0Eh`/`12h` 存的是「以前的向量内容」,不是空位。** DOS 在装载程序之前把这三个向量抄进 PSP,然后把自己的处理程序装进向量表;程序结束(`INT 22h`)时 DOS 再把它们放回去。所以一个刚装载的 PSP 里这三个字段**必须**有值,而写什么由装载者决定——本机取「当前向量表里的值」。
- **`50h` 那三个字节是给不认识 `INT 21h` 的程序用的老入口。** 现在没有程序走它,但它在规范里,而且只有三个字节。——**注意不要和 `05h` 搞混,它们是两个不同的东西**:`50h` 是 `INT 21h` + `RETF` 三字节,谁都能用;`05h` 是 CP/M 的 `CALL 5`。

### `05h` 那五个字节是怎么来的(值得知道,但本机不做)

`9A F0 FE 1D F0` 里的 `FEF0h` **不只是地址偏移,它同时是「程序段的大小」**:DOS 算的是 `min(内存顶端段 − PSP 段, 0FFEh)`。而 `F01Dh` 那个段值是**为了让它绕回来**才选的:

```
0F01Dh + 0FEF0h = 1000C0h  -- 超过 1 MiB,回绕到 0000:00C0h
```

`0000:00C0h` 是 **`INT 30h` 的向量**,DOS 内核在启动时把它填成一个指向内核服务的远跳转。所以执行 `PSP:05h` 上的那条 `CALL` 最终会到 DOS 的分发器。**它依赖 8086 的 1 MiB 回绕**,A20 打开之后就不成立了。

**本机不实现这个入口。** 理由:它需要偏移 `06h` 那个字同时是「程序大小」而 `08h` 那个段值是**为了回绕算出来的**,两者是一对;而本机没有 `INT 30h` 的处理程序,填出来的字节会**看起来正确却跳到虚空**。写成零并在这里说明,比写一串读起来像真的、效果是死路的字节好。DOS 时代之后没有一个程序用 `CALL 5` 走进 DOS 功能——那是 CP/M-80 的遗物。

**来源:** [Stack Overflow: Call 5 interface on MS-DOS](https://stackoverflow.com/posts/39949334/revisions)(字节含义、`FEF0` 双重含义、回绕到 `0:00C0h`);[Wikipedia: Program Segment Prefix](https://en.wikipedia.org/wiki/Program_segment_prefix)(字段的存在)。

**来源:** [Wikipedia: Program Segment Prefix](https://en.wikipedia.org/wiki/Program_segment_prefix)(整张表);[Wikipedia 的 PDF 镜像](https://en.wikipedia.org/wiki/Program_segment_prefix#1)。`02h` 的含义另见 [Stack Overflow: Stack write order and code execution order](https://stackoverflow.com/posts/63782300/revisions)。

## 二、`.COM` 的进入约定

装载完成、控制权交给程序的那一刻:

| 寄存器 | 值 |
|---|---|
| `CS`, `DS`, `ES`, `SS` | **全部等于 PSP 的段** |
| `IP` | **`0100h`** —— PSP 之后 |
| `SP` | **`FFFEh`** |
| `SS:FFFEh` 那个字 | **`0000h`** |
| `IF` | **置位**(可以被打断) |

**那个零字是 CP/M 兼容的全部内容。** DOS 把 SP 设成 `0000h` 再压一个零字,于是 SP 落在 `FFFEh`,字本身写在 `SS:FFFEh`。程序末尾一条**近 `RET`** 就弹出 `0000h` 进 IP,`CS:IP` 变成 `PSP:0000h` —— 那里正是 `INT 20h`。这就是为什么 `.COM` 可以**不写任何结束代码**。

**`IF` 是置位的,而这一点和本仓库已有的语料约定相反。** `dos/corpus/bios/replay.h` 冻住的约定是 `FLAGS = 0xF002`,即 **IF 清零**,那段注释也自己说了「真实 DOS 进入一个程序时 IF 是置位的」,并说明那个偏离是为了让 M5 加 PSP 时不移动 M3 的样本。**所以两条路要并存**:裸机语料仍然 IF 清零,DOS 装载器出来的程序 IF 置位。这不是不一致,是两套不同的东西,而这个区别必须有人写下来,否则下一个人会「修」其中一个。

**来源:** [Stack Overflow: Why does DOS set the SP register to 0xFFFE after loading a .COM file?](https://stackoverflow.com/questions/60805609/why-does-dos-set-the-sp-register-to-0xfffe-after-loading-a-com-file)(SP、压零字、`RET` 与 `INT 20h` 的关系);[Wikipedia: Program Segment Prefix](https://en.wikipedia.org/wiki/Program_segment_prefix)(四个段寄存器与 `IP = 100h`)。

## 三、环境块

环境块**按段落对齐**,内容是若干个 ASCIIZ 字符串:

```
NAME=VALUE\0
NAME=VALUE\0
...
\0                 <- 再多一个 0 字节,表示字符串表结束
--- 以下 DOS 3.0+ ---
WORD  n            <- 后面还有几个字符串(通常是 1)
<程序的全路径>\0    <- 驱动器、路径、文件名、扩展名
```

**两处容易写错的。**

- **结尾是「一个空的字符串」,不是一个「空表」。** 最后一个变量后面还要再跟一个 `00h`。所以一个**空环境块**在 `00h` 处只有**一个**零字节就结束了字符串表——而不是两个。**有些代码去找「双零」,在空环境上会越过边界**;FreeDOS 的邮件列表里专门讨论过这个坑。
- **`WORD n` 和全路径是 DOS 3.0 以后才有的。** 只认 DOS 2 的程序按「双零之后就是别的」读,所以那一段的**存在**不破坏它们,但**长度**是程序不该假设的。

**来源:** [FreeDOS kernel mailing list, 2003-09-15](https://marc.info/?l=freedos-kernel&m=106362891012631)(Ralf Brown 的条目与偏移布局);[Concurrent DOS 86 Programmer's Guide](http://www.mirrorservice.org/sites/www.bitsavers.org/pdf/digitalResearch/concurrent/1066-2023-001_Concurrent_DOS_86_Programmers_Guide_Version_5.0_Mar1986.pdf)(字符串表与结尾的双零)。

## 四、命令行尾部(`80h` / `81h`)

- `80h` 是**长度**,计的是 `81h` 开始的那一串字节,**不含**结尾的 `0Dh`。
- `81h` 是尾部本身,**从程序名之后的第一个字符开始**,最大 126 个字符,以 `0Dh` 结尾。
- `80h` 到 `FFh` 同时是**默认的 DTA**(FCB 功能的磁盘传输区)。

**这里有一个流传很广的错误假设,值得单独写下来:尾部以空格开头是习惯,不是规定。** `PROG arg1 arg2` 之所以看起来总是以空格开头,是因为人和 shell 通常会在程序名后面打一个空格。但是在 `PROG` 直接接参数、或者调用方式不同的场合,第一个字节就不是空格。**假定第一个字节是空格并跳过它的程序,会在那些场合丢掉一个字符**——而丢掉的是一个参数的第一个字母,症状是「文件找不到」而不是任何像解析错误的东西。

**来源:** [Stack Overflow: 60805609 的答案串](https://stackoverflow.com/questions/60805609/why-does-dos-set-the-sp-register-to-0xfffe-after-loading-a-com-file)(「往往是空格、但不总是」,以及 `CHKDSK/V C:` 那个反例);[Wikipedia: Program Segment Prefix](https://en.wikipedia.org/wiki/Program_segment_prefix)(长度不含 CR、`81h`–`FFh` 同时是 DTA)。

## 五、两个默认 FCB(`5Ch` / `6Ch`)

DOS 把命令行尾部的前两个参数按 CP/M 的格式解析进这两个未打开的 FCB。一个 FCB 的前 12 个字节是:

| 偏移(相对 FCB) | 长度 | 内容 |
|---|---|---|
| `00h` | 1 | **驱动器号**:`0` = 默认驱动器,`1` = A:,`2` = B:,…… |
| `01h` | 8 | **文件名**,不足 8 个字符用**空格**补满 |
| `09h` | 3 | **扩展名**,不足 3 个字符用空格补满 |

**没有参数时**:驱动器字节是 `00h`,文件名和扩展名都是**空格**。也就是说 `PSP:5Ch` 起是 `00 20 20 20 …`,不是一片零。**这一点是查到的**(见来源),而且它和「一片零」看起来同样合理——程序把 `PSP:5Ch` 当暂存区用时两者没区别,而把第一个字节当「有没有参数」的判据时就有区别。

**两个 FCB 在内存里是重叠的**:第一个占 `5Ch`–`6Bh`(16 字节),第二个占 `6Ch`–`7Fh`(20 字节)。一个**扩展 FCB** 要 7 个字节的前缀,借用 `55h`–`5Bh` 那块保留区,而那正好压在第二个 FCB 上——所以规范自己写着「打开第一个 FCB 之后第二个就被覆盖了」。

**来源:** [MS-DOS 2.00 手册扫描件(bitsavers)](http://www.mirrorservice.org/sites/www.bitsavers.org/pdf/ibm/pc/dos/6936752_DOS_2.00_Jan83.pdf)(**由检索命中,未逐页读**);[C't 1986.12 扫描件](https://www.archive.org/download/ct-1986.12/C%27t%20-%201986.12.pdf)(驱动器字节 `0` 的含义);[Concurrent DOS 86 Programmer's Guide](http://www.mirrorservice.org/sites/www.bitsavers.org/pdf/digitalResearch/concurrent/1066-2023-001_Concurrent_DOS_86_Programmers_Guide_Version_5.0_Mar1986.pdf)(FCB 布局)。

## 六、本机的取值(决定,不是事实)

上面是规范。规范留了余地的地方,这台机器要自己选,而**选了什么必须写在这里**——否则它就会散在代码里,变成几个看起来像常数的决定。

| 位置 | 本机取值 | 为什么 |
|---|---|---|
| `PSP:02h` 内存顶端 | **`0A00h` 段**(线性 `0A0000h`) | 一个 `.COM` 在 DOS 下拿到**到常规内存顶端为止**的全部空间。这台机器的常规内存是 **640 KiB**——这是 `dos/intr/firmware.c` 里 `VM86_CONVENTIONAL_KB` 已经写下并且由 `INT 12h` 与 `0040:0013h` 两处向程序公布的事实。所以顶端是 `0A0000h`,**段值 `0A00h`**。取 `PSP + 0x1000` 会是一台自称 640 KiB 却只肯给出 64 KiB 的机器,而不一致的地方是程序会去读的地方 |
| `PSP:0Ah/0Eh/12h` 三个旧向量 | **抄装载那一刻向量表里的实际值** | 规范说存的是「原来的内容」。装载者把它们抄下来,是因为 DOS 随后会覆盖向量表。本机没有「DOS 自己的处理程序」要装,但**抄下来仍然是正确的事**:这三个字段的语义是「程序结束之后该回哪里」,而写一个编出来的值就是一个程序跳过去会死的地方。抄实际值至少是自洽的 |
| `PSP:16h` 父 PSP | **调用者给的段,没有调用者时写自己的段** | 规范说这是父进程的 PSP 段。本机今天只有一个进程,所以「父」就是它自己——**但那是一个要写下来的选择**,不是一个可以随便填的常数 |
| `PSP:18h`–`2Bh` JFT | **20 个字节,全部 `FFh`** | `FFh` = 空句柄。这台机器还没有文件句柄表(它在 W5),而「全部空」是唯一诚实的初始状态 |
| `PSP:2Ch` 环境段 | **本机造的环境块**(见第三节) | 至少要有一个 `COMSPEC=`,否则某些程序会去找它 |
| `PSP:32h` / `34h` | **`20`** / **`PSP:0018h`** | 与 JFT 一致。两处都写出来,是因为规范里它们各是一格,而一格写错就是一处静默的不一致 |
| `PSP:40h` 要报告的 DOS 版本 | **`3.30`**(`AH=30h` 也报同一个值) | **这是一个决定,而且要能被推翻。** 主张 3.30 的理由:许多老程序按版本号开功能,而版本号报得越高,程序越可能去用这台机器没有的东西(4.x 的 EXEC 参数块、5.x 的内存功能)。报低了只会让程序走保守路径;报高了会让它走进不存在的功能。**代价也要写下来**:少数程序要求 `>= 5.0` 才肯跑,它们会在本机上拒绝启动。等到真有这样的程序时,再决定是加 `SETVER` 还是整体升版本——**那时改的是同一个常数** |
| `PSP:50h` | **`CD 21 CB`** | 规范说这三个字节固定是 `INT 21h; RETF` |

## 七、来源没说的、或者互相矛盾的地方

| 位置 | 情况 | 目前的处置 |
|---|---|---|
| 命令行尾**是否以空格开头** | 规范只说「从程序名之后第一个字符开始」。多数二手资料直接说「以空格开头」,而 Stack Overflow 那一条明确反驳并给了反例 | **按规范走:原样复制程序名之后的字符**。本机的命令行由装载调用者给出,它给什么就是什么——**装载器不替调用者补一个空格**,因为「补空格」正是那个错误假设的写法 |
| FCB 解析的具体规则 | 规范说「按 CP/M 的格式」,而合法文件名字符集、通配符 `*`/`?` 的展开、`.` 与 `:` 的处理**细节各家说法不一** | W3 **只做「切出前两个以空格分隔的参数、把驱动器/名字/扩展名填进去」**,并把这一条当作**已知的近似**写在代码里。真正的 FCB 调用(`INT 21h` 的 `0Fh`–`29h`)在 M6,到那时再按真实程序的需要补齐 |
| `PSP:2Eh`(保存的 `SS:SP`) | 规范说是内部字段,刚装载时应当是什么**没有查到** | 写 `0` 并在代码里注明「刚装载时无意义」。**没有查到不等于不存在**,这一条列在这里而不是让它消失 |
| `PSP:05h` 的 CP/M 入口 | 规范给了它的**构造规则**(见第一节),但本机没有 `INT 30h` 的处理程序 | **五个字节写零**,并在第一节写明为什么不填。填出来会「看起来对、跳向虚空」,比留空更坏 |
| DOS 版本号的**最佳**取值 | 不存在这样的东西;它取决于要跑哪些程序 | 见第六节,取 `3.30` 并写明代价 |

## 九、`INT 21h` 的功能(按功能码,写一条是一条)

这一节记录 W4 核心，W5 文件和 W6 输入分别在第十、十一节。**第九至十一节都没有的功能码就是没写的**,本机对它做的事写在这一节末尾——那本身是一条要写下来的行为,不是一个漏洞。

### 调用与返回约定

`INT 21h` 用 **AH** 选功能。功能码各自用别的寄存器传参(下面每行写出来)。

DOS 2.0 以后,绝大多数功能用**进位标志**报成败:

- **CF 清零** = 成功;
- **CF 置位** = 失败,并且 **AX 里是错误码**(不是 AH)。

这一条是 DOS 2 相对 DOS 1 的改动,而它是**唯一**能报错的方式:`AH=09h` 这类老功能连 CF 的约定都没有(DOS 1 的调用没有返回值可言)。所以一个程序看到 CF 置位之后必须读 AX,而**只清 CF 不填 AX 的实现在成功路径上看起来完全正常**。

**来源:** [Ralf Brown's Interrupt List, INT 21/AH=30h 条目](http://mirror.math.princeton.edu/pub/oldlinux/Linux.old/docs/interrupts/int-html/rb-2711.htm);[Some MS-DOS Interrupts (METU CENG336)](https://saksagan.ceng.metu.edu.tr/courses/ceng336/2004/Some_MS.pdf)。

### 功能码

| AH | 名称 | 入 | 出 | 依据 |
|---|---|---|---|---|
| `00h` | 终止程序(老式) | — | 不返回 | 与 `INT 20h` 等价([SO 12591673](https://stackoverflow.com/questions/12591673/whats-the-difference-between-using-int-0x20-and-int-0x21-ah-0x4c-to-exit-a-16)) |
| `02h` | 输出一个字符 | `DL` = 字符 | 无(实机上 `AL` = 该字符) | [SO 37651270 的答案串](https://stackoverflow.com/questions/37651270/error-while-printing-a-string-from-assembly-code) |
| `09h` | 输出以 `$` 结尾的字符串 | `DS:DX` = 串 | 无(实机上 `AL` = `24h`) | 同上。`$` = `24h`,串里可以带 `0Dh`/`0Ah` |
| `0Dh` | 磁盘复位 | — | 无 | 清缓冲区,不改变任何程序可见的状态 |
| `0Eh` | 选默认驱动器 | `DL` = 驱动器(0=A) | `AL` = 机器上的驱动器数 | 本机一台,见下 |
| `19h` | 取当前默认驱动器 | — | `AL` = 驱动器(0=A) | 与 `0Eh` 同一个编号约定,**从 0 起**——写成 1 会让每个程序都去访问不存在的 B: |
| `1Ah` | 设 DTA | `DS:DX` = 缓冲区 | 无 | [Yale CS 的 int21-1a 页](http://www.cs.yale.edu/flint/feng/research/BIOS/Resources/assembly/int21-1a.html) |
| `25h` | 设中断向量 | `AL` = 向量号,`DS:DX` = 新地址 | 无 | [Ralf Brown, INT 21/AH=25h](https://www.cin.ufpe.br/~clac/infra_de_software/Art%20of%20Assembly.pdf) |
| `2Fh` | 取 DTA | — | `ES:BX` = 当前 DTA | 与 `1Ah` 成对 |
| `30h` | 取 DOS 版本 | — | **`AL` = 主版本,`AH` = 次版本**;`BX`=OEM,`CX`=序列号低半 | [Ralf Brown, INT 21/AH=30h](http://mirror.math.princeton.edu/pub/oldlinux/Linux.old/docs/interrupts/int-html/rb-2711.htm) |
| `35h` | 取中断向量 | `AL` = 向量号 | `ES:BX` = 当前地址 | 与 `25h` 成对 |
| `4Ch` | 带返回码终止 | `AL` = 返回码 | 不返回 | [SO 12591673](https://stackoverflow.com/questions/12591673/whats-the-difference-between-using-int-0x20-and-int-0x21-ah-0x4c-to-exit-a-16) |

**`30h` 那一格是本文件里错得最隐蔽的一处,值得单独说。** 三个二手来源都写「AL 是主版本、AH 是次版本」,而 `dos/include/vm86/dos.h` 里那段注释曾经把它写反(说 AH 是主版本),同时把常数 `0x1E03` 写对。**常数是对的,散文是错的**——`0x1E03` 的 `AL` 是 `03`、`AH` 是 `1E`,也就是 3.30;按注释读会读成 30.3。Ralf Brown 的原条目是 `AL = major version number`、`AH = minor version number`,这里按它。

### 错误码(本机用到的)

| 码 | 含义 |
|---|---|
| `01h` | 功能号无效 |
| `02h` | 文件没找到 |
| `03h` | 路径没找到 |
| `04h` | 打开的文件太多 |
| `05h` | 拒绝访问 |
| `06h` | 句柄无效 |
| `0Ch` | 访问方式无效 |

**来源:** [Ralf Brown's Interrupt List, 错误码表](http://www.cs.yale.edu/flint/feng/research/BIOS/Resources/assembly/int21-1a.html)。

### 本机对**没实现的功能码**做什么(决定,不是事实)

**`AL = 0`,并置 CF。**

这条是查过的,不是猜的:FreeDOS 内核把没实现的功能统一落到一个默认处理里,**返回 `AL = 0` 并置 CF**。同一封邮件还说,曾经有一版返回 `AX = 1`("未知功能"),那一版**把 4DOS 弄坏了**——因为程序看到 CF 置位后会读 AX,而 `AX = 1` 和"一个字节的 0"对调用方是两件事。所以本机跟 FreeDOS 现在的做法,而不是它曾经的做法。

**为什么不是"什么都不做"**:这台机器的**固件**层对没实现的中断就是"原样返回",而那是 BIOS 的正确行为——BIOS 没有"调用失败"这个概念。DOS 有,而且 `INT 21h` 的绝大多数功能都有 CF 约定,所以这里不能用固件那条规矩。**两层用不同的约定,是因为两层本来就有不同的约定**,这一点写在 `dos/dos/int21.c` 里。

**来源:** [FreeDOS kernel 邮件列表, "Phantom" 功能与默认处理](https://marc.info/?l=freedos-kernel&m=106924917001824&q=mbox)。

### 终止:本机怎么做,以及没做什么

`INT 20h`、`INT 21h AH=00h`、`INT 21h AH=4Ch` 三条路都**让机器停下来**,返回码分别是 0、0、`AL`。`INT 20h` 与 `AH=00h` 的返回码是 0,DOS 2 以后也是这样处理的。

**没做的两件事,写在这里而不是让它消失:**

- **不走 `INT 22h`。** 真实 DOS 终止时把 `INT 22h/23h/24h` 从 PSP 里恢复回向量表,然后**远跳到 `INT 22h` 向量里存的地址**——那是"程序该回到哪里"。本机没有父进程也没有 EXEC(`AH=4Bh` 是 M6),那个地址是装载器抄下来的、指向一段没有意义的代码,跳过去会死在别的地方。**机器停下来、返回码交给宿主**是这里唯一能诚实做到的事。
- **不释放内存。** 一个 `.COM` 拿到的是到常规内存顶端的全部空间,而本机没有分配器(`AH=48h`/`49h`/`4Ah` 都在 M6)。程序停了,它的那一整个地址空间随进程消失——这是宿主进程模型给的,不是 DOS 语义给的,而两者的区别在一个程序终止后还想让另一个人接着用那块内存时才看得出来。

**来源:** [SO 12591673](https://stackoverflow.com/questions/12591673/whats-the-difference-between-using-int-0x20-and-int-0x21-ah-0x4c-to-exit-a-16)(`INT 20h` 与 `AH=00h` 等价、`4Ch` 不依赖 `CS`、DOS 2+ 把 `INT 20h` 当作 `4Ch` 返回码 0)。

## 十、W5：文件句柄、目录查找与 FAT 镜像

**本节的原件依据**：本地 `reference-msdos/v2.0/source/XENIX.ASM`
（`$Open`、`$FIND_FIRST`、`$FIND_NEXT`）、`XENIX2.ASM`
（`$Read`、`$Write`、`$LSEEK`）；BPB 字段顺序对照
`reference-msdos/v4.0/src/INC/BPB.INC` 的 `BPBLOCK` / `A_BPB`。
补充查阅 Ralf Brown 的 `INT 21h/AH=40h` 条目：零字节写会截断或
扩展到当前位置；磁盘满通常表现为成功但 `AX<CX`。
因此本节不再是“全无原件”的依据。W3/W4 的历史来源没有因此自动升级。

| AH | 输入 | 成功（CF=0） | 失败（CF=1） |
|---|---|---|---|
| `3Ch` | DS:DX=NUL 路径，CX=属性 | AX=句柄；存在则截断，不存在则创建 | AX=DOS 错误码 |
| `3Dh` | DS:DX=NUL 路径，AL 低三位=0/1/2（读/写/读写） | AX=句柄 | 同上 |
| `3Eh` | BX=句柄 | 关闭 | 同上 |
| `3Fh` | BX=句柄，CX=最大读取数，DS:DX=缓冲区 | AX=实际读取数；EOF=0 | 同上 |
| `40h` | BX=句柄，CX=写入数，DS:DX=缓冲区 | AX=实际写入数；CX=0 按当前位置改长度 | 同上 |
| `41h` | DS:DX=NUL 路径 | 删除文件、释放 FAT 链 | 同上 |
| `42h` | BX=句柄，AL=0/1/2（头/当前位置/尾），CX:DX=32 位位移 | DX:AX=新位置 | 同上 |
| `4Eh` | DS:DX=8.3 通配路径，CX=搜索属性 | 当前 DTA 获得第一项 | 同上 |
| `4Fh` | 当前 DTA 的保留区=上次查找状态 | 当前 DTA 获得下一项 | AX=`0012h`（18），无更多文件 |

### DTA：公开布局和私有布局不要混为一谈

返回区的公开布局是 **43 字节**：`15h` 属性，`16h` 时间 word，
`18h` 日期 word，`1Ah` 大小 dword，`1Eh` ASCIIZ 文件名（13 字节）。
`00h..14h` 是 DOS 保留区，**本机不承诺复制 MS-DOS 的内部格式**。
本机在其中保存目录簇、下一项序号、8.3 模式、属性与标记。
状态属于 DTA 而不是全局“最后一次搜索”，所以换两块 DTA 可以交错查找。

普通文件（含只读和 archive）总可参加普通搜索；hidden/system/directory
需在搜索属性中选入，volume label 仅在卷标搜索中选入；跳过 LFN 和已删除项。
`*`/`?` 按 8.3 名字匹配；比如 `*.*` 包括没有扩展名的文件。
搜索耗尽返回 18；本机对没有匹配项的 FindFirst 同样返回 18。

### 本机决定、容量和错误

- **F: 是唯一盘**。支持大小写不敏感的 8.3 根目录路径和现有子目录链；
  `/` 与 `\` 均可分隔。没有当前目录、长文件名、mkdir/rmdir、rename、设备名解析。
- FAT12/FAT16 **superfloppy** 从 BPB 解析，不从文件扩展名或卷标猜格式；
  没有 MBR 分区选择、FAT32、exFAT。签名、扇区/簇尺寸、元数据边界、
  FAT 容量、链越界/坏簇/环都需通过检查；子目录扩容暂不支持。
- 文件句柄 `5..20`，最多 16 个。0=控制台输入；1/2=控制台输出；3/4
  不提供设备实现。`3Fh` 对 0 目前一次返回一个原始控制台字节，
  **没有实现完整的可重定向 DOS cooked stdin**。
- `3Dh` 支持兼容共享模式及 bit 7 的不继承标记（目前无 DOS EXEC），
  其他共享模式明确返回错误 12，不假装提供文件锁。
- 错误码：1=功能/定位不合法，2=文件不存在，3=路径不合法，4=句柄用尽，
  5=访问被拒（权限/只读/目录/删除或截断正在打开的文件），6=坏句柄，
  12=模式不合法，13=数据/镜像/guest 缓冲区不合法，15=未挂载/无此驱动器，
  18=搜索耗尽，39=无法完成零字节扩展。
- 负定位会失败；可以定位到 EOF 之后，之后写入时空洞清零。
  磁盘满时普通写允许短写；零字节扩展的容量不足返回失败，不能静默改元数据。
  FAT12 的相邻偶/奇项共享一个字节，写入必须保留另一项，且更新所有 FAT 副本。
- **镜像是 VM 进程的私有可写副本**。内核 ramfs 只通过 `DOS.IMG`
  交付字节，FAT 解析和 DOS 文件处理不在内核里。写入跨句柄可见，
  同次运行关闭后再打开可见；新运行重新挂载，**不持久化**。
  这是 W5 对原计划“先只读”的有界扩展，用来真正验 `3Ch`/`40h`/`41h`。
- guest 路径读取有界，缓冲区逐字节检验，段内 offset 按 16 位回绕。
  不合法缓冲区不能推进文件位置或消耗键盘输入。

## 十一、W6：DOS 输入、原始扫描码与阻塞服务

**原件依据**：`reference-msdos/v2.0/source/MISC.ASM` 的 `$RAW_CON_IO`
和 `$RAW_CON_INPUT`（6/7），`STRIN.ASM` 的 `$STD_CON_STRING_INPUT`
（10：容量为零立即返回，最大字符数预留一个 CR，退格编辑），
`CTRLC.ASM` 的 `INT int_ctrl_c`；BIOS 扫描码/ASCII 的依据仍是
姊妹篇 `dos-refs.md` 的键盘节。标准调用号还可对照 `MSCODE.ASM` 的分发表。

| AH | 行为 | 返回 |
|---|---|---|
| `01h` | 阻塞读一个字符，回显，检测 Ctrl-C | AL=字符 |
| `06h` | DL!=FFh 输出 DL；DL=FFh 非阻塞、不回显读 | 有键：ZF=0、AL=字符；无键：ZF=1、AL=0 |
| `07h` | 阻塞、不回显，不检测 Ctrl-C | AL=字符 |
| `08h` | 阻塞、不回显，检测 Ctrl-C | AL=字符 |
| `0Ah` | DS:DX=输入缓冲区；[0]=容量，[1]=字符数，[2..]=正文 | [1] 不含 CR，正文尾含 CR；编辑和回显 |
| `0Bh` | 非阻塞可用性查询，不消费普通键，检测 Ctrl-C | AL=FFh 有键，AL=0 无键 |

扩展键按 DOS 两次字节读取约定返回 **00h、扫描码**；第二个字节尚待
返回时 `0Bh` 必须报告可用。`0Ah` 当前支持退格、容量约束、CR 和空
缓冲区；不实现 DOS 的 F1–F5 模板编辑、重定向行编辑、Ctrl-Z 文本 EOF。
未提供标准句柄重定向，输出仍走同一份 BIOS teletype。

检测到 Ctrl-C 的调用走 **guest 的 INT 23h 向量**，不是绕过向量直接杀死。
本机默认处理器返回退出码 3（本机策略，不声称是 MS-DOS 规定值）；
guest 通过 `25h` 替换处理器后可以观察到调用并 IRET 返回。
`06h`/`07h` 不走这个检测。

### 原始字节是资源，不能用字符反查

8042 translation 明确启用，使系统调用交出的流为 **set 1**。
`SYS_KBD_ACQUIRE/POLL/RELEASE` 按进程独占原始流，保留 E0/E1、modifier、
make、break 字节；为空立即返回 -1，溢出返回 -10，不把漏掉的 break
伪装成正常输入。持有原始流期间，键盘 IRQ 不再给 Shell 的译码队列
追加副本；显式释放或进程销毁清空队列与修饰键状态。另有非阻塞的
`SYS_POLLKEY` 返回译码键或 0，供验收页释放后返回控制台时使用。

VM 在 slice 边界只在 BIOS 8042 latch 空闲且没有 pending IRQ 时取一个
字节，再交 `bios16_key_arrived()` 和 INT 09h；不会把一次 Shift+B 当成
一个翻译后的字符，也不会覆盖还没消费的控制器字节。

### 纠正阻塞服务的旧注释和嵌套帧记录

`vm86_service_retry()` **不弹出 guest 的 INT 帧**，也不重跑 INT；它
把 IP 指回现有 stub 的 host trap，并开 IF 让真实键盘 IRQ 能进入。
所以等待时有一个 live frame（SP 比调用前低 6），不是栈泄漏；输入
到达后同一个 IRET 返回，SP 恢复。旧 BIOS16 注释把这一点说反了。

原来的 `intr_frame_sp` 单值会被嵌套键盘/定时器中断覆盖。
现在 INT 记录 SS:SP 的帧栈，IRET 恢复外层帧身份；far-call 链仍拒绝
冒充 INT 帧。最多记录 64 层，再深仍执行 guest 中断但拒绝猜测服务
flags 写回。flags 计数器在机器清服务时重置，避免前一台机器的结果污染下一台。

### W6 的硬件验收覆盖什么

`KEYS.COM` 在宿主与 QEMU BIOS/UEFI 跑相同字节；QEMU monitor 依次注入
`a`（AX=1E61h）、`Shift+B`（3042h）、`Up`（4800h）、`F1`（3B00h），
先 INT16h/01h peek，再 /00h take；随后 DOS /01h 与 /0Ah 验回显和
`d、Backspace、e、Enter` 编辑结果。普通字符的 scan 与 ASCII 不相等，
方向键与功能键的 ASCII 是零，**字段交换不能混过去**。
BIOS/UEFI 的页各 32,000 条扫描线经截图比对；释放原始流后真实 Enter
经非阻塞译码接口返回；Shell 的 DOS 命令回归再确认连续运行和资源释放。
