# FunnyOS 设计文档

**版本**: v0.1
**日期**: 2026-09-27
**定位**: 原生 x86-64 操作系统，内建 8086 虚拟机，以原生执行 16 位 DOS 程序为核心使命

---

## 0. 一句话定义

FunnyOS 是一套全新的 64 位操作系统。它不基于 MS-DOS 的代码，但在**设计哲学**上以 DOS 为基准参考——小内核、直白的分层、命令行交互、程序对机器有充分的控制权——同时在一个关键点上明确背离 DOS：**它用现代 x64 硬件的保护机制兜住 DOS 程序的崩溃，而不是让它们拖着整机一起死。**

DOS 在这里扮演两重角色：

1. **设计参照系**——什么该继承（简单、直接、可理解），什么该抛弃（无保护、单任务作为限制、1MB 天花板）。
2. **测试语料库**——`microsoft/MS-DOS` 仓库能编译出真实的 `.COM` / `.EXE`（DEBUG、EDLIN、FORMAT、CHKDSK 等），这是验证模拟器兼容性的现成素材，比任何自造测试都硬。

## 1. 核心设计决策

每一条决策都附了理由和被我否决的替代方案。**D1 是整个项目的地基，如果它错了，后面全错。**

### D1 ★ DOS 程序的执行机制：纯软件 8086 解释器

**决策**：自己写一个 8086 指令集解释器，在 64 位长模式下纯软件模拟 16 位实模式环境。

**理由（这条决定了项目的可行性边界）**：

x64 长模式**不提供 virtual 8086 模式**。vm86 是 80386 为 32 位保护模式引入的，一旦 CPU 进入 64 位长模式就彻底不可用（32 位保护模式操作系统反而可以用）。这条硬件事实砍掉了最省事的路径。

硬件虚拟化（Intel VT-x）理论上是另一条路：用 unrestricted guest + EPT，可以让 VMEntry 直接进入未开分页的实模式 guest。但要注意两点：

- **早期 VT-x 做不到这件事**。只有 Westmere（2010）之后的 unrestricted guest 特性才允许 VMEntry 进未开启分页的 guest。这意味着方案对 CPU 世代有硬性要求。
- **复杂度完全不成比例**。VMCS 配置、EPT 页表维护、VM exit 分类处理、中断虚拟化、实模式 guest 的段语义处理——光是让一个实模式 guest 跑起来并正确响应 `cli`/`popf`/中断，代码量就远超一整个 8086 解释器。而且这类代码**极难调试**：你面对的是 VM exit 日志而不是可单步的执行流。

相比下，软件解释器的代价是性能。但性能在这里**不是瓶颈**：

- 现代 CPU 上一个优化良好的解释器（函数指针分发 / threaded code，而非巨型 switch）可以跑到等效 100–500 MHz 8086 的水平。DOS 时代绝大多数程序的原始硬件是 4.77–33 MHz。
- DOS 程序的真实瓶颈通常在 I/O 和 BIOS 调用，而不是 CPU 指令吞吐。一个等待键盘输入的 DOS 程序，解释器跑多快毫无区别。
- DOSBox 二十多年的实践已经证明：性能优先型的解释器（每模拟周期执行一条指令、忽略真实时钟）足以覆盖绝大多数 DOS 软件。

**被否决的方案**：

| 方案 | 否决理由 |
|---|---|
| 硬件虚拟化 (VT-x/AMD-V) | 复杂度高一个数量级，有 CPU 世代要求，调试困难，对 16 位实模式收益接近零 |
| vm86 模式 | x64 长模式下硬件层面不存在 |
| 降级到 32 位保护模式用 vm86 | 那就不是"x64 操作系统"了，违背项目目标 |
| 动态二进制翻译 (JIT) | 正确，但属于优化阶段的事，不做在第一步。路线已预留（见 §3.3） |

### D2 语言：C + 汇编

**决策**：内核与模拟器用 C（C17，freestanding），引导和底层用 NASM 汇编。

**理由**：裸机 x64 的资料、参考实现、社区经验几乎全部是 C。8086 解释器尤其适合 C——它是一个巨大的译码分发循环加上大量位运算，C 的表达能力刚好，而它需要的高效指针跳转（computed goto）也是 GCC 扩展支持的。

**被否决**：Rust（裸机生态年轻，unsafe 边界和链接脚本的坑更多，且模拟器核心是一个天然 unsafe 的位操作密集结构，Rust 的安全性在这里收益有限）；Zig（社区 OS 参考资料明显不足）。

### D3 引导：Limine 引导加载器

**决策**：使用 Limine 作为引导加载器，通过 Limine 引导协议进入内核。

**理由**：Limine 是活跃维护的现代多协议引导加载器（v12.x，BSD-2-Clause，支持 x86-64 的 BIOS 与 UEFI 双路径）。它替内核完成了三个繁琐且容易出错的步骤：进入 64 位长模式、获取物理内存映射、初始化帧缓冲。把这几件事交给引导器，意味着内核代码可以从第一天就专注于内核本身。

**被否决**：自研 UEFI 应用（教育价值高，但会把 M0 从一周拉长到一个月，且这部分工作与"跑 DOS 程序"的核心目标无关）；GRUB/Multiboot2（协议更老，帧缓冲和内存映射没有 Limine 协议干净）。

**后路**：Limine 是引导层，与内核通过一个明确定义的协议接口隔开。如果将来想换成自研 UEFI 加载器，只需要重写填充内核入口数据结构的那一段。

### D4 模拟器的特权级：Ring 3 用户态进程

**决策**：8086 虚拟机的解释器运行在 Ring 3，作为一个普通用户态进程。

**理由**：解释器主循环的性能与特权级**完全无关**（同样的指令在同样的 CPU 上执行，进出 Ring 0 不带来任何循环内的开销）。而把模拟器放在用户态，几乎免费地获得了 MMU 提供的隔离——guest 能碰到的内存就是宿主分配给模拟器进程的那块区域，越界访问会触发宿主内核的 page fault，而不是静默地破坏系统。

结果是：**一个 DOS 程序崩溃只杀死它自己**。这是 FunnyOS 在哲学上明确背离 DOS 的地方——DOS 把"程序能搞死整机"当作设计的一部分，FunnyOS 不继承这个缺陷。

**唯一需要跨特权级的地方**是 guest 请求宿主服务时（INT 21h 文件操作、INT 10h 显示输出、INT 16h 键盘输入）。这些是**低频操作**——一个典型 DOS 程序每秒发起的服务调用在几百到几万次量级，每次几十纳秒的 syscall 开销完全可忽略。

**被否决**：模拟器跑在内核态。快一点点，但失去了全部隔离，且把一个大而复杂的组件拖进了内核地址空间。

### D5 内存模型：宿主连续映射 + guest 分段翻译

- 宿主为每个 VM 分配一块**连续虚拟地址区域**作为 guest 的物理内存（基础 1 MB + 扩展内存池，初期合计 16 MB，预留增长到 64 MB）。
- guest 看到的 1 MB 地址空间映射到该区域的前 1 MB（含 0xA0000–0xBFFFF 的显存窗口、0xC0000–0xFFFFF 的 ROM 区域）。
- **段:偏移 → 线性地址**：`(seg << 4) + off`，**不按 20 位环绕**。
  20 位折返只在 A20 关闭时发生（`mem.c` 的 `vm86_mem_offset`），而 A20 默认是打开的，所以线性地址可以越过 1 MiB 进入扩展池——这正是下一句那 16 MB 能成立的前提。原句写的"按 20 位环绕（A20 逻辑）"与代码不符，也与它自己的下一句矛盾：真按 20 位环绕，多出来的 15 MB 永远够不着。（2026-10-01 由任务 L 查出，改文档不改代码。）
- **线性地址 → 宿主指针**：`base + linear`，线性地址超出 guest 物理内存时不报错，而是映射到一块共享的"洞"页（反映真实硬件行为：读未映射内存返回 0xFF，写被丢弃）。
- 对 0xA0000–0xBFFFF 的**写入被拦截**，转发到宿主显示子系统（见 §3.4）。

### D6 中断模型：IVT 改写检测 + 宿主服务挂钩

DOS 生态的重要事实是 **TSR（常驻程序）会改写中断向量表**来劫持系统调用。天真的"拦截所有 INT n"实现会让所有 TSR 失效。

采用的模型（与 DOSBox 一致）：

1. VM 初始化时在 guest 内存中为每个宿主提供的服务（INT 10h/13h/16h/1Ah/21h 等）安装一段小的 stub，并把 IVT 对应项指向该 stub。stub 内容是一条特殊的宿主陷阱指令。
2. guest 执行 `INT n` 时，解释器查找 `IVT[n]`：
   - 若仍指向我们安装的 stub → 调用宿主实现。
   - 若已被改写成其他地址 → 按 guest 内存中的地址正常跳转（TSR 接管了）。
3. 链式调用（TSR 保存旧向量并在处理完后跳回）因此自然工作。

> **M4 的实现方式与上面两句有一处出入，记在这里。** 上面第 2 条读起来像是"解释器要特判 `INT n`"，实际上不需要：`INT n` **一个字都不用改**——它照常读 `IVT[n]` 压帧跳过去，落到桩上就进宿主服务，被改写就进 TSR 的处理程序。
>
> 而"向量有没有被改写"**不是靠监听对 `0x0000-0x03FF` 的写**，是靠**投递时比较**：`IVT[n]` 是否还等于我们装进去的那个地址。同一个答案，少一套机器，而且不需要在每条 `mov [bx], ax` 上多一次范围判断。这就是 `vm86_vector_is_stub()`。

### D7 显示：从文本模式到图形模式的四级路径

| 阶段 | 模式 | 用途 |
|---|---|---|
| S1 | 宿主帧缓冲上的软件文本网格 (80×25, 内建字体) | 内核控制台、Shell |
| S2 | VGA 文本模式兼容 (0xB8000 语义、属性字节、光标) | 绝大多数 DOS 命令行程序 |
| S3 | VGA 模式 13h (320×200×256 调色板) | 老游戏 |
| S4 | VESA/VBE 线性帧缓冲模式 | 现代一点的 DOS 图形程序 |

阶段 S2 是 DOS 兼容性的关键——大量 DOS 程序直接写 0xB8000 而不通过 BIOS，所以模拟显存窗口必须支持属性字节（前景/背景/闪烁）的完整语义。

### D8 文件系统：宿主 FS + FAT 镜像挂载

两条并行的路径：

- **宿主路径映射**：DOS 的 `C:\FOO\BAR.TXT` 映射到宿主的某个文件系统路径。便于用户直接用宿主工具管理文件。
- **FAT 镜像挂载**：把一个 FAT12/16/32 镜像文件挂载为 DOS 的一个驱动器号。这是兼容性最好的方案——可以用 `mtools` 之类的现成工具在宿主机上准备镜像，模拟器只需实现 FAT 的读写。

初期优先做 **FAT 镜像挂载**，因为它把"磁盘"这个概念的复杂性封装在一个文件里，且与真实 DOS 的行为最接近。

## 3. 8086 虚拟机详细设计

这是项目的核心，也是工作量最大的部分。

### 3.1 CPU 状态

```c
struct vm86_cpu {
    /* 通用寄存器 — 同时保留 16 位视图和 8 位高低字节视图，
       避免每次访问都做掩码运算 */
    union { uint16_t ax; struct { uint8_t al, ah; }; };
    union { uint16_t bx; struct { uint8_t bl, bh; }; };
    union { uint16_t cx; struct { uint8_t cl, ch; }; };
    union { uint16_t dx; struct { uint8_t dl, dh; }; };
    uint16_t si, di, bp, sp;
    uint16_t cs, ds, es, ss;

    uint16_t ip;
    uint16_t flags;              /* CF PF AF ZF SF TF IF DF OF */

    /* 段基址缓存：段寄存器改变时重算，避免每次内存访问都左移 */
    uint32_t seg_base[4];        /* CS DS ES SS 的线性基址 */
    uint8_t  seg_dirty;          /* 位图，标记哪个需要重算 */

    /* 挂起的中断（硬件注入用） */
    uint8_t  pending_int;
    int      halted;

    /* 性能与调试 */
    uint64_t insn_count;
    struct vm86_mem *mem;
};
```

**设计要点**：段基址缓存（`seg_base`）是必要的优化。若不缓存，每次内存访问都要做 `(seg << 4) + off` 两次移位加一个加法；DOS 程序的内存访问极度密集，这个开销会直接反映在性能上。

### 3.2 指令译码与执行

**采用函数指针分发表（threaded dispatch），而非巨型 switch。**

解释器性能的关键是译码分发的效率。一个 `switch` 覆盖全部 8086 操作码会让编译器生成稀疏跳转表，分支预测表现差。标准做法是：

1. 一级表按操作码（256 项）索引，指向处理函数。
2. 对前缀指令（`0F`、段前缀 `26/2E/36/3E`、`F0/F2/F3`），先解析前缀再查二级表。
3. 每个处理函数执行完直接 `return` 下一条指令的地址或调用下一轮分发，减少循环开销。

```c
typedef int (*op_fn)(struct vm86_cpu *cpu);

static const op_fn opcode_table[256] = { /* ... */ };

int vm86_step(struct vm86_cpu *cpu) {
    uint8_t op = fetch8(cpu);
    return opcode_table[op](cpu);   /* 返回 0 = 继续, 非 0 = 异常 */
}
```

**指令集覆盖范围**（按优先级分三档）：

| 档位 | 内容 | 说明 |
|---|---|---|
| P0 | 完整 8086 指令集 | 算术/逻辑、数据传送、串操作、控制流、标志位操作 |
| P1 | 80186/286 扩展 | `PUSHA`/`POPA`、`ENTER`/`LEAVE`、多操作数 `IMUL`、移位立即数。**必须做**——大量 DOS 程序用了 186 指令 |
| P2 | 286 保护模式指令 | `LGDT`/`LIDT`/`LMSW`/`CLTS` 等。用于支持部分 DOS extender 程序，后期 |
| P3 | 8087/387 浮点 | 通过宿主 SSE 指令实现。**大量老游戏依赖**，属于后期里程碑 |

### 3.3 性能路径（预留，不在初期实现）

分三步演进，每一步都是前一步的严格超集：

1. **朴素解释器**（M3）：译码 → 立即执行。
2. **译码缓存**：把已译码的指令块缓存起来，跳过重复译码。对循环密集的代码收益显著。
3. **基本块 JIT**：识别基本块，翻译成宿主 x64 机器码。这是 DOSBox-X 等项目的做法，可以把性能推到等效 GHz 级别。**只在有实测需求时做。**

### 3.4 guest 内存访问

所有 guest 内存访问必须通过受检查的访问函数，不得直接解引用：

```c
static inline uint8_t  mem_r8 (struct vm86_cpu *cpu, uint32_t lin);
static inline void     mem_w8 (struct vm86_cpu *cpu, uint32_t lin, uint8_t v);
/* ... r16/w16, 以及显存窗口的特殊处理 */
```

这层间接看起来是性能负担，但现代编译器会把它内联掉，实际开销主要是地址计算和边界判断。**代价换来的是**：所有越界访问都被捕获，显存窗口写入被正确拦截，未映射区域返回硬件一致的值。

**显存拦截**：`0xA0000–0xBFFFF` 的写入不落在 guest 内存上，而是转发到宿主显示子系统：

```c
if (lin >= 0xA0000 && lin < 0xC0000) {
    display_write(cpu->mem->vga, lin - 0xA0000, v, size);
    return;
}
```

> **M4 不这么做，记在这里免得它读起来像是忘了。** M4 里 `0xB8000` 就是 guest 内存里的一块**普通 RAM**，宿主**从那里读**去渲染（`vm86_display`）。
>
> 代价是：图形模式（M7）**必须**回来做上面那个重定向，因为那时一条扫描线的字节不是"屏幕上的东西"而是一个索引。换来的是：**直接写 `0xB8000` 再读回来的程序看到的是自己写的东西**——重定向方案里它读到的是别处，而这是程序真的会做的事（属性字节尤其）。
>
> 所以 M4 的显存约定是"约定"不是"拦截"：地址、布局、属性位在 `dos/include/vm86/firmware.h` 里是冻结的，拦截机制留到 S3。

### 3.5 中断投递

硬件中断（定时器、键盘）由模拟器主循环在每条指令边界检查：

```c
while (vm_running) {
    if (cpu->pending_int && (cpu->flags & IF)) {
        deliver_interrupt(cpu, cpu->pending_int);
        cpu->pending_int = 0;
    }
    vm86_step(cpu);
}
```

若 `IF` 被清除（`cli`），中断保持挂起，直到 `sti` 后生效。这与真实硬件行为一致。

## 5. 构建与测试

### 5.1 工具链

**构建主机：WSL2 Ubuntu**（已确认本机可用，Ubuntu 发行版已安装）。裸机开发的标准工具链在 Linux 上是原生的，这是最省事的路径。

需要安装：`build-essential`、`nasm`、`qemu-system-x86`、`xorriso`、`mtools`、`gdb`、`git`、`limine`。

**不用 Visual Studio / MSVC**，尽管本机已安装（VS 2026 Community, MSVC 14.51）。裸机内核需要完全控制链接布局、无 CRT、无 SEH、自定义链接脚本，MSVC 在这方面的可配置性远不如 GCC；而且 QEMU/nasm/make 生态在 WSL 里是原生的。

### 5.2 编译标志

```
CFLAGS = -std=c17 -ffreestanding -fno-stack-protector -fno-pic \
         -mno-red-zone -mcmodel=kernel -mno-sse -mno-sse2 \
         -nostdlib -Wall -Wextra -Werror -O2 -g

NASMFLAGS = -f elf64 -g -F dwarf
```

`-mno-red-zone` 是必须的——x86-64 的 red zone 假设存在有效栈，中断处理会破坏这个假设。
`-mcmodel=kernel` 把代码放在地址空间上半区。

### 5.3 测试策略

| 层次 | 手段 |
|---|---|
| 内核单元测试 | 无硬件的纯逻辑模块（分配器、页表、FAT 解析）编译成宿主可执行文件直接跑 |
| 内核集成测试 | QEMU + `-serial stdio`，串口输出断言 |
| 崩溃诊断 | QEMU + GDB stub (`-s -S`)，符号已通过 `-g` 带上 |
| 模拟器指令测试 | 对每条指令构造小型测试程序，比对预期寄存器/标志位状态 |
| **模拟器兼容测试** | **MS-DOS 4.0 源码编译出的真实 .COM/.EXE** ← 最有价值的测试 |

`make run` 封装成一条命令：编译 → 构造镜像 → 启动 QEMU。

### 5.4 关于测试语料库

前面克隆的 `microsoft/MS-DOS` 仓库（在 `reference-msdos/`）有一个超出"参考阅读"的用途：

**它能编译出真实的 DOS 程序和工具**——`DEBUG.COM`、`EDLIN.COM`、`FORMAT.COM`、`CHKDSK.COM`、`XCOPY.EXE` 等等，全都是 1988 年真实发布的二进制，全都在 MIT 许可下。

这给了我们一个**分难度梯度的兼容性测试集**：

- 最简单：自己写的 `hello.com`（只调 INT 21h 的 09h 输出）
- 中等：`EDLIN.COM`（行编辑器，大量字符 I/O + 文件操作）
- 较难：`DEBUG.COM`（自己就是一个调试器，涉及内存读写和多种服务）
- 最难：`FORMAT.COM`、`CHKDSK.COM`（直接操作磁盘扇区，走 INT 13h）

比自造测试程序有价值得多——它们会撞上你没预料到的边界情况。这也让之前对 MS-DOS 源码的调研有了第二重回报。

**M0 实际达成的范围**（超出原定验收标准）：不仅串口有输出，还完整解析并展示了引导器信息、固件类型、内核物理/虚拟基址、HHDM 偏移、物理内存映射汇总、帧缓冲参数，且在 BIOS 与 UEFI 两条固件路径上都有自动化断言覆盖。

**M1 已完成的部分**：GDT/TSS（含 16 KiB 的 #DF / NMI IST 栈）、256 向量 IDT、完整的 CPU 异常诊断（错误码解码、CR2、RFLAGS、段选择子、控制寄存器、全部通用寄存器）、物理页帧分配器（位图）、页表管理（映射/解映射/查询，含 1 GiB 与 2 MiB 大页拆分）、内核堆（带拆分与合并的空闲链表）、ACPI MADT 解析、本地 APIC 与 I/O APIC 初始化、以 PIT 为基准标定的 LAPIC 定时器（100 Hz）。验收标准已达成，并由自动化故障注入测试与定时器自检覆盖。

**关于定时器标定**：LAPIC 定时器无法自报频率——它的计数基准随 CPU 型号在 24 MHz 到核心频率之间浮动。因此频率是**测出来的**而不是假设的：用 8254 PIT 的 1.193182 MHz 晶振作为参考时标，实际测量一个已知区间。同一窗口顺便标定了 TSC，得到一个分辨率为亚微秒的自由运行时钟。每次启动时会用 TSC 复核实际 tick 速率，只有当测得值与编程值相符才报告 PASS。

一个诚实的限制：**这条自检在 QEMU 下比看起来弱**。模拟器里 PIT、TSC 与 LAPIC 定时器都源自同一个虚拟时基，所以它们之间不可能互相发现误差；只有在真机与 VMware 上，PIT 晶振和 TSC 的 PLL 才是彼此独立的振荡器，标定才是一次真实测量。这也是为什么 ISR 与定时器的验证不能只靠模拟器。

目前的验证状态：**VMware Workstation 上已确认能正常启动并进入 Shell**（见 README 里的截图，走的是 BIOS 固件路径），标定值本身尚未记录；**真机上还没试过**。这是 M1 唯一一项还欠着的验证。

**M2 已完成的部分**：PS/2 键盘驱动（含 28 组扫描码序列的解码自检）、带回显与退格的行编辑、进程与私有地址空间、`int 0x80` 系统调用、只读内存文件系统，以及 Ring 3 的 Shell（FunnyCOM）。验收标准已达成，并且有一项专门的测试证明**程序崩溃不会拖垮内核**。

**M3 已完成的部分**：一个纯软件的 8086 解释器，全部 256 个操作码槽位，加 80186 扩展——CPU 状态与标志位规则、ModRM 解码、取指与分发循环、内存模型，以及一个单步调试器。**它作为 Ring 3 进程运行在 FunnyOS 里**：内核以 `vm=1` 启动时把同一份用户镜像跑成解释器模式，接上由加载器映射并清零的 guest 内存，跑完一段手工汇编的 guest，把终态交出来给自动化断言比对（`make test-vm`）。

**这一层是怎么被验证的，比测试数量重要。** 十二个套件、四百多个用例，但真正说明问题的是**变异测试**：往实现里种一个缺陷，看对应用例变不变红。三处独立的变异活动合起来种了一百二十多处，**每一条用例都被至少一个变异体弄红过**——没有空洞用例。而三处各自的第一轮都暴露过漏洞：F 那批第一轮有四条用例没能被任何缺陷弄红，四条全是测试自己的问题（两个段基址的低 16 位都是 0，所以截断之后看不出用了哪个基址；只断言了 `IP`，而没被消费的那个字节恰好是 `PUSHA`；`ModRM` 的写回写在没被断言的那个寄存器上）。**不做变异测试，那四条会一直绿着。**

**M3 诚实地说没有证明什么**：全部期望值都是**按 8086 编程模型推导**的，没有一条对照过真实硬件——机器上没有手册，也没有 DOSBox。推导的来源不止一处（两批人各自独立写了一整套用例和一批样本），两批在重叠处**全部一致**；但**两个独立推导之间的一致，不覆盖它们共享的盲区**。`PUSH SP` 就是这么被抓到的：两批都测过它，两批都只走了 `54` 这一种编码，而 `FF F4` 是另一条编码，压进栈的值不一样。

**M3 还开着的**（都不在验收标准之内，记在这里是为了它们不消失）：

1. **中断投递**按计划留给 M4。`REP` 的不可中断性、`STI` 的延迟生效、`MOV SS` 对中断识别的抑制——这三条在 M3 里**完全观察不到**，M4 写投递时要一并处理。
2. **Shell 还不能启动 VM。** 卡住它的那件事**已经解决**（M5 的 W1）：`process_run()` 现在把当前进程、当前 PML4、TSS 内核栈指针和向量寄存器四样在进入时保存、离开时还原，并新增了 `SYS_SPAWN`，一个程序可以启动另一个程序并拿回它的退出码。剩下的是 VM 本身还没成为一个独立进程——它今天仍是同一份用户镜像的一个模式（见本节第 4 条），那属于 M5 的 W2/W3。
3. **`POP SP` 的终值没有定论。** 手册的措辞照字面读是 `2002h`，实现给的是 `2000h`；用例钉住了当前行为并标明是开放点，需要手册才能裁决。
4. **`dos/` 与内核的接口只有一处**（那个启动参数）。VM 现在是同一份用户镜像的一个模式，不是架构图里那个独立进程；那要等第 2 条解决。
5. **`0F`、`60`–`6F`、`MOV CS` 这三处按 186 判，与 `FLAGS` 恒置位所声称的"我是 8086"是有意的矛盾**——见下面关于"这台机器到底是哪颗芯片"的说明。

**M4 已完成的部分**：一台 IBM PC 兼容机的固件——中断向量表、宿主陷阱、中断投递，加上六个服务（10h/11h/12h/13h/16h/1Ah）和那块程序可以直接读写的文本显存。**验收标准已达成**：一个自己写的 `.COM` 通过 `INT 10h` 打出的那行字，在 FunnyOS 的屏幕上真的出现。`make test-vm` 断言的是**那行字本身**，不是退出码——退出码对一台"跑了程序但什么都没画"的机器同样成立。

**这一层是怎么被验证的，比测试数量重要。** 二十一个套件、五个模块各有自己的测试，但真正说明问题的是**交叉审查**：每个模块由一个**没有写它的人**独立审过，报出十七条发现。而作者自己的套件在其中至少四处是**全盲**的，每一处的形状相同——**断言说的和它实际检查的不是一件事**：

- **服务回不了 CF**（`INT 13h` 用它报错）。桩以真 `IRET` 收尾，IRET 从 guest 压的帧里重载 FLAGS，于是服务的 `vm86_flag_set` 到不了程序。24 个用例里 23 个直接调服务，**只有 1 个报红而 233 条断言全绿**。
- **验收自己的断言只验了一半**：`screen_present` 拿到的 guest 显存指针，拷进帧的那一半被断言、交给后端去画的那一半没有。**一个不读显存、自己拼字符串的后端能让 20 条断言全绿**——而"整屏就是 guest 内存"正是这一层的全部设计。
- **语料声称的行为从没被走到**：`cursor.asm` 说"写落在 `BH` 命名的页上，而不是恰好活动的那一页"，而它每一次调用的 `BH` 都等于当时的活动页。
- **文档在代码改过之后还说反话**，而且不止一处（`firmware.c` 的文件头同一个坑踩了两次）。

**M4 诚实地说没有证明什么：**

1. **全部期望值仍然没有对照过真实硬件。** `docs/dos-refs.md` 是查证过的**二手**来源，而其中"依据是可读源码"的那一节**曾经被升格成"这份文件里最硬的依据"、后来证明有两条是错的**——升格本身比错误条目更值得记：一句"这一节最硬"会让人跳过复核。
2. **总闸上有一条成因未知的抖动**（`make check` 曾三次红一次：三个 M4 用例一起 FAIL 而 `the process did not fault` 为真）。最后一次出现在一棵**已经不存在的树**上，之后两个改动都改变了行为，而**这台机器给不出干净的测量窗口**（无人值守升级一直在跑，另有一轮二十来分钟的全核负载压在采样窗口上）。**它记为"一次观测到的、成因未知的抖动"，不是"已修复"**；判别方法（不是成因）已经写进那条断言的失败信息。

**暴露面现在指出来了**（B 的 `M4-acceptance-flake-report.md`，只读分析，没跑任何东西）：timer 用例的**上界不是结构性的**——余量是一个 tick，约 65 ms，而同一份代码的注释里记录过调度把同一个进程吊了 370–450 ms。下界是结构性的：客人不可能在 274.6 ms 的钟走过之前数到五个 tick。所以**只有上界会在机器被吊起时假红，而客人是对的**。E 把两种失败拆成两句并**注入验证过两半**——上界调成 200 ms 报 `THE MACHINE WAS DESCHEDULED`，让 08h 数两次报 `THE COUNT IS WRONG`——上界没有被放松，一个 tick 的余量是这件事的物理量。悬空指针那条解释**已被证伪**（E 的栈投毒实验）：指针真的坏了，但在那棵树上没有任何断言读过它。
3. **键盘在 FunnyOS 里没有来源。** 内核交出的是**译好的键码**，而 BIOS 的 `INT 09h` 要的是 **set-1 扫描码**，所以"加一个非阻塞系统调用"是半个修法。`INT 16h` 只在宿主套件里活。
4. **`ES:DI` 的软盘参数表、`0xC0000–0xFFFFF` 的 ROM 洞、8259/8042 的端口**都留着——前两条是**说出来的缺口**，第三条是真实的兼容缺口。
5. **一条已知的残余**：验收分不开"读了 guest 显存"和"把整屏硬编码"。结构性答案是让 guest 写一个宿主不可能当字面量知道的值（自己代码的校验和、或读到的滴答数），那是换一条设计，不是补一条断言。

**M5 已完成的部分（W1：进程模型）。** `process_run()` 现在可重入：当前进程、当前 PML4、TSS 的内核栈指针、向量寄存器四样在进入时保存、离开时还原。新增 `SYS_SPAWN`（阻塞式，因为 DOS 的 `INT 21h AH=4Bh` 就是阻塞的：程序启动另一个程序，拿回它的退出码）。

**这一版的验收是一条可观测的不变量，不是一句声明。** 内核在每次**从 Ring 3 进来的**定时器中断上，检查那个帧是不是落在**当前进程**的内核栈里，并在退出时报告三种结果之一——全对、有落错、或者**一个都没观测到**。第三种单独成一种结果是刻意的：什么都没观测到会满足"没有落错"，而把这种情况报成成功，正是一个测试什么也没证明的写法。

**它挡的错法**：嵌套运行结束时没有把 `rsp0` 还回去，于是父进程的下一次中断把帧压进**已经释放的子进程内核栈**——静默，直到分配器把那块内存给了别人。注入验证过：把那行还原拿掉，报 `FAIL (6 of 17 Ring 3 ticks landed off the running program's kernel stack)`。7 条新断言，`make check` 全绿。

**顺带查出来的一件事。** FPU 那条自检一直被描述成"守护 `-mgeneral-regs-only` 的那条测试"，而它**做不到**：它的循环每一轮都问一次时钟，所以落在循环期间的中断全都进在系统调用里——内核在自己的栈上，程序不在背后。量出来的数字是 33 次滴答、**Ring 3 里 0 次**。代码自己的注释早就写明了这一点并指向静态检查（`tools/check-no-vector-regs.sh` 反汇编产物），是**测试脚本的注释**在过度声称，已按实情改写。这条能查出来，靠的正是上面那把尺子——它是这一版的第一个副产品。

**M5 已完成的部分（W2：程序看得见）。** 屏幕现在是一个**可以被持有的东西**（`kernel/console/screen.c`）。内核默认持有它；一个程序可以通过 `SYS_SCREEN_ACQUIRE` / `SYS_SCREEN_PRESENT` / `SYS_SCREEN_RELEASE` 借走它，把它自己的文本页画上去——**是 VM 进程自己画的，不是测试夹具里的断言**，这是 M5 验收句子里"并且看得见"那半句。日志在被持有期间照常往自己的网格里写，只是不画；还回来时整屏重画，因此 log 是完整的。`panic()` 第一件事就是抢回屏幕。

**计划的形状和落地的形状有一处不同。** 计划说"VM 是独占屏幕，还是借用一块再还回来；倾向后者（内核的 panic 输出必须随时能抢回屏幕）"。落地的是后者的一个版本：**屏幕只有一个持有者**，而不是"在一块共享屏幕上留一个内嵌区域"。理由是日志是一整块会滚动的网格，而**留一个洞不让它滚，等于同时维护两种网格**。整块借出把问题从"画在哪"变成了"谁来画"，而后者有一个干净的答案。

**页是直接从调用者的内存画的，没有拷贝。** 传的就是 guest 页在 guest 内存里的那个指针，属性的渲染也在 W2 落进了 `fb.c`（一套 16 色的 IBM PC 文本调色板，**该表来自通用知识、仓库里没有可对照的文档**——`fb.c` 在表旁边这么写着）。这让"屏幕是 guest 内存的相片"成为两行代码的性质，而不是一条可以对着自己的副本断言的话。

**但它有一个前提，而且这个前提写下来了**：页还在调用者的内存里。可以切走再切回来的页会把它打破——那时内核必须持有自己的副本，而那句话就要跟着改。**这条记在 [M4-G](tasks/M4-G-mouse-tabs.md) 的 G3 里**，因为那是它第一次成立的地方。

**验收长出了这一版唯一能看见屏幕的工具：`tools/run-screen-test.sh`。** 串口日志能说的每一句话——guest 的页对、内核收到了、内核说它画在哪——**都和一个从没被写过的 framebuffer 相容**。所以这条路是：让程序把页留在屏幕上等一个按键（`vm=screen`），用 QEMU monitor 截屏，再由 `tools/check-screen-pixels.py` **逐扫描线**比对每一个格子是不是字体里那个字的形状。

那个检查器刻意**不假设调色板**：背景色取自一个已知是空白的格子，前景色取块里另一种颜色，两个颜色都是从**屏幕上读出来的**（实测得到 `000000` / `aaaaaa`，正是属性 `0x07` 该有的样子）。代价写在脚本的文件头：**调色板本身不被检查**，而且**字体是内核自己那张**——一个错的字体表会让预测和渲染一起错，比对看不出来。

**它挡的错法，五个，注入验证过，诊断各不相同**：字右移一格（`outside the guest's page are not the console's background colour`）、丢掉属性字节用控制台自己的颜色（`drawn in the console's own background colour`）、什么都没画（`the whole page is one colour`）、页根本没交给内核（`NOTHING WAS PRESENTED`）、**每个字左移一个像素且留在格子里**（`cell 0,0 scan line 3 is not the font's glyph for 'M'`）。

最后一条单独注入过一次，因为前四种都被**别的**检查先拦住了——移出矩形、把空格画出了墨。**只有形状比对能看见"位置对、栅格对、形状不对"**，所以"逐扫描线比对"这句话要靠它才有证据。

**W2 没有做它计划里的键盘那一半，是故意的。** `INT 16h AH=01h`（"有键吗"）要一条非阻塞的读键调用，加它是十行——但 guest 在 W6 之前根本没有键盘来源，于是它**没有调用方、也测不了**。一条加了却没人用的接口，是"套件绿在一个从没被测过的实现上"的另一种写法。**它移到 W6**，和真实的 set-1 扫描码一起验。

### M4 中几处值得记下的决定

完整的清单在 `docs/tasks/M4-README.md` 第三节，那里每一条都附了理由。这里只记**改动了这份设计文档的地方**——也就是后来读 DESIGN 的人会以为和代码不符的那几条。

**陷阱是一个字节对，不是一条指令。** guest 要够到宿主，走的是**中断向量表**（8086 没有 `syscall`）。所以固件给 256 个向量各装一个四字节的桩 `FE 38 <向量> CF`，桩里的 `FE 38` 是一个**汇编器产不出来**的编码（`FE` 组只有 `/0` 和 `/1` 有定义），宿主陷阱就是它。桩用**自己的 IRET** 收尾——栈上的帧是 guest 的 `INT` 压的，只有 guest 自己的 IRET 知道怎么弹开它。TSR 链接因此**不需要任何代码**：一个 `jmp far` 跳回旧向量就落回桩上了。

**异常按"这个向量有没有被改写过"决定投不投递。** 向量还是我们的桩（程序没为它装处理程序）→ 停下并报告，这就是 M3 的行为；向量被改过 → 投递给程序。DOS 的默认处理程序也是"终止程序"，所以这一条和真机一致，而且它是 D6 那套检测的**比较实现**（见 D6 下的注）。

**`HLT` 是等待，不是结束。** 有挂起中断且 IF=1 就唤醒并投递；否则运行循环返回，交给宿主。`cli; hlt` 才是终结——IF=0 的 HLT 在真机上不会被可屏蔽中断唤醒。验收程序靠这一点结束。

**`REP` 可中断、`STI` 延迟一条、写 `SS` 抑制一条**，三条 M3 欠账在这一轮还掉。前两条共用一个"影子"计数；第三条是串操作循环里的**迭代间检查 + IP 回卷到第一个前缀之前**——回卷到操作码之后会**静默地**把 `rep movsb` 变成 `movsb`，机器看起来还在正常工作。

**阻塞的 BIOS 调用靠"把这条指令重来一次"实现**（`vm86_service_retry`）。`INT 16h` 读不到键时不能在服务里自旋——服务不返回，宿主就永远拿不回控制权，键也就永远进不来。所以那条指令被重放：**IP 退回它自己的起点，别的什么都不动**。guest 于是真的在"开着中断等"，而宿主在两次尝试之间拿到控制权、喂键、拉起 `INT 09h`，下一次尝试就读到了。

**这里有一处曾经想错、值得记下来。** 最初的写法是"顺便把 `INT` 压的那个帧也弹掉，让重试看起来像那条 `INT` 从没跑过"。**那是错的，而且错两次**：帧里存的是 `INT` **之后**的地址，弹掉它等于**跳过**那条读键指令而不是重跑它；而且"替别人弹帧"对经由 `INT` 到达的桩是对的、对经由 `TSR` 链式 `jmp far` 到达的桩是错的——重试就得先知道自己是哪一种。**什么都不弹就没这个问题**：帧留在 `INT` 放它的地方，桩那条 `IRET` 在服务最终成功时把它弹掉一次，无论桩是怎么被到达的。

**第二个决定是机器自述的边界。** `INT 11h`/`12h`（设备字、内存大小）由固件提供，因为那两个字节描述的是**机器**、没有哪个设备在背后维护它；而模式字、光标、滴答计数、键盘队列各归它们的服务。`firmware.h` 里"谁的服务谁写"这条规矩，这两个字段是唯一的例外，例外本身也写在代码里。

**`INT 20h` / `INT 21h/4Ch` 的程序终止不在 M4。** 它要 DOS 服务先存在（M5）。因此 M4 的 `vm86_service_fn` 返回 `void`——**没有任何东西需要"结束程序"**。等 M5 需要它时 `enum vm86_result` 会多一个枚举值，而 `-Wswitch` 会把每一个必须做决定的消费方列出来：那个枚举当初就是为此设计的。

### M2 中几个值得记下的决定

**地址空间的划分是推导出来的，不是选出来的。** HHDM 位于 `0xffff800000000000`，即 PML4 的第 256 项；内核映像位于 `0xffffffff80000000`，即第 511 项；而用户程序能命名的一切——整个低半区——正好是第 0 到 255 项。于是进程地址空间就是一个私有 PML4：256..511 直接复制内核的（共享而非拷贝，这样切 CR3 之后内核仍然映射着，中断才落得进来），0..255 归进程自己。这个划分不需要协商，它是地址布局的直接推论。

**进程的结束走的是 longjmp，不是函数返回。** 退出系统的调用发生在中断处理程序内部，而中断处理程序离开上下文的唯一途径是入口桩底部的 `iretq`——可进程已经死了，不能 iretq 回去。所以 `SYS_EXIT` 只记录意图并正常返回，中断分发在**发完 EOI 之后**调用一个后置钩子，由它切回内核页表并 longjmp 回 `process_run`。EOI 必须在前，否则一个被转走的 CPU 会让这个中断永远留在服务中。

**用户态指针在读之前就被检查，而不是读崩了再补救。** 内核在触碰任何程序传来的地址前，先走一遍那个进程的页表，确认整个区间都映射且每一级都有用户权限。这在本项目里是充分的，因为没有任何东西能在背后改动一个进程的映射——没有写时复制、没有交换、没有第二个线程。将来只要加上其中任何一个，这个方案就不成立了，必须改成"出错再恢复"的故障修复路径。代码里是这么写的，因为不写清楚的话，后来加写时复制的人不会知道。

### 浮点：一个刻意的不对称（M2 与 M3 之间补上）

**中断不保存 FPU/SSE 状态。** CPU 在中断时只压入通用寄存器和返回帧，XMM 和 x87 栈一概不管。这是有意的设计——为了让"用不到向量寄存器的操作系统"可以完全跳过这件事。

于是就有了这个不对称，它是整个浮点方案的全部内容：

- **内核绝不触碰向量寄存器**，由 `-mgeneral-regs-only` 强制。因此中断处理不需要保存任何浮点状态，中断入口的开销就是压 15 个通用寄存器。
- **用户程序可以自由使用浮点**。进程状态在控制权易手时用 FXSAVE/FXRSTOR 保存恢复；中断期间不需要保存，因为内核根本不碰那些寄存器。

代价是失败**无声**：一旦有人从内核 CFLAGS 里删掉 `-mgeneral-regs-only`，每次中断都会开始破坏被打断程序的数据——不报错，只是过一会儿某个结果变错，而且只在恰好被打断时才错。这种 bug 没人靠阅读能发现。

所以它是**机械校验**的：`tools/check-no-vector-regs.sh` 反汇编链接后的内核**产物**，出现任何一个向量寄存器就让构建失败。跑在产物而不是源码上是有意的——源码可能完全无辜，编译器却有权把某个循环向量化。

**AVX 被显式关闭。** FXSAVE 的 512 字节镜像不包含 YMM，所以 `CR4.OSXSAVE` 保持清零，AVX 指令会触发 `#UD`。响亮地失败胜过安静地只保存一半状态。真需要 AVX 的时候要换的是整个状态镜像——XSAVE 区域的大小由 CPUID 决定，得按 CPU 查询后动态分配。

**每个进程有自己的 512 字节状态区**，在 `process_create` 里分配、并初始化为架构默认值（x87 复位、异常全屏蔽、就近舍入）。目前同时只有一个进程，所以保存和恢复实际上是把同样的值原样放回去；但它现在就位，因为替代方案是等调度器落地那天，两个程序的寄存器被静默交错——而那种 bug 在暴露之前一直看不见。

**为什么这件事排在 M3 之前**：M3 的 8087 模拟打算借用宿主的 SSE 来执行 guest 的浮点指令，而解释器会是一个用户态进程。没有这一步，它一行都写不了。

**关于中断控制器地址**：LAPIC 与 I/O APIC 的地址来自固件而非常量（见 §6 的说明），因此内核解析 ACPI MADT，而不是硬编码 0xFEE00000 / 0xFEC00000。两者恰好几乎总是这两个地址，这正是「猜」能一直奏效、直到碰上某台机器为止的原因。

**总计到 M6（一个能跑真实 DOS 工具的完整系统）：约 5–8 个月的全职投入**，或按业余时间折算 1.5–2 年。

## 7. 范围：不做的，和以后做的

写下来是为了防止范围蔓延。但有两件事必须分开，因为它们对**现在**的含义完全相反：

- **不做** —— 设计上不打算做。现在的接口不需要为它留任何位置。
- **以后做** —— 目标里有，只是排在基础完成之后。**这一类会反过来约束现在**：如果今天的接口把门关死了，将来就不是"多做一点"，是推倒重来。

把这两类混成一句"不在范围内"，代价是**在还便宜的时候把门关上**，而关门这件事当时不会有任何症状。

### 7.1 不做

- **硬件虚拟化**（D1 已论证：复杂度高一个数量级，对 CPU 世代有要求，调试困难，而它要解决的那个问题——跑 16 位实模式程序——软件解释器已经解决了）。

### 7.2 以后做，所以现在的接口要留门

下面五条**是目标的一部分**，只是排序在核心里程碑之后。每一条都写了"它需要今天的什么"——那才是这一节的实际作用。

| 特性 | 为什么排在后面 | 现在必须不为它关上的地方 |
|---|---|---|
| **多核 SMP** | 单核就能跑 DOS 程序，而 SMP 会把内核里每一处"全局单例"都变成 bug。先用单核把语义做对 | 中断与定时器路径，以及**每 CPU 状态**。`g_current` 那种"一个全局变量就是当前进程"的形状，不是为了 SMP 才要改——它会以同样的方式挡住 M4 之后的进程模型，**而它已经挡过一次了**：M5 的 W1 就是为它做的 |
| **抢占式多任务** | DOS 程序本身是单任务的；需要多任务的是**宿主**的进程模型 | 调度点与可重入性。`process_run()` 原本不可重入（`g_current`、当前 PML4、TSS 的内核栈指针、向量寄存器四样都在离开时被抹掉而不是还回去），这是 M4 之后的第一件事，**M5 的 W1 已经做掉**——见上面"M5 已完成的部分（W1：进程模型）"。**但门只关了一半**：§7.2 那一栏说的是"现在的接口要留门"，而门开在进程模型上，不在调度器上——可重入不是多任务 |
| **图形用户界面** | 命令行是设计的一部分，不是过渡状态。但 GUI 需要图形模式先存在 | 显示抽象。现在只有文本网格（D7 的 S1/S2），S3/S4 已在路线里（M7）。**GUI 会建在同一个抽象上，所以那一层不能是"文本专用"的** |
| **Windows / Linux 二进制兼容** | 需要另一整套加载器与系统调用层，而且要先有一个稳定的进程模型 | 系统调用边界必须是**通用的**，不能围绕 DOS 硬编码。今天的 `int 0x80` 只是雏形，但它要经得起第二种 ABI |
| **网络** | 初期完全不碰；没有设备要驱动 | 设备框架。内核已有设备抽象，新设备按同一套接进来即可 |

**这一节和 §6 的路线图是一件事的两面**：路线图说什么时候做，这一节说为什么现在不能把门关上。

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| **兼容性长尾** | 高 | 自举程序总有边界情况，永远"还差一个功能"。缓解：**M5 之后立即引入真实程序测试**，用 MS-DOS 4.0 编译产物当回归测试集，而不是等到最后 |
| **自举依赖** | 高 | 没有好用的 Shell 和文件系统，调试 DOS 程序会极其痛苦。缓解：**M2 必须做扎实**，调试工具（单步追踪、内存查看）要在 M3 就位 |
| **范围蔓延** | 高 | OS + 模拟器本质上是两个大项目。缓解：严格执行里程碑，M2 完成前不碰 DOS 层一行代码 |
| **解释器性能低于预期** | 中 | 若实测达不到等效 50 MHz，先做译码缓存（§3.3 第 2 步），这通常能带来 2–3 倍提升 |
| **图形/声音外设模拟** | 中 | 跑游戏需要大量外设。缓解：**接受"应用优先于游戏"**，M7 之前不考虑 |
| **浮点与保护模式** | 低 | 属后期需求，不阻塞主线 |
| **引导器绑定** | 低 | Limine 是引导层，通过协议接口隔离，可替换 |

## 9. 与 DOS 的关系：继承什么，抛弃什么

| DOS 的特质 | FunnyOS | 理由 |
|---|---|---|
| 极小的内核与直白的分层 | ✅ 继承 | 可理解性胜过一切 |
| 命令行作为一等交互界面 | ✅ 继承 | 不是过渡状态，是设计选择 |
| 程序对机器有充分控制权 | ✅ 部分继承 | guest 程序在 VM 内获得完整的"裸机"体验 |
| 简单的整数/段式内存观 | ✅ 继承（在 VM 内） | 这是 DOS 程序运行的语义环境 |
| 无内存保护 | ❌ 抛弃 | MMU 的隔离几乎是免费的，没有理由放弃 |
| 程序崩溃即整机崩溃 | ❌ 抛弃 | DOS 程序的崩溃只杀死 VM 进程 |
| 1 MB 地址空间天花板 | ❌ 抛弃 | 宿主侧没有这个限制，guest 侧通过 XMS/EMS 扩展 |
| 单任务作为架构限制 | ❌ 抛弃 | 宿主是多任务的；VM 内仍是单任务，符合 DOS 语义 |
| 驱动直接编译进内核 | ❌ 抛弃 | 采用统一的设备框架 |

## 10. 下一步

设计已定，建议的执行顺序：

1. **搭建 WSL2 工具链**（`build-essential`、`nasm`、`qemu-system-x86`、`xorriso`、`mtools`）
2. **M0：跑通 Limine + 最小内核**，在 QEMU 里看到串口输出
3. **M1：内核基础设施**，目标是能干净地报告异常而不是三重故障
4. **M2：控制台与 Shell** —— 你选定的首期验收点

M0 是整个项目里唯一一个"一天之内能看到结果"的阶段，也是验证工具链和引导路径是否真的可用的一次现实检验。建议先把它做完再做任何长期承诺。
