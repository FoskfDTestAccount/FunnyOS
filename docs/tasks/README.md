# M3 任务书:8086 解释器

这份目录里的每一份文件都是一个**独立任务**，交给一个独立的执行者（人或 AI）。这份 README 是总纲：开始之前先读完，然后只看你自己那一份。

---

## 一、这个项目在做什么

FunnyOS 是一个原生 x86-64 操作系统，核心使命是**运行 16 位 DOS 程序**。因为 x64 长模式没有 virtual 8086 模式（硬件层面不存在），所以必须写一个**纯软件的 8086 解释器**。

M0（引导）、M1（内核基础设施）、M2（控制台与 Shell）已经完成并通过验证。**M3 是这个项目的核心**：让一个 8086 解释器能正确执行手工汇编的二进制，寄存器和标志位状态正确。

M3 之后是 M4（BIOS 中断）、M5（DOS 服务与 COM 加载器）——那时才能跑起真实的 DOS 程序，包括用 `microsoft/MS-DOS` 源码编译出来的 `EDEBUG.COM`、`EDLIN.COM` 这些。

## 三、硬性规则

### 1. 只改你自己的两个文件

你**只能**修改：

- 你负责的 `dos/cpu/ops_XXX.c`
- 你的 `dos/tests/test_XXX.c`

**不要碰**任何头文件、`decode.c`、`step.c`、`flags.c`、`mem.c`、`harness.*`、`Makefile`，以及**别人的** `ops_*.c`。

这不是形式主义。五个人同时改同一个头文件，产出的是五套互不兼容的抽象。接口是先冻住再分工的，顺序不能反过来。

### 2. 需要接口里没有的东西时——停下来报告

如果你发现 `decode.h` 或 `ops.h` 缺了某个你需要的函数，**不要自己加**。在报告里写清楚：你需要什么、为什么现有的不够、你打算怎么绕过。

加一个函数会让其他四个人的代码全部要重新编译验证，所以这件事必须由冻结接口的人统一做。

### 3. 不要重新实现共享 helper

`vm86_alu()`、`vm86_alu_incdec()`、`vm86_push16()`、`vm86_pop16()`、`vm86_flags_result()`、`vm86_flags_logic()`、`vm86_parity()` 已经写好并且被多方调用。**直接用。**

自己写第二份的后果不是"多了一点代码"，是两份实现**必然会在某个边界情况下不一致**，而那个边界情况会在 M5 跑真实 DOS 程序时出现。

### 4. 每个认领的操作码都要有测试

没有测试的操作码等于没写完。测试写在你自己的 `dos/tests/test_XXX.c` 里。

### 5. 编译必须零警告

`dos/Makefile` 开了 `-Werror`。这是故意的：这个目录是新的，没有历史包袱，所以没有理由放过第一个警告。

## 四、怎么构建和测试

**测试跑在宿主上，不跑 QEMU。** 解释器是纯逻辑，给它一块内存和一些字节它就能执行——所以不需要虚拟机、不需要启动、毫秒级出结果。

```bash
cd dos
make list        # 看有哪些测试套件
make test        # 跑全部
make test-alu    # 只跑你自己的
```

第一次跑 `make test` 会看到 `smoke` 套件（8 个用例，全绿）。那是骨架的自检。

**测试的写法**在 `dos/tests/harness.h` 开头，写得很详细，照着写。核心是：

```c
static void test_add_al_imm8(struct vm86_cpu *cpu)
{
    static const uint8_t code[] = { 0x04, 0x05, 0xF4 };  /* add al,5; hlt */

    vm86_test_load(cpu, code, sizeof(code));
    cpu->ax = 0x0010;
    vm86_test_run(cpu, 10);

    vm86_expect_u16("AL", cpu->al, 0x15);
    vm86_expect_flag("CF", cpu, VM86_CF, false);
}
```

### 两个必须知道的约定

**每个测试的代码末尾必须有 `HLT`（0xF4）。** 8086 上没有"程序结束"这回事——IP 走过头就继续取指，而 guest 内存是清零的，于是一串 `00` 字节会被解码成 `add [bx+si], al`，改掉标志位、写地址 0。测试于是测的是残留物而不是自己的指令，而且**它是否通过取决于被测指令恰好留下了什么**。

**断言要断标志位，不只断结果。** 一个算对了值但进位标志错了的指令是错的，而只检查值的测试抓不住它——程序会在很久以后的某个分支上走错，那时 bug 会被算到别的东西头上。

## 六、权威参考

行为以**《Intel 8086 Family User's Manual》**（1979，文档号 9800722）为准，尤其是：

- 第 2 章：指令编码与 ModRM 的完整表格
- 第 3 章：每条指令的**标志位影响表**——这张表是测试的依据
- 附录 A：操作码图

**不要凭记忆写标志位。** 8086 的辅助进位、溢出、以及"哪些标志位未定义"，是这份文档里最容易记错的部分，而记错的后果是静默的。

拿不准的时候，可以对照 `reference-msdos/` 里的 MS-DOS 源码——那是真实程序如何用这些指令的第一手材料。

**还有一类错误比记错标志位更隐蔽：弄错"这是哪颗芯片的行为"。** 这份任务书的第一版就犯过一次——把 `8E` 描述成"延迟加载，下一条指令读到旧值"。8086 上不是这样：段寄存器**立即**拿到新值，被延迟的是一整条指令的中断识别。错的后果不只是文档难看：一份写着"手册明确说了某某"的任务书，会让执行者去**实现**一个真实硬件上没有的行为。

容易踩的同类地方，答案取决于**芯片**，不取决于"哪个更合理"：

| 问题 | 8086 | 186 及以后 |
|---|---|---|
| `PUSH SP` 压进去的值 | **减之后**的 SP | **减之前**的 SP |
| `shl ax, cl`，CL = 20 | 真的移 **20** 次 | 截断到 **5** 位，即移 4 次 |
| `MOV CS, ...`（`8E` `/1`） | 硅片执行（手册不承诺） | 非法 | **本机：非法（异常 6）**——有意偏离，见下 |

**拿不准就查 8086 那一列。** 这台机器声称的是 8086；186 的扩展是显式加上去的（任务 E），不是默认。表里每一行都至少有一份任务书要按它做决定。

### 这台机器**到底**是哪颗芯片

上面那句"查 8086 那一列"留下了一个没说清的问题：186 的扩展是加上去的，那么当两者**在同一位上不一致**时听谁的？这里把它补完。

**规则：操作码图的形状按 186 判，已文档化的指令语义按 8086 判。**

- **操作码图的形状**（哪几个字节归谁）——按 **186**，而且这是硬性的：
  - `60`–`6F` 在 8086 上是 `70`–`7F` 条件跳转的**未公开别名**。而 DESIGN 的 P1 要求 `PUSHA`/`POPA`/`ENTER`/`LEAVE`/`BOUND` 必须做，它们**占的就是这几个字节**。两者不可能共存，186 必须赢。
  - `0F` 在 8086 上是 `POP CS`，186 起改作**两字节转义**。DESIGN 的 P2（286 保护模式指令）在第二张图上，所以它作为转义**预留着**。
- **已文档化的指令语义**（它们怎么算）——按 **8086**。`PUSH SP` 压的是减之前还是减之后、`shl ax, cl` 在 CL=20 时截不截断，都按 8086 那一列。

**`MOV CS` 是有意的偏离。** 8086 的硅片会执行它（手册不承诺），本机让它报异常 6，也就是 186 那一列。理由是那条"执行"在 8086 上表现为**一次跳转**，是一个危险且几乎无人使用的行为，而去模仿它没有对应收益。**这条偏离写在这里，是因为表里原来只有两列，没有"本机怎么选"这一列。**

### `FLAGS` 的 `0xF002` 是一句有意的夸大，而且它有代价

`cpu.h` 让 bit 1 和 bit 12–15 恒读为 1。这正是当年程序**辨认 8086** 的手法。所以 `FLAGS` 在告诉 guest"我是 8086"。

可是按上面的规则，这台机器在**操作码图**上是 186。于是：一个程序据此判定"这是 8086"，然后去用 `0F`（期望 `POP CS`）或 `60`–`6F`（期望条件跳转别名），**拿到的是 186 的答案**。

**这个矛盾是设计选择，不是疏忽。** 之所以写下来，是因为它是这套规则唯一的代价，而一个没被写下来的矛盾，下一个人会把它当成 bug 去"修"，然后把兼容性弄坏。

### "手册没写"不等于"硅片不做"

这一条是**由一次真实的错误换来的**：`0F` 的注释曾经写着"POP CS 从不存在，8086 把这个编码空着"。**它是错的。** 8086/8088 在 `0F` 上执行的就是 `POP CS`，是 80186 把它挪作转义。同类还有 `D6`（SALC，8086 硅片上存在，只是没公开）和 `F1`（8086 上按 `LOCK` 动作）。

所以：**凡是拿"未定义""不存在"当理由的注释，都要改成真实理由**——"硅片会这么做，我们选择不做"。不实现可以是正确的决定；**用一个假的理由去支持它不行**。带理由的错误比没理由的错更难发现，因为理由读起来完整，读者就不去查了。

这条同时解释了为什么上面那张表第三列现在叫"**本机**"。

### 两个协调点

**一、任务 C 和 E 共用 REP 循环。**

串操作(`A4`-`AF`)和 `INS`/`OUTS`(`6C`-`6F`)是同一套重复语义,**必须只有一份实现**——两份不一致就会出现"MOVSB 能正确重复而 INSB 不能"这种 bug。

分工:

- **E 的 `INS`/`OUTS`(`6C`-`6F`)用 C 交付的循环。** 已完成:C 把 REP 循环写成了 `vm86_str_repeat()`(回调式,循环体由调用方传入),已经加进 `ops.h` 的"字符串循环"一节。E 直接调用,**不要写第二份**。
- **E 的另外八个操作码**(`60`-`62`、`68`-`6B`、`C8`/`C9`)和 REP 无关,照原样写。

E 现在**没有前置依赖**了。

**二、`STI` 和 `8E` 的"延迟"都不需要接口变更——查过了。**

两份任务书的第一版都写着"这需要往 `struct vm86_cpu` 加字段"。**那是错的,已经改掉。** 两者的理由相同:被延迟的东西是**中断识别**,而 M3 没有中断投递,所以这两个特性在 M3 里**完全观察不到**。加一个没人读的字段不是"提前建模",是无法验证的死状态——而 M4 写消费者的时候,会发现当初那个字段的语义是猜的。

**顺带纠正一处事实错误。** 任务 B 的第一版把 `8E` 写成"段寄存器延迟更新,下一条指令读到旧值"。**8086 上不是这样**:段寄存器**立即**拿到新值,被延迟的是中断识别,而且据 errata 这个抑制作用在**所有** `mov segreg` / `pop segreg` 上,不只是 SS。

两处都改掉了,因为错的后果不只是文档难看:一份写着"手册明确说了某某"的任务书,会让执行者去**实现**一个真实硬件上没有的行为。**任务书里的错误事实会变成代码里的 bug。**

### 没有任何任务认领的操作码

下面这些字节**故意**不属于任何一份任务。列在这里是因为"没人管"和"不需要管"是两回事,而只有写下来才能区分:

| 字节 | 是什么 | 为什么不管 |
|---|---|---|
| `26` `2E` `36` `3E` | 段超越前缀 | 由 `step.c` 的取指循环消费,**永远不会到达分发表** |
| `F0` | LOCK 前缀 | 同上;而且单处理器上没有需要加锁的地方 |
| `F2` `F3` | REPNE / REP 前缀 | 同上,通过 `cpu->prefix.repeat` 交给串操作 |
| `63` | ARPL | **80286** 指令,不是 8086/186 的。我们的目标是 8086 |
| `64` | 8086 上是 `74`(`JZ`)的未公开别名 | 同下:整行随 186 一起被拿走。**而且它原来整条从这张表里漏掉了** |
| `65` `66` `67` | 8086 上是 `75`/`76`/`77` 的未公开别名 | 不实现**是对的**,但理由不是"未定义"——见第六节 |
| `D6` | SALC | **8086 硅片上存在**,只是没公开。不实现是我们的选择,不是"它不存在" |
| `F1` | 8086 上按 `LOCK` 动作 | 同上:不实现是选择,不是"它未定义" |
| `D8`-`DF` | ESC / 8087 | M7 |

**`64` 原来整条从这张表里漏掉了,而它漏的方式值得记一笔。** 这个字节没被认领、也没人认领,但 `tools/check-opcode-coverage.py` **不报** —— 因为脚本是去任务书里搜十六进制字符串,而 `64` 作为数字出现在"64 KiB 段边界""x86-64"这些完全无关的地方。**一个烟雾报警器的固有盲区:当被搜的记号同时是一个常见数字时,搜到的是噪声,而真信号被噪声盖住。** 后果是这张表掉一条,脚本照样绿。

这也是为什么这张表要**人**来维护、而不是让脚本生成:脚本能告诉你"这个字节从没被提到",但它没法告诉你"这个字节被提到过,只是提的不是它"。

**一张覆盖检查表**:`tools/check-opcode-coverage.py` 会扫这些任务书里出现过的十六进制字节,报出**没有任何文档提到过**的那些。它是个烟雾报警器不是证明——文档里有很多十六进制不是操作码(中断向量号、字节数、示例里的寄存器值),所以"被提到"不证明什么。

但**"从没被提到"是明确的信号**。8086 的操作码图是不规则的:做不同事的段并不连续,把 256 个槽位分给五个人、留下一两个谁也没注意到的洞,是很容易发生的事。**这份任务书的第一版就漏了 `8D`(LEA)和 `C4`/`C5`(LES/LDS)**,是跑这个脚本才发现的。

所以:把它的输出当成一份"去看看这些"的清单。
