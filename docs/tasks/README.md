# M3 任务书:8086 解释器

这份目录里的每一份文件都是一个**独立任务**，交给一个独立的执行者（人或 AI）。这份 README 是总纲：开始之前先读完，然后只看你自己那一份。

---

## 一、这个项目在做什么

FunnyOS 是一个原生 x86-64 操作系统，核心使命是**运行 16 位 DOS 程序**。因为 x64 长模式没有 virtual 8086 模式（硬件层面不存在），所以必须写一个**纯软件的 8086 解释器**。

M0（引导）、M1（内核基础设施）、M2（控制台与 Shell）已经完成并通过验证。**M3 是这个项目的核心**：让一个 8086 解释器能正确执行手工汇编的二进制，寄存器和标志位状态正确。

M3 之后是 M4（BIOS 中断）、M5（DOS 服务与 COM 加载器）——那时才能跑起真实的 DOS 程序，包括用 `microsoft/MS-DOS` 源码编译出来的 `EDEBUG.COM`、`EDLIN.COM` 这些。

## 三、硬性规则

### 1. 只改你自己的两个文件

你**只能**修改：

- 你负责的 `dos/cpu/ops_XXX.c`
- 你的 `dos/tests/test_XXX.c`

**不要碰**任何头文件、`decode.c`、`step.c`、`flags.c`、`mem.c`、`harness.*`、`Makefile`，以及**别人的** `ops_*.c`。

这不是形式主义。五个人同时改同一个头文件，产出的是五套互不兼容的抽象。接口是先冻住再分工的，顺序不能反过来。

### 2. 需要接口里没有的东西时——停下来报告

如果你发现 `decode.h` 或 `ops.h` 缺了某个你需要的函数，**不要自己加**。在报告里写清楚：你需要什么、为什么现有的不够、你打算怎么绕过。

加一个函数会让其他四个人的代码全部要重新编译验证，所以这件事必须由冻结接口的人统一做。

### 3. 不要重新实现共享 helper

`vm86_alu()`、`vm86_alu_incdec()`、`vm86_push16()`、`vm86_pop16()`、`vm86_flags_result()`、`vm86_flags_logic()`、`vm86_parity()` 已经写好并且被多方调用。**直接用。**

自己写第二份的后果不是"多了一点代码"，是两份实现**必然会在某个边界情况下不一致**，而那个边界情况会在 M5 跑真实 DOS 程序时出现。

### 4. 每个认领的操作码都要有测试

没有测试的操作码等于没写完。测试写在你自己的 `dos/tests/test_XXX.c` 里。

### 5. 编译必须零警告

`dos/Makefile` 开了 `-Werror`。这是故意的：这个目录是新的，没有历史包袱，所以没有理由放过第一个警告。

## 四、怎么构建和测试

**测试跑在宿主上，不跑 QEMU。** 解释器是纯逻辑，给它一块内存和一些字节它就能执行——所以不需要虚拟机、不需要启动、毫秒级出结果。

```bash
cd dos
make list        # 看有哪些测试套件
make test        # 跑全部
make test-alu    # 只跑你自己的
```

第一次跑 `make test` 会看到 `smoke` 套件（8 个用例，全绿）。那是骨架的自检。

**测试的写法**在 `dos/tests/harness.h` 开头，写得很详细，照着写。核心是：

```c
static void test_add_al_imm8(struct vm86_cpu *cpu)
{
    static const uint8_t code[] = { 0x04, 0x05, 0xF4 };  /* add al,5; hlt */

    vm86_test_load(cpu, code, sizeof(code));
    cpu->ax = 0x0010;
    vm86_test_run(cpu, 10);

    vm86_expect_u16("AL", cpu->al, 0x15);
    vm86_expect_flag("CF", cpu, VM86_CF, false);
}
```

### 两个必须知道的约定

**每个测试的代码末尾必须有 `HLT`（0xF4）。** 8086 上没有"程序结束"这回事——IP 走过头就继续取指，而 guest 内存是清零的，于是一串 `00` 字节会被解码成 `add [bx+si], al`，改掉标志位、写地址 0。测试于是测的是残留物而不是自己的指令，而且**它是否通过取决于被测指令恰好留下了什么**。

**断言要断标志位，不只断结果。** 一个算对了值但进位标志错了的指令是错的，而只检查值的测试抓不住它——程序会在很久以后的某个分支上走错，那时 bug 会被算到别的东西头上。

1. `cd dos && make test` 全绿,零警告
2. 你清单上的每个操作码都有测试,覆盖**正常值、边界值和标志位**

## 六、权威参考

行为以**《Intel 8086 Family User's Manual》**（1979，文档号 9800722）为准，尤其是：

- 第 2 章：指令编码与 ModRM 的完整表格
- 第 3 章：每条指令的**标志位影响表**——这张表是测试的依据
- 附录 A：操作码图

**不要凭记忆写标志位。** 8086 的辅助进位、溢出、以及"哪些标志位未定义"，是这份文档里最容易记错的部分，而记错的后果是静默的。

拿不准的时候，可以对照 `reference-msdos/` 里的 MS-DOS 源码——那是真实程序如何用这些指令的第一手材料。

| 任务 | 文件 | 操作码数 | 难度 | 说明 |
|---|---|---|---|---|
| **A** | `M3-A-alu.md` | 约 60 | 中 | 算术逻辑的核心,含乘除与移位 |
| **B** | `M3-B-mov.md` | 约 45 | 低 | 数据传送,量大但直白 |

| **D** | `M3-D-ctl.md` | 约 55 | 中高 | 控制流、中断、标志、I/O |
| **E** | `M3-E-186.md` | 12 | 中 | 186 扩展,含几个真正微妙的 |
| **F** | `M3-F-verify.md` | — | — | **独立验证,在 A–E 之后** |

**任务 C 和 D 的难度不在操作码数量上**,在它们各自的语义细节(REP 的终止条件、段超越对隐含段访问是否生效、近跳转的位移相对于哪个 IP)。这两份写得最长,值得先读。

**任务 A–E 可以完全并行**:五个人改五个文件,互不重叠,接口已经冻住。

**任务 F 必须在 A–E 之后**,而且应该交给**没有参与实现**的人。它测的是"有没有什么事所有人都以为做了但没做",作者写自己的测试回答不了这个问题。

### 两个已知的接口协调点

任务 C 和 E 都涉及 REP 循环(串操作和 `INS`/`OUTS`)。**它们必须在同一套 REP 实现上达成一致**,否则会出现"MOVSB 能正确重复而 INSB 不能"这种 bug。两份任务书里都写了这一点,但需要有人实际去协调。

任务 D 会发现 `STI` 的延迟生效需要往 `struct vm86_cpu` 里加一个字段——那是对冻结接口的改动。**它应该在报告里提出来,由冻结接口的人统一加**,不要自己改头文件。

### 派活的建议

如果同时开五个,建议**先让任务 C 和 D 开始**——它们最可能撞上接口的不足,早发现早处理。A、B、E 相对独立,晚一点开始也来得及。

## 八、不在本次范围内

以下**明确不做**，不要顺手实现：

- **中断的真正投递**（INT n 跳到 IVT 里的处理程序）。M3 只负责把 `INT` 识别成一条指令、更新栈和 IP;IVT 和中断模型是 M4 的事。
- **8087 浮点**（`D8`-`DF` 的 ESC 操作码）。M7。
- **保护模式指令**（`LGDT`、`LMSW` 等）。更晚。
- **性能优化**（译码缓存、JIT）。DESIGN §3.3 规划了，但不在 M3。先把正确性做对。
