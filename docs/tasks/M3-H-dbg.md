## 一、为什么要做这件事

DESIGN 把单步调试器列为 M3 的一部分,风险登记里给了理由:

> 没有好用的 Shell 和文件系统,调试 DOS 程序会极其痛苦。缓解:**M2 必须做扎实**,调试工具(单步追踪、内存查看)要在 M3 就位。

也就是说这不是一个可选的附加项。M5 之后要靠它调真实的 DOS 程序,而到那个时候再写就晚了 —— 你会一边面对一个不认识的 DOS 程序,一边面对一个没人验证过的调试器。

还有一层:M3 的验收标准是"**能执行手工汇编的二进制,寄存器与标志位状态正确**"。这句话里"状态正确"是要**看得见**才能说的。调试器就是那个眼睛。

## 二、你要做什么

三个能力,加一个把文字送出去的方式。

### 2.1 单步

在一个 `struct vm86_cpu` 上精确执行**一条**指令。用现成的 `vm86_step()`(在 `vm86/ops.h` 里,已冻结),不要自己写分发。

### 2.2 状态格式化

把 CPU 状态变成人能读的文字。至少要有:

- 八个通用寄存器(`AX BX CX DX SI DI BP SP`),16 位
- 四个段寄存器(`CS DS ES SS`)—— **并且显示 `seg_base[]` 里缓存的线性基址**。这两个不一致本身就是 bug,看不出来就没法查。任务 F 在验证 `8E`(286 的延迟加载和 8086 的立即加载在这一对值上表现不同),这一栏对它有直接用处。
- `IP`、`FLAGS`
- **标志位要逐位展开成名字**:`CF PF AF ZF SF TF IF DF OF`,而不是只打一个十六进制数。只打数值等于没打。
- **保留位要如实显示。** 8086 上 FLAGS 的 bit 1 和 bit 12–15 **恒读为 1**(`VM86_FLAG_ALWAYS_SET`,见 `cpu.h`)。这正是当年程序用来辨认 CPU 型号的手法(压 FLAGS 再弹出来看)。一个把保留位藏起来的调试器,会让这个手法在调试器里看起来像 bug。**这是本任务里最重要的一个细节。**

### 2.3 内存查看

按 hex + ASCII 双栏 dump 一段 guest 内存。**必须走 `vm86_mem_read8()`**,不能直接解引用 `mem->ram` —— 未映射区域的 0xFF 语义、以及将来对 0xA0000 显存窗口的拦截,都只在那层后面。绕过去的话,dump 出来的东西和模拟器看到的不一样,而调试器最不该做的就是骗人。

### 2.4 输出走一个 sink,不直接 printf

这是**唯一需要冻结的接口**,因为同一份代码要在两个地方跑:

- 宿主测试里 → 写 `printf`
- 进了 FunnyOS 的 VM 进程之后 → 走 `SYS_WRITE`

所以格式化函数**不返回字符串、也不调用 `printf`**,而是接受一个回调:

```c
typedef void (*vm86_dbg_write)(void *ctx, const char *text, size_t length);
```

自己定一个你喜欢的形状也行,但**必须满足**:调试器里不出现 `printf` / `puts` / `stdio.h`,不依赖任何全局输出状态,并且内部缓冲不超过一个小的栈上数组(freestanding、用户态、没有 malloc)。

**校验这一点的方式**:让 `dos/dbg/trace.c` 的 include 列表里只有 `<stdbool.h> <stddef.h> <stdint.h>` 加 `vm86/*.h`。多一个都要有理由。

### 2.5 追踪记录

一次单步要能留下"执行前 → 执行后"的记录,包含:

- 执行前的 `CS:IP`
- **这条指令的原始字节和长度**(见下面第三节第 2 条 —— 为什么不做反汇编)
- 执行后的全部寄存器与标志位
- `vm86_step()` 的返回值(`VM86_CONTINUE` / `VM86_FAULT` / 其它),以及 fault 时的 `cpu->fault`

## 三、坑

### 1. 长度必须在单步**之前**解码出来

> 这一节的第一版举了三个例子来说明"`vm86_step()` 可能不前进":`jmp $`、`rep movsb` 配 `CX=0`、触发 fault 的指令。**后两个是错的**,任务 H 的负责人既核了代码也核了硬件:
>
> - `rep movsb` 配 `CX=0` 时,`IP` **前进 2 字节**。前缀字节在取指阶段就被消费掉了(见 `step.c` 的取指循环),`ops_str.c` 的 REP 循环对 `cpu->ip` 一次引用都没有。
> - 触发 fault 的指令,`IP` 也已经越过整条指令。
>
> **三个例子里只有一个成立。** 结论没变,但理由换了 —— 而理由才是承重的那部分,所以这里重写。

真正的规则是:**长度必须在单步之前由你自己解码,不能用 `step` 前后的 `IP` 相减。**

**唯一的例外是控制转移指令**(`jmp`/`call`/`ret`/条件跳转……)。它们的"长度"和它们的"IP 增量"是两回事:相减得到的是跳转目标,不是长度。除此之外,一条非控制转移指令的 `IP` 增量就等于它的解码长度 —— 这一点任务 H 用一次全操作码扫描立住了:每个被认领的操作码 × 四种 ModRM 填充,解码长度与 `step` 实际消耗的 `IP` 增量逐一比对,804 组全一致。

顺带,前缀在取指阶段被消费这件事还有一个后果,它是个**很有用的反向用例**:

> `rep movsb` 配 `CX=0` 时,整条指令什么也不做,但 `IP` 仍然走 2 字节。

它区分了"**指令没执行**"和"**IP 没动**",而这两件事在实现里很容易被混成一个。写调试器时把这条钉成断言 —— 它是"`step` 到底怎么前进"这件事上唯一一个反直觉但正确的情形。


### 2. 不做反汇编器,**但也不要把这项留白**

反汇编器(把字节变成 `add ax, bx`)是一个独立的大工程,而且半个反汇编器比没有更坏 —— 它会自信地打错。**M3 不做,明确记下来。**

但"没有反汇编器"不等于"看不出这是什么指令"。把**原始字节和长度**打出来就够用了:`0034: 01 D8  (2)` 配上任何外部反汇编器都能还原,而且不会说谎。所以追踪记录里必须有字节和长度,**这是不做反汇编器的前提**。反过来,如果你只记 `CS:IP` 不记字节,那这一条就变成了一个真的缺口。

### 3. `VM86_FAULT` 之后状态是半成品

指令触发 fault 时,寄存器可能已经被改了一部分(比如 `DIV` 在设置 `cpu->fault` 之前已经动过标志位)。追踪记录要如实反映这一点 —— **记录的是"执行之后真实的状态",不是"一条正常指令执行完之后应该有的状态"**。这两者在 fault 时不同,而调试器正是用来看这种不同的。

### 4. 单步要能把 CPU 留在可继续的状态

`vm86_dbg_step()` 跑完之后,`cpu` 必须还能被 `vm86_step()` 继续驱动,或者被再次单步。不要为了取字节而留下一个"取指位置已偏移"的副作用 —— 如果实现里需要偷看 `CS:IP` 处的字节,用 `vm86_mem_read8()` 自己按 `CS:IP` 读,读多少都不改变 CPU。

### 5. `dos/Makefile` 的套件号册方式

`dos/Makefile` 用一个 `SUITES` 变量,靠静态模式规则(`test-%: $(BUILD)/test_%`)把 `make test-dbg` 挂上去。注意 `make test-<套件>` **曾经是静默不跑的**(对 `.PHONY` 目标 make 会跳过隐式规则搜索),已于 2026-09-30 修好。加套件时**确认 `make test-dbg` 真的跑了**,别只看它退出码是 0 —— 那正是当初漏掉这个 bug 的原因。

## 四、完成标准

1. `cd dos && make test` 全绿,`-Werror` 下零警告
2. `make test-dbg` 会**真的执行** `test_dbg`(用 `make -n` 或者故意让一条断言失败来证明,不要只看退出码)
3. 测试覆盖至少这些:
   - 一条普通指令单步之后,`CS:IP` 落在正确的位置
   - **`rep movsb` 且 `CX=0`**:单步之后 `IP` 到底动没动?把结论写成断言。这是第三节第 1 条的活证据。
   - 一条 fault 的指令单步之后,`cpu->fault` 被设置,并且记录里的状态是"执行之后的真实状态"
   - 标志位格式化:`FLAGS` 的保留位(bit 1、bit 12–15)在文本里**出现**,并且读到的是 1
   - 内存 dump 跨越未映射区域时得到 `FF` 而不是崩溃或 0
4. `dos/dbg/trace.c` 的 include 只有标准 C 的整数/布尔/大小这几个头加 `vm86/*.h`(见 2.4)
5. 报告里写:你的追踪记录长什么样、`vm86_dbg_step()` 怎么算出指令长度、以及**你没做反汇编器的理由和那项留白由什么补上**
