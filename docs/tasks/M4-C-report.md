## 二、任务书的勘误(三条,两条是内容错,一条是笔误)

**一、`INT 16h AH=02h` 不返回扫描码。** 任务书原文写"注意:`AH` 也要放扫描码,
没有的话给 0"。**那是错的**,已在 main@98140cd 勘误。实现只写 `AL`(换挡状态字节),
`AH` 原样不动。

- 依据:`dos-refs.md` 第五节。我另做了一次独立检索,结论相同 —— Ralf Brown 的
  INT 16/AH=02h 条目原文是 "**AH destroyed by many BIOSes**",没有任何来源说它返回扫描码。
- 分歧记录在 `dos-refs.md` 第八节(维基表格写 `AH`,详细资料一致写 `AL`),按 `AL` 走。
- 这条错了不会崩,但会让程序在"有没有按 Shift"上判断错,症状是某个按键行为不对,
  很难追到 BIOS 调用上 —— 正是 `mark-inferred-vs-checked-claims` 那条说的形状。

**二、计数不是 32 位回绕,是午夜归零。** 一天是 `0x1800B0`(1 573 040)个滴答,
午夜时计数**归零**,`AL` 就是那个午夜标志。依据 `dos-refs.md` 第六节。
已按此实现(见第三节的决定三)。

**三、任务书消息里的 "65456 / 1.193182 MHz" 是笔误。** 正确值是 **65536**
(任务书正文与 `dos-refs.md` 写的都是 65536)。1193182 ÷ 65536 = 18.2065 Hz。
如果照 65456 实现,速率会偏 0.12%,一小时差 80 个滴答 —— 不会崩,但会一直漂。
记在这里是因为**任务书里的数字也承重**(`task-book-claims-need-checking`)。

## 三、第四节的两个决定

### 决定一:换算放在 `bios1a.c`,不放宿主

**做法:** 宿主只调用 `bios1a_advance(st, ms)`,得到"这些毫秒值几个滴答",
再去 `vm86_raise(cpu, VM86_INT_TIMER)`。宿主不知道 18.2 这个数,
也不知道一天有多少个滴答。

**理由:** 常数只有一份。放在宿主的话,测试、FunnyOS、以及下一个宿主
**每一个都要知道一遍**,而"每一个都要知道一遍"就是"迟早有一个记错"。

**做成了精确有理数,不是"每次除以 54.925":**

```
tick/ms = 1193182 / (65536 × 1000) = 596591 / 32768000   (约掉公因子 2,已是最简)
```

累加器保存的是**余数**(`fraction`,单位是 1/32768000 个滴答),每次
`total = fraction + ms × 596591`,`ticks = total / 32768000`,余数留下。

- 实测:`advance(1000)` 调 1000 次 → **18206**(精确值 18206.48,向下取整);
  `advance(10)` 调 1000 次 → **182**;一分钟 → **1092**;一小时 → **65543**
  (注意一小时差一点就是 65536)。
- **误差恒小于一个滴答,而且不随时间增长** —— 不是"有界",是擦掉的部分
  全部留在余数里,一次都没丢。任务书要求"用一个明确的数字钉住",这里的
  数字就是那个分数本身。
- 边界用例:`advance(54)` → 0、`advance(55)` → 1。一个滴答是 54.925493 ms,
  不是整数毫秒,所以边界落在 54 和 55 之间 —— 这一对把速率钉到优于一毫秒。

### 决定二:计数在 `INT 08h` 的服务里加,不在 `advance` 里加

**做法:** `bios1a_advance()` 只回答"该响几下";`0040:006C` 只有 `bios1a_irq()` 会加。

**理由:** 真机就是 `INT 08h` 的处理程序加的。这不是实现细节,是**程序能观察到的事实**:
一个挂钩了 `INT 08h` 又不链回原处理程序的程序,会让 BIOS 的计数**停住**。
这是真行为,不是 bug。`advance` 里加计数会把这个事实抹掉。

**一个跟着来的后果,值得写下来:** `vm86_raise()` 按位去重(host.h 里说明过,
"已经挂起的向量再抬一次还是一个")。所以 `advance` 一次返回 N 个滴答、宿主调 N 次
`raise`,实际只挂起一个中断 —— N−1 个滴答丢了。这**和真机一致**(8259 的某条线上
一次未处理完的请求期间再来一个边沿会丢),所以 guest 长时间关中断时 `0040:006C`
会落后于真实时间。BIOS 的计数是钟,不是秒表。

### 决定三:`INT 1Ah` 的 02h/04h 不注册服务

**做法:** 不注册。调用落到桩上,**什么都不做,AH 保持调用者放进去的值**。

**理由:** 那要 CMOS 硬件,这台机器没有。两条路:

- 落桩什么都不做 → 程序看到 AH 没变 → 判定"没有这个功能" → 走 PC/XT 路径。**选了这条**。
- 返回一堆 0 → 看起来像 **1980-01-01 00:00:00**,程序会当成真时间用,
  而且**没有任何办法分辨**。

依据 `dos-refs.md` 第六节(以及第九节对 CMOS 的说明)。

## 四、**接口里没写、但阻塞读必须有的一步:重试之前要开中断**

**这是这份报告里最值钱的一条。**

`vm86_service_retry()` 的文档说的是"把这条指令重跑一遍,两次之间有一个指令边界
让运行循环投递硬件中断"。**但那一步不会自己发生。**

`vm86_interrupt()` 会清 IF(那是 `INT` 的语义)。走到 `bios16_service` 里的时候,
guest 的 `INT 16h` 已经把 IF 清成 0 了。而 `vm86_interruptible()` 要求 **IF=1**。
两者一叠加:

```
IF=0 → 运行循环判定 guest 不接受中断 → 不投递 IRQ1
     → 队列永远空 → 服务永远重试 → 「程序卡住不动」
```

不是报错,不是死循环被步数预算打断 —— 是**卡住**,和任务书第三节警告的那种
"读不出东西的死循环"长得一模一样,但原因完全不同。

**做法:** 重试前把 IF 打开。

**依据:** 真机的 BIOS 阻塞读正是这么做的 —— `INT 16h AH=00h` 的处理程序
**先 `STI` 再开始等**,因为 `INT` 把 IF 清了。这不是为了模拟器方便,是同一个原因。

**并且刻意**没有**做 STI 的另一半。** STI 还会把"中断识别"延迟一条指令
(`intr_shadow = 1`)。这里**不能**设:那个影子是一次性的,而这个服务**每次重试都会
从函数头重新进入**,重新起影子就等于在"本该清掉它的那个边界"之前又立了一次 ——
机器永远投递不出任何东西。运行循环返回这一动作本身已经提供了那个延迟。

**这条接口里一个字都没写。** 任何做阻塞服务的模块(将来 `INT 21h AH=01h` 的
带回显读键盘、`INT 16h AH=10h`)都会踩它,而且症状是"程序卡住不动"。

### 它最后落在哪儿:在 `vm86_service_retry()` 里,不在服务里

我最初的修法是在 `bios16_service` 里自己 `vm86_flag_set(cpu, VM86_IF, true)`。
**协调方指出这行该在 retry 里**(main@`5a929f2` 已经那么修了,而且时间上早于我开工,
只是我的分支不含它),理由是对的,而且比"少一行"更重要:

放在服务里的话,**每一个**阻塞式服务都得记得这一句,而**忘记的后果是死锁而不是报错** ——
不编译不过、不测试失败,是机器停住。会忘的那个服务,恰恰是**没写"等一个事件"的用例**
的那个。放在 retry 里只有一份,而且和"重试"这个动作绑定。

**本分支已按此改**:`bios16.c` 不再自己开中断,只调 `vm86_service_retry()`,
并在原处留了一行注释说明为什么刻意不在这儿做。`host.h` 的 `vm86_service_retry`
声明下面现在同时写了 IF 和 `intr_shadow` 两条 —— 后者是我这一轮报的。

### 附带一条:重试**不弹帧**,任务书的心智模型和实现对不上

任务书第三节写的是"**把这条 `INT` 撤销并重来** —— 弹掉 INT 压的帧、把 IP 退回指令本身",
第十节又要求断言"**SP 复原**(帧真的弹掉了,没有泄漏)"。

**实现不弹任何东西。** `vm86_service_retry()` 只有一行:`cpu->ip = cpu->insn_ip;`。
理由是 host.h 里写了完整推理的那个:帧里存的是 `INT` **后面**那条指令的地址,
按它弹会恢复执行到"读完了",而不是重跑读;而且"把帧退回去"对经由 `INT` 到达的服务
是配平的,对经由链接的远调用到达的服务就是错的,重试还得先知道自己是哪一种。

不弹的代价是零:**重试重跑的是陷阱指令本身**(桩里的 `FE 38`),
不是整条 `INT`,所以**不会再压一次帧**。那条帧一直原样待在栈上,
最后由桩自己的 `IRET` 弹一次 —— 无论服务重试了几次。栈是配平的。

**所以我的用例断言的是可观测量,而且刻意不去决定这件事:**

- 重试之后 guest **没有**从那条 `INT` 返回(`cpu->ip` 不等于 `INT` 的下一条指令);"服务直接返回"会让它等于;
- 整条阻塞读**成功之后** `cpu->sp` 回到 `INT` 之前的值 —— 这才是"没有泄漏"。

**这里有一个需要说明的改动。** 我最初写的是 `cpu->ip == 桩的首字节`,那等于**用测试
把"重试回到桩"这个实现选择钉死了**。A 那边的 `retry.c` 走的是另一条路(弹掉帧、
还原 FLAGS、退回到那条 `INT` 本身)—— 两条路都能让 guest 真的在等,中间值不同而
**最终结果相同**(栈配平、键读到)。一条钉死其中一种的用例,会在决定改向的那天变红,
而且看起来像"实现坏了"。

现在断言的是"读还没返回":两种实现都过,而**破坏性的实现**(不重试、直接返回)
仍然被抓住 —— 变异测试确认(`the retry is not asked for` 照样被杀)。

## 五、三处缺口(任务书第九节)

### 1. 8259 的端口

程序用 `out 0x21` 屏蔽 IRQ 是常见做法。M4 的 `IN`/`OUT` 把端口吞掉,所以:

- **不是"收不到中断",是"关不掉中断"。** 一个用关中断保护临界区的程序保护不住;
  一个靠"关了就没有定时器中断"来避免重入的程序**会重入**。
- 后果的严重程度取决于程序:大部分程序只是多收几次定时器中断(计数多走几个),
  少数会在临界区里被自己的中断处理程序打断。
- 真机的 8259 还负责优先级和 EOI;宿主现在自己决定"什么时候投递",没有 EOI。
  任务书第五节明确说 EOI 不归我管,记在这里是免得它消失。

### 2. 8042(键盘控制器)的命令

同上。后果:程序读端口 0x64(状态)、写命令字节(开关扫描码集、控制 LED、
清输出缓冲区)都会"什么都没发生"。

- 读 0x64 的程序拿到的是浮动总线的 0xFF 或 0 —— 有的程序据此判断
  "这台机器有没有 8042"。判断错的后果是走 PC/XT 的旧路径,那倒未必是坏事。
- 一个想把键盘 LED 点亮的程序(改 NumLock 灯)在这里不会报错,灯也不会亮。

### 3. CMOS / RTC(`INT 1Ah` 02h、04h)

见第三节决定三。**这条已经做了选择并且有测试**,不是遗漏:
`test_the_rtc_functions_do_nothing` 断言三者(02h/04h/一个不存在的功能号)
调用后 AH、AL、CX、DX 全部原样。

## 七、没覆盖到的 / 已知不完整的

**扫描码表的边界**

- 只做 **set 1(PC/XT)**。方向键是**单字节** 0x48-0x50,没有 `E0` 前缀
  (那是 AT/PS2 的两字节转义)。表里 0x54 及以上全是 `K_NONE`:
  **F11/F12、101 键键盘上独立的方向键/Home/End/PgUp/PgDn 段、右 Ctrl/右 Alt**
  在这里都不存在。为 101 键写的程序会少一些键,而且**不会报错**。
- 只做 **US 布局**。`dos-refs.md` 说扫描码表在它的范围之外,这张表是我按单一
  二手来源写的(见第六节),拿到 IBM PC 技术参考手册后应当逐行复核。

**`0040:0018` 的 bit2/3**

来源互相矛盾,而且**矛盾在 RBIL 自己内部**:它的 BDA 条目(表 M0011)是
SysReq@2 / Pause@3,它的 `INT 16h AH=12h` 返回表(表 00588)是右 Ctrl@2 / 右 Alt@3 ——
同一个字节的两种解释。另有 `0040:0096` 确实是右 Ctrl/右 Alt。

本机是 XT 类:只有一个 Ctrl、一个 Alt,两个键都不存在。所以只写 bit0/bit1
(所有来源都同意的那两位),bit2/3 一律 0。**这不是"忘了",是"没有能写的"。**

**没实现的行为**

- **Pause / Ctrl+Alt+Del / PrintScreen 的特殊处理**。真 BIOS 在 `INT 09h` 里做这些
  (Ctrl+Alt+Del 触发热启动、PrintScreen 调 `INT 05h`)。这里它们就是普通的几个键
  进队列。**Ctrl+Alt+Del 不会重启这台机器** —— 一个用它当作"退出"手段的程序
  会卡住。
- **Alt + 小键盘数字输入**(Alt-numpad 打字符)。真 BIOS 用 `0040:0019` 累积。
  `dos-refs.md` 第七节提到了那个字节,但它**不在我认领的字段表里**,所以没写。
- **`0040:0080`/`0082`**(缓冲区首尾偏移)。`dos-refs.md` 第七节记了,
  并注明"很多机器不支持"。没写。
- **`INT 16h` 的 10h/11h/12h**(扩展键盘的读键/查询/取扩展换挡状态)。
  任务书只列了 00h/01h/02h,没认领,落到桩上什么都不做。
- **Ctrl+方向键 / Alt+方向键的特殊扫描码**。表里 `K_KEYPAD` 的控制列是 0,
  所以它们和普通方向键一样给 AL=0 + 原扫描码。真机在 AT 上给 `E0` 扩展码,
  本机是 XT,按 XT 做。

**一处需要别人接手的东西**

- **`0040:0071` bit 7** 不在 `firmware.h` 的数据区映射里,也不在任务书第七节的
  字段表里,但任务书第八节的坑 4 要求溢出时置位。做法:`bios16.c` 里一个**文件内的**
  `#define BIOS16_BDA_OVERFLOW`,没有改头文件。如果以后有人给这个字节找主人,
  应该把它搬进 `firmware.h`。

**测试覆盖的边界**

- `bios1a_advance()` 的返回值和 `vm86_raise()` 去重语义的**组合**没有专门用例
  (一次返回 N 个滴答、实际只挂起一个)。它属于 A 的运行循环,记在这里。
- 那两个最小运行循环是**测试夹具**,不是产品代码。`vm86_run` 落地后应当替换,
  替换前它们和真循环的差异只有 `intr_shadow` 的递减位置。

## 八、测试与变异测试

**规模:** 37 个用例 / 159 项检查,`cd dos && make test` 全绿,零警告
(`-Werror` 开着,14 个套件全部通过)。

**变异测试:** 人工注入了 **32 个缺陷,32 个全部被杀**;
**37 个用例每一个都至少红过一次**。(工具是本轮临时写的,在仓库外,不入库 ——
`tools/verify-mutations.py` 是既有工具但只服务 `test_verify`,而这一轮不改 `tools/`。)

注入的缺陷分四类:

- **阻塞读**:不调重试;重试前不开中断。
- **服务号**:01h 取走键(`kb_peek` 内部前移头指针);01h 的 ZF 说反;
  02h 读错状态字节;未知功能号动了寄存器;00h/01h 动了别的寄存器。
- **环形缓冲区**:回绕晚一格;空/满判断反了;溢出标志不置;字的字节序反了。
- **翻译**:断码当成按键;松开换挡键不更新;Caps/Num 不起作用;左/右 Shift 对调;
  Alt 给出普通字符;Ctrl 不生效;锁定键在按下和松开时都翻转;
  **端口 60h 里的残字节被当成按键**(这条同时证明了状态位那一步是有用的)。
- **计数**:速率算错;余数丢掉;午夜边界写成溢出;午夜不归零;
  标志累加而不是置位;08h 不计数;08h 不链到 1Ch;00h 不清标志;00h 的 CX/DX 对调;
  01h 不清标志;RTC 功能返回 0。

**变异测试自己抓到两种假绿,都修了才好意思报上面的数字:**

1. **编译不过的变异不是"被杀"。** 有一个变异让 `kb_peek` 变成没有被使用的静态函数,
   `-Werror` 直接把它拦下,套件"失败"了 —— 但那是因为树不编译,
   不是因为有用例注意到了。脚本现在区分"编译失败"和"用例报红"。
2. **`copytree` 保留 mtime,`make` 于是跳过重建。** 一份没被改动的源码副本,
   mtime 比上一轮变异构建出的二进制**旧**,`make` 认为无事可做,于是跑了**上一轮的
   变异二进制**。第一次跑出的"基线是红的"就是这个。现在用 `make -B`。

这两条的形状和 `mutation-testing-a-layer-for-coverage` 那条记忆里记的一样:
**基线不绿则整套结果不可信**,而基线不绿的原因是构建系统,不是被测代码。

## 九、给下一个人的

1. **做阻塞服务之前先读第四节。** 重试不会自己让中断进来,`INT` 已经关了 IF。
2. **别"修"午夜标志的丢失。** 它是真行为的缺陷,`dos-refs.md` 第六节写了,
   代码注释里也写了。改成累加会让这台机器和所有真机不一致。
3. **别把 `01h` 写成取走键。** 程序普遍是"先 01h 确认、再 00h 读",
   取走的话每次读键前丢一个。
4. **方向键的 AL=0 不是翻译失败**,那是这台机器区分"方向键"和"数字"的唯一方式。
5. **`bios16_state` 里那个"控制器寄存器"字段不要合并掉。** 程序有权挂钩 `INT 09h`
   并从端口读走扫描码,那样队列里就没有东西 —— 那是它的权利,而分开两个字段
   是让这件事能被表达出来的唯一方式。
