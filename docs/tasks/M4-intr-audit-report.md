## 二、我自己算错的一处

第一次报告里我建议把设备字的 bits 2-3 改成 `11`,然后写了"即 `0x0031`"。

**那是错的。** `0x31` = `0b0011_0001`,它的 bits 4-5 是 `11`,也就是把初始显示改成 **80×25 单色**。正确的算法是 `bits 2-3 = 11` → `0x0C` → `0x21 | 0x0C = 0x2D`。

协调方定的 `0x002D` 是对的,并且把这条写进了 `firmware.c` 的注释("别用加一个数去设这些位")。我的建议值本身踩了那个坑,而**建议值是会被照做的** —— 这是本次审查里我自己犯的、影响最大的一处错。

用例 `the equipment word decoded bit by bit` 现在**逐位**断言,并且专门断言 `0x2D` 而不是 `0x31`,注释里写明了原因。

## 三、`run.c`:审查结论 —— **正确,包括那处偏离**

### 3.1 顺序的四条理由,每条都能失败

`run.c` 的注释说"顺序就是它的全部正确性"。我按四条论据逐条验证,每条都配了用例:

| 顺序 | 论据 | 用例 |
|---|---|---|
| **投递在 halted 之前** | `hlt` 是"等中断"不是"停"。先查 halted 会丢掉每一次唤醒,而丢掉的程序是空闲循环 —— 也就是操作系统而不是测试。 | `sti then hlt is woken by an interrupt`(变异"halted 检查提前"→ 该用例红) |
| **投递在预算之前** | `steps = 0` 是合法请求:"有没有该跑的,但不执行任何指令"。预算检查放前面会跳过它。 | `a zero budget still delivers`(变异同上) |
| **影子在两者之前** | 它是循环里唯一不靠指令就会变的量。 | 见 3.2 |
| **投递不清预算** | 中断不是指令;记进预算会让一台稳态中断负载下的机器每片跑得比空闲的少。 | 见 3.4 |

### 3.2 A 自己报的那处偏离:**正确**

他报的是"影子递减挪到预算检查之后"。我独立推了一遍**三种放法**,结论是他选的这一种是唯一正确的:

- **放在最上面(和投递检查在一起)**:STI 之后的下一条边界会先把影子减到 0,然后**放行投递** —— 于是"STI 之后的那条指令"在被执行之前就被中断了。**这正是该被阻止的事。**
- **放在预算检查之前(投递检查之后)**:正常路径没问题,**但切片边界上会出事** —— 一片恰好在 STI 处用完预算时,影子被减掉却没执行任何指令,下次调用就会在窗口内投递。**这就是他用例要防的"另一个入口进来的同一个故障"。**
- **放在 step 之后**:STI 执行完立刻减掉,等于没有宽限期。
- **放在 step 之前、预算检查之后(他选的)**:唯一一个既让"STI 后的那条指令"先进、又让宽限期跨切片存活的位置。

**用例 `the grace survives a slice that ends in it` 就是照这一条写的**:预算正好是 1(只跑那条 STI),然后下一次调用继续。断言客人处理程序记下的**被中断的 IP 是 `0x0102`**(宽限期生效)而不是 `0x0101`(早了一条边界)。变异测试里"影子在投递检查处扣掉"会同时打掉四条用例 ✓。

### 3.3 异常路径

- 向量还是桩 → `VM86_STOP_FAULT`,向量留在 `cpu->fault` 里给调用方。✓
- 向量被挂钩 → 当作普通中断投递。✓ 这是"不用逐向量表就能区分机器的异常和客人接管的异常"的那条规则,`a hooked fault is delivered to the guest` 端到端钉住(客人挂钩 → 除零 → 处理器跑 → 机器继续到 hlt)。
- **异常不受 IF 约束**(不可屏蔽):`an exception is delivered with interrupts off` 用 `cli; div bl` 证明。变异"给异常加 IF 门"会被它抓住 ✓。
- `cpu->fault` 在 `VM86_FAULT` 分支里**立刻**读走 —— 注释解释了为什么不能推迟(下一条指令开头会清掉它)。✓

### 3.4 我否掉的一个假设(写下来免得下一个人重新提)

我一开始认为"投递不占预算"会让循环**无界**:客人的故障处理程序如果自己也出错,而那个向量被挂钩,就会无限投递、`vm86_run` 永不返回,宿主拿不回控制权。

**推导之后这是错的。** 每一次**故障**都由一条指令引起,而 `retired++` 就写在 `vm86_step` 之后、`switch` 之前;每一次**后续投递**也都由一条指令引起(raise 来自宿主,只在两次 `vm86_run` 之间发生;或者来自服务,服务由陷阱指令触发)。所以:

> 一次调用里的投递次数 ≤ 已退休指令数 + 1 ≤ `steps` + 1,循环迭代上界是 `2*steps + 1`。

**有界,不是缺陷。** 我没有把它写成发现,也没有为它写用例(一个"证明它会挂"的用例会真的挂)。

## 四、这次新发现的两条

### 1(中)。`write_flags_back` 假设栈上恰好是 INT 的三字帧 —— **远调用链会被改写**

`trap.c` 新增的 `write_flags_back()` 把服务写进寄存器的标志位合并回**栈上 `SS:SP+4`** 那个字。对 INT 的帧这是对的(IP、CS、FLAGS,FLAGS 在 SP+4)。**但远调用只压两个字。**

一个用 `call far` 链到原向量的 TSR:进入时 `[SP]`=它自己的返回 IP、`[SP+2]`=它的返回 CS、`[SP+4]`=**INT 帧里保存的返回 IP**(不是 FLAGS)。陷阱把那个字当成帧里的 FLAGS 重写掉 —— 于是 IRET 会把它当成标志位弹出去,而且 SP 会多走两个字。

**为什么现在没暴露:** 固件安装的两条路径都安全 —— INT 压三个字,客人自己执行陷阱字节时也必须自己搭出同形状的帧(我用例 `a guest can execute the trap itself` 就是那么搭的)。**只有远调用链这一条路暴露**,而它恰好是 `host.h` 里"服务不能用 retry"那条注记点名的同一条路径 —— 也就是说这个情形被考虑过,只是没被考虑到这里。

**最小复现**(就在用例 `KNOWN DEFECT: a chained far call gets its stack rewritten` 里):把 `FE 38 10 CF` 放在 `CS:0100`,栈上摆一个远调用形状的帧(SP 处放返回 IP、SP+2 放返回 CS、**SP+4 放一个标记 `0xBEEF`**),走一条指令。

```
SP = 0xFFF0
[0xFFF0] = 0x0104      } 一次远调用会压的
[0xFFF2] = 0x0000      }
[0xFFF4] = 0xBEEF      <- 调用方自己的数据,不该被动
```

结果:`[0xFFF4]` 变成 **`0xF202`**(= `(flags & ~(IF|TF)) | (0xBEEF & (IF|TF))`)。用例断言的就是这个值,并注明**修好之后应当变成 `0xBEEF`**。

**建议:** 让陷阱记下它自己压帧的位置(或"我是不是被 INT 进来的"),而不是假设 SP+4;或者把写回限制在"帧形状确实是本次 INT 压的"时。这一处我不改 —— `trap.c` 是 A 的。

### 2。测试载入地址 `0x0100` **落在向量表里**(共享基础设施,不是核心的错)

`tests/harness.h` 的 `VM86_TEST_CODE_BASE = 0x0100`,而 `vm86_test_load` 把 `CS` 设成 **0**。

真实的 `.COM` 程序也确实在 `CS:0x100`,但它的 `CS` 是**自己的段**,永远不是 0。harness 把 CS 设成 0,于是程序的字节落在**线性 `0x0100`** —— 那在真机上是**中断向量表内部**(表是 `0x000`–`0x3FF`)。

后果:**在 0x100 装入程序会覆盖从向量 `0x40` 往上的向量表**。用例 `KNOWN HARNESS: the program loads inside the vector table` 把它钉住:先装表并确认向量 `0x40` 是桩,再装入六字节程序,确认向量 `0x40` **不再**是桩、而且它的入口就是程序的前两个字节。

现在所有用例都还成立,**只是因为**它们用的向量都低于 `0x40`、而且都是先装表后装程序。这对 M5 不是小事:一个挂钩 `0x60` 以上向量(TSR 私有 API 的惯用位置)的程序,会被**自己的代码**覆盖掉它刚设的向量,而机器会跳到程序中间去。

**建议:** 这是共享基础设施,不在我该改的文件里。要么 harness 用一个非零的 CS(比如 `0x1000`,更接近真实 .COM 的布局),要么把代码区搬到 IVT 之上并让测试显式知道。**在 M5 的加载器写出来之前值得先定**,因为加载器的布局要和测试的这个假设对上。

## 五、我查过、确认没问题的(第二次)

- **`vm86_raise` 的 `|=` 行为本身**:同向量两次算一次、不同向量各留一位、同字节内多位互不覆盖。这是对中断线的正确建模(mutating 成 `=` 会被"同字节两向量"那条用例抓住)。**设备那一半**现在写在 `host.h` 里了;谁把扫描码写进缓冲区由 C 决定。
- **`vm86_interrupt` 的帧**:顺序、IF/TF 的清除与"帧里保留调用方的 IF"、以及**不清 `halted`**(那是循环的活,现在 `run.c` 在一个地方清它,并且注释说明"到达这一行就是被唤醒的定义")。三者各有用例。
- **重试**:跨三次重试栈完全不变、机器 IF 在重试期间为 1、调用返回后客人的 IF 回到调用前的值。回卷目标是**桩**而不是 INT,所以帧只压了一次 —— 这一点与 `host.h` 现在的措辞一致了。
- **`write_flags_back` 的安全性论证**:IF/TF 取自帧而不是寄存器,所以服务**不能**用这条通道把中断关掉、也不能给客人装上单步陷阱。变异"IF/TF 取自寄存器"会被 `a service cannot leave interrupts off` 抓住。
- **`install_ivt` / `vector_is_stub`**:无改动,`0xA5` 预填扫描仍然显示表区之外被写字节数为 0、`0xF0400` 仍是填充值。
- **`run.c` 的预算记账**:见 3.4,有界。
- **一处观察(不是缺陷)**:宿主 raise 一个**没有服务**的向量时,待决位会被投递、桩 IRET 掉、一台 halted 的机器会被"唤醒"但什么也没发生,程序随后越过 HLT 继续。宿主只会 raise 它实现了的向量,所以这条现在够不着;记在这里是因为 C/D 接键盘和磁盘时可能碰到。
