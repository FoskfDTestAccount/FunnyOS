## 二、需要处理的问题

### 问题 1(中,会丢数据):`vm86_raise` 的 `|=` 与键盘

**事实**(`test_raising_twice_is_one_interrupt`、`test_two_vectors_sharing_a_byte_are_both_remembered`):同一个向量 raise 两次只留一个待决位;不同向量各留一位;同字节内多位互不覆盖。

**注释给的理由是"这就是 8259 的做法"。这个理由对中断线成立,对键盘不完整。**

- 对**中断控制器**(edge 触发、IRR 是锁存位):同一根线在中断被取走之前再次拉高,确实还是一次。✓
- 但**真机的键盘路径会重新拉高**:8042 的 ISR 把扫描码从端口读走之后,如果键盘控制器里还排着下一个键,它会**再次**拉高 IRQ1 —— 那是一**次新的边沿**,于是客人拿到**一次新的中断**。所以 N 次按键最终得到 N 次中断,只要每次都被服务。

**我们的 OR 会把"客人还没取走时到达的一串按键"合并成一次。** 后果取决于**谁把扫描码放进 BIOS 缓冲区**(`0040:001E` 的环形队列,见 `dos-refs.md` §5):

- 宿主**直接写缓冲区**、IRQ 只是"叫醒" → **安全**,数据不依赖 ISR 跑几次。
- 向量 `09h` 的服务是**每次读一个**宿主队列项 → **按键会丢**,而且丢的是"打字快的时候才丢"的那种间歇性故障。

**建议(这是唯一一条会影响别人系统的发现,请优先定):**

> **把约束写进 C 的接口:向量 `09h` 的服务必须一次排空整个宿主队列,不能一次取一个。**

或者把 `|=` 换成计数(代价是引入一个真 8259 没有的概念,我不推荐)。

`dos-refs.md` §8 的矛盾表里没有这一条,所以它不是"两说取一",而是**注释里的类比不完整**。

### 问题 2(中,时序陷阱):`insn_ip` 今天只有一个写者

**事实**(`test_nothing_but_the_trap_writes_the_instruction_pointer_record`):执行三条普通指令(`mov ax,1` / `inc ax` / `hlt`),`insn_ip` 一个字节都没动。

`cpu.h` 与 M4-README 都说这个字段由**运行循环**在消费前缀之前记下。但 `vm86_step()`(`step.c`)**没有写它**。全树唯一的写者是 `trap.c` 的 `cpu->insn_ip = (uint16_t)(cpu->ip - 2u);`。

**所以今天这个字段的含义是"最后一次宿主陷阱",不是"当前指令"。**

现在没有坏,是因为唯一的读者(`vm86_service_retry`)要的**正好是桩的地址** —— 见第三节第 1 条。

**但 M4-4/M4-7 让 `vm86_str_repeat()` 用它回卷。** 如果 REP 在运行循环记录它之前接上:

> `rep movsb` 在任何一次 INT 之后都会回卷到 `F000:` 里那个桩,把 **REP 变成一次跳进 BIOS**。

**建议:**

- 运行循环落地时**必须**补上那一行;并且
- **在它落地之前,不要把 REP 的回卷接到 `insn_ip` 上。**

这条不是 A 交付代码里的缺陷(记录本来就不在它的范围里),是一条**顺序上的地雷**。我把它写成用例,是为了让"先接 REP"这个顺序**会红**。

---

### 问题 3(低,不可达,但注释是错的):`ip - 2` 的两种算错情形

陷阱运行时 `cpu->ip` 指着服务字节,所以"起点"是 `ip - 2`。**这只在"陷阱与服务字节之间没有别的字节"时成立。** 有两种情况不是(用例各一条):

**A. 陷阱前面有前缀**(`F3 FE 38 10 CF`)
记到 FE 而不是 F3。注释说"早一或两个字节" —— **描述是对的**。

**但后果其实无害**:重试回卷到 FE 会重跑**同一个陷阱**,因为那个前缀(F3=REP)对 FE 不产生任何作用。它坏的是**这个字段的语义**(对读它的别人来说),不是重试。

**B. ModRM 带位移**(`FE 7F 05 10 CF`)
注释写的是 *"a register-form ModRM other than 38, where a displacement would sit between the opcode and the service byte"*。

> **这句自相矛盾:寄存器形式(mod = 11)永远不带位移。**

真正的情形是**内存形式**:mod = 01(8 位位移)、mod = 10(16 位位移),以及 mod = 00 且 r/m = 6(16 位直接地址)。

**这一种是有害的**:`FE 7F 05` 会把 `insn_ip` 记到 ModRM 字节 `0x7F` 上,重试于是回卷到 **`7F` = `jg rel8`**,跳到别处去。

**两种都不可从汇编器产生**(`FE 38` 本身产不出来,那正是选它当陷阱的理由),所以这是**注释与代码的契约**问题,不是活的 bug。

**建议:** 改注释(把 B 描述对),或者干脆承认 `ip - 2` 只在"我们自己的桩"上成立、并把这句话写成它的**定义**而不是"两种例外"。

## 三、确认没问题的,以及我是怎么确认的

### 1. `vm86_service_retry` 打开 IF —— **论证站得住,而且比我预想的更干净**

**我一开始的假设是错的。** 我推演成:重试回卷到 INT → 重新执行 INT → 再压一帧 → 每重试一次泄漏 6 字节栈,而且被重压的那一帧里 IF 已经是 1,所以**客人的 `cli` 会被永久抹掉**。

**用例把这两个都证伪了**,原因是**回卷目标是桩而不是 INT**:

- 帧**只压了一次**(INT 那次),重试只是在桩里重跑同一个陷阱;
- 所以栈**不泄漏**(测:跨 3 次重试,服务看到的 SP 完全相同;调用返回后 SP 回到起点);
- 而且桩最后那条 IRET 弹的是**那一帧** —— 里面是**客人原来的 IF**。重试期间机器 IF=1,**调用返回后客人的 IF 回到调用前的值**。

两条断言在同一条用例里,互为上下文。

**独立论证(不依赖"真 BIOS 也这么干"):** 重试这套机制**只有**在中断可投递时才可能结束。IF=0 时运行循环拒绝投递,缓冲区永远是空的,客人永远转 —— 死锁。所以"处理程序为了让等待成立而打开中断"是**结构上必要**的,不只是类比。

**那"真键盘 BIOS 会 `sti`"这句话本身**,我没有查到原件;**`dos-refs.md` 没有覆盖它**。所以报告里把它标成**推理**,不是事实。好在上面那条结构性论证不需要它。

**一条文档不一致(建议改 host.h):**

> 原文:"the frame the INT pushed is popped, and the instruction pointer is rewound to the instruction itself."

**两件事都没发生。** 没有 pop,回卷到的是桩。结果一样(一帧、中断开、IRET 还原本来的标志位),所以不是 bug;但读文档的人会去找一个不存在的 pop,而且**下一个写重试服务的人会以为帧已经被解开了**。用例 `a retry rewinds to the stub and not to the INT` 把这个事实钉住。

### 2. `vm86_interrupt` 不清 `halted` —— 理由成立,但它是一份**契约**

- **链式那条成立**:08h 处理程序转调 1Ch 时不是在"唤醒"谁 —— `vm86_interrupt` 在那条路径上被调用时机器本来就不是 halted,清不清都一样;真正会出问题的场景是"服务在 halted 的机器上跑",而那正是运行循环要负责的。
- **但树里没有任何地方清 `halted`**(`vm86_run` 不存在)。所以"运行循环在唤醒处清"目前是**未兑现的承诺**。
- **风险:** 运行循环忘了清 → `sti; hlt` 被唤醒后机器仍然 halted,而 `vm86_interrupt` 已经把中断投递了 —— 表现为"中断处理程序跑了一次,然后机器再也不动"。
- 用例 `vm86_interrupt does not wake a halted processor` 把决定钉住(变异"清 halted"会被它抓住)。**接运行循环时请把另一半也钉上。**

### 3. `vm86_vector_is_stub` 的比较 —— **对,而且是对的答案**

一个客人把向量写成**恰好等于** `F000:(v*4)` 时,报告"没被挂钩"。

- 这与 M4-5 的规则一致:规则问的是"还指不指向我们的桩",而不是"有没有人写过它"。
- 更严格的做法(记下安装时的快照、或监视 `0x000-0x3FF` 的写)**答案一样**,所以多出来的机器没有收益 —— 这正是 M4-5 明说的取舍。
- 唯一代价:一个"写回原值"的程序与一个"从没写过"的程序不可区分 —— 而它们的**行为也确实相同**,所以没有代价。

用例 `a guest storing the same vector reads as unhooked` 把它钉住,包括"半个挂钩"(只改 offset 不改段)也算被挂钩。

### 4. `vm86_install_ivt` 写到 `0xF0000` 的一整个 KiB —— 确认没写到别处

**怎么确认的:** 把整块 guest 内存预填成 `0xA5`(一个桩和向量都产生不出来的字节),装完之后**扫描全部 1 MiB**,统计落在表区之外的**被写字节数**。

结果:

- 表区之外被写的字节数 = **0**。
- 被写区域恰好是 `0x000-0x3FF`(向量表)∪ `0xF0000-0xF03FF`(桩区),两块不重叠。
- **最后一个字节**在 `0xF03FF`(向量 `FF` 的 IRET),紧挨着的 `0xF0400` 仍然是填充值。

### 5. `firmware.c` 的设备字 `0x0021` 的 bit 2-3 —— 你的怀疑成立,而且比"没把握"更糟

`dos-refs.md` §2 的表:bits 2-3 = `00`→16K / `01`→32K / `10`→64K / `11`→64K 以上。

当前值 `0x0021` 的 bits 2-3 = **`00`**,也就是**"主板内存 16K"**。

而同一个 `vm86_install_firmware()` 在 `0040:0013` 写下 **640**。

> **一台宣称"主板 16K"、同时又宣称"常规内存 640K"的机器是自相矛盾的。**

按 `dos-refs.md` §2 那张表,一台 640K 的机器应当是 `11`(即 `0x0031`)。

**"没有东西读回它们"这个理由也不成立:** `INT 11h` 就是把它交给程序的通道,程序确实用设备字判断机型 —— 只是**在这个仓库里**没有消费者,那是仓库的状态,不是机器的状态。

**保留意见:** 注释里说的"XT 给的就是 00"这句,我**没查到独立依据**;`dos-refs.md` §2 的表是我能找到的最好依据。所以:

> **建议改成 `0x0031`,但这一条标注为"按 `dos-refs.md` §2 的表应当如此",不是查证。**

用例 `the equipment word decoded bit by bit` 把**每一位**都单独钉住了 —— 改的时候它会告诉你改动了哪一位,而不是只说"值不对"。

### 6. `vm86_install_firmware` 只写 `0040:0010` 和 `0x0013` —— 理由成立,但留下一个后果

**"这两个字段没有归属的服务"成立**:没有东西维护它们、没有设备在背后。✓

**但后果是:装完之后所有视频字段是 0。**

| 字段 | 装完之后 | 谁读它 |
|---|---|---|
| `0040:0049` 模式 | 0 | 一个在设模式前读它的程序会以为机器在"模式 0" |
| `0040:004A` 每行列数 | 0 | 按它算列偏移的程序会全写到第 0 列 |
| `0040:004C` 每页字节数 | 0 | **按它算页地址的程序会除以 0** |
| `0040:0060` 光标形状 | 0 | 画光标的宿主 |
| `0040:0062` 活动页 | 0 | 同上 |

**这不是 `firmware.c` 的错**(分工是对的,`dos-refs.md` §7 / M4-9 也是这个分工)。它是**接口缺口:** 没有任何一个"安装视频固件"的钩子。

- 我在 B 那边(视频)独立报过同一条给 E。
- **建议:由 E 的集成在装完固件之后空跑一次 `INT 10h AH=00h`;或者约定一个 `bios10_install()` 承担这件事。**
- 用例 `KNOWN GAP: install_firmware leaves the video words at zero` 把这个后果钉住 —— 将来谁补上这一块,用例会告诉他"你刚刚改了五个字段"。

## 四、你清单之外的发现

### 1. `vm86_interrupt()` 在树里**没有任何调用者** —— M4-4 "唯一一份压帧实现"目前不成立

`INT n` 走的是 `ops_ctl.c` 里的 `do_interrupt()`:六次 `vm86_push16` + 两次清标志,**与 `deliver.c` 的 `vm86_interrupt()` 逐行相同**。

- 今天两条路**逐字节一致** —— 用例 `the INT instruction and vm86_interrupt agree` 把同一个向量分别从指令和函数送进去,比较 SP、CS、IP、FLAGS **以及栈上那一帧的三个字**。
- 但后果是:**`vm86_interrupt()` 是从未被执行过的代码**,而 M4-4 说三条路径共用它。
- 用例每次跑都会比较两者,所以它们**开始分歧的那天会红**,而不是等到有程序返回到错误地址。
- **建议(A 的范围):把 `do_interrupt` 改成转调 `vm86_interrupt`,删掉那份拷贝。** 这正是 M4-README 第三节第 3 条("不要写第二份共享实现")。

### 2. 陷阱的服务字节取自 **CS** —— 有意的,而且我端到端钉住了

`vm86_host_trap` 用 `vm86_fetch8` 取服务字节,也就是从**当前 CS** 取。所以一个把 `FE 38 nn` 放进**自己内存**的客人,服务号从它自己的段里读。

`host.h` 说这是有意的("DOS 程序在真机上也能直接调 BIOS")。用例 `a guest can execute the trap itself` 让客人**自己搭好帧**(返回偏移/返回段/标志位)、自己执行陷阱字节、再由 `CF` 的 IRET 回到客人搭的帧上 —— 这条路径此前**没有测试**。

### 3. `vm86_install_firmware` 的顺序要求**没有强制**

文档说"在 CPU 复位、内存挂上**之后**调用"。如果先装固件再 `vm86_mem_clear`,会得到一台"向量表和桩都在、数据区是空的"机器 —— 表是好的,所以看起来没问题,直到有程序去读 `0040:0010`。

建议:要么让 `vm86_mem_clear` 之后重装(现在的做法,靠调用者记),要么在头文件里把顺序写成一句更硬的话。

### 4. 服务注册表是**进程级**的,跨用例残留 —— 已知,我把它变成了断言

`trap.c` 的注释已说明"测试套件在用例之间要调 `vm86_clear_services()`",而 `vm86_test_main()` **不**代劳。任何新套件都必须自己清。

我用例 `clear_services removes everything` 把四个服务(10h/13h/16h/1Ah)同时注册再清掉,断言**一个都不再运行**且程序照常走完。这比"清完之后某个向量不响应"更接近真实风险(一个套件清了、另一个没清)。

**两个过程性的收获:**

1. **"同字节两个向量"那条用例是被变异测试逼出来的。** 我原来的 `raise` 用例只 raise 同一个向量两次 —— 而 `=` 和 `|=` 在那里**结果相同**,所以那个断言根本抓不住 `=` 这个错误。补了"两个向量落进同一字节"之后才真的能失败。这正是"永远不红的用例比没有更糟"的形状。
2. **基线检查当场抓到我自己的错。** 我第一次写"同字节两向量"用例时把 `0x0F` 当成了第 0 字节的向量(它是第 1 字节、bit 7),副本基线立刻报红。**如果没有先验基线这一步,那 19 个变异的结果都会是脏的。**
