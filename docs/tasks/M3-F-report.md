### 做了(续):和任务 I 的语料对了一次

写得比较晚才发现 main 上有任务 I 交付的 `dos/corpus/` —— 一批**手工汇编的程序**,
每个文件顶上写着"执行到 HLT 时寄存器、FLAGS、内存应该是什么",由 `replay.c`
检查。那是**另一个人独立推导出来的期望值**,虽然推导依据和我一样(8086 编程模型),
不是硬件,但它是**第二个独立来源**。

凡是两边覆盖到同一件事的地方,**结论一致**:

- PUSHA 保存的 SP 是"第一条 push 之前"的值,而且**和 `PUSH SP` 不是同一条规则** ——
  语料 `ext_pusha.asm` 的说法和我的 `pusha saves the stack pointer from before it
  started` 逐字同义。
- **移位计数为 0 时一个标志位都不动** —— 语料 `shift_loop.asm` 专门有一节测它,
  和我的 `a shift by zero changes nothing` 一致。
- 计数 >1 时 **AF 和 OF 都要 `ignore`**,`PF` 只看结果的低字节,`CF` 是"最后移出的
  那一位" —— 语料 `ext_shifts.asm` 的 FLAGS 推理和我的 `sar never sets overflow`、
  `a shift count is not masked` 一致。
- `SCAS` 像 `CMP` 一样设全部六个标志,`CX` 是"没看过的元素个数" —— 语料
  `repne_scasb.asm` 和我的两条 `repne scasb` 用例一致。

**没有对上的地方也值得记**:语料的 `chip_pushsp.asm` 测的是 `54`,**没有测
`FF F4`** —— 也就是说 §四.1 那处不一致,两个独立来源都漏了,只有我这一套抓到了。
（反过来讲,这也是它值得被写下来的原因。）

要注意这**仍然不是**"对照验证":两个人的期望值都出自同一份知识(8086 的编程
模型),一起记错的可能性并没有被排除。它排除的是"只有我一个人这么想"。

## 二、用例是怎么选的

不是"每条指令测一遍正常用法"——那是作者们已经做过的。选的是:

| 类别 | 例子 |
|---|---|
| 段的边界 | 指令跨过 CS:FFFF;字访问在 DS:FFFF 处跨进下一个段;push 在 SP=1 时跨过栈段末尾 |
| 内存的边界 | A20 关闭时字访问跨过 1 MiB 折返;A20 打开时读浮空总线 |
| 计数为 0 / 1 | 移位计数 0(一个标志位都不动);`loop` 的 CX=1;`rep` 的 CX=0 且 DF=1 |
| 精确的边界值 | 进位刚好发生/不发生;有符号溢出刚好发生/不发生;AF 在 bit 3 |
| 配对往返 | PUSH/POP、INT/IRET、CALL/RET、ENTER/LEAVE、PUSHA/POPA |
| 隐含段与段超越 | `lea` 的偏移、`A0-A3` 的偏移、串操作只有读侧被前缀改变、`bp` 的默认段 |
| 前缀本身 | 段超越只作用于一条指令;重复前缀;LOCK |

另外有一条我在写的过程中自己踩到、值得写下来:**同一测试函数里跑两段程序时,
FLAGS 不会自动复位。** `vm86_test_load()` 不碰 FLAGS,所以 DAA 的第二个子用例会
继承第一个用例设的 AF —— 于是"不该调整"的那一例被调整了,而且看起来像实现错了。
我第一版就是这样,6 条断言报了红。**这正是任务书警告过的"测的是残留物"。**

## 三、每个用例如何被证明能失败

`tools/verify-mutations.py`:把 `dos/` 复制到 WSL 本机文件系统,逐个变异体重建
`test_verify` 并运行,记录哪些用例报红。

- 变异体总数:**107**
- 应用不了或编译不过的:**0**
- 一个用例都没弄红的变异体:**0**
- 被至少一个变异体弄红的用例:**106 / 106**

107 个变异体分布在 `mem.c`、`decode.c`、`step.c`、`flags.c` 和五个 `ops_*.c` 上,
每一个都是一处真实的、会让某个行为变错的改动(交换字节序、把有符号读成无符号、
把 `>` 写成 `>=`、把顺序反过来、把一个"拒绝"删掉、把 `CX` 的判零写成别的值……)。
其中 **105** 个是改实现,另外 **2** 个改的是用例自己的期望值 —— 那一条在下面单独说明,
另一条只是冗余(A20 那处本来也能被改实现弄红)。

### 唯一一个不能靠改实现来弄红的用例

`a near jump wraps the instruction pointer`:这条性质是**结构性**的 —— `ip` 是
`uint16_t`,赋值时必然截断,写不出一个"不截断"的版本。所以用任务书 §一 允许的另
一种办法:把用例自己的期望值从 `0xFFF9` 改成 `0xFFF8`,确认它变红,再还原。
**这个用例能失败,但它不能被"改错实现"弄失败** —— 区别写在这里,不藏着。

### 变异测试抓到的是我自己的测试,不是实现

值得单独写下来:第一轮跑完,有问题的是 **4 处** —— 三个用例一个变异体都没弄红,
一个变异体会让模拟器死循环。逐条查下去,**四条全是我的测试写漏了**,不是实现
有问题:

| 用例 | 为什么没红 | 补了什么 |
|---|---|---|
| `lea ignores the segment override` | 我把 DS 设成 1000h、ES 设成 3000h,**两个段基址的低 16 位都是 0**。把线性地址截断成 16 位之后,"用哪个基址去减"根本看不出来。 | ES 改成 1001h(低 12 位不同) |
| `the immediate port is consumed once` | 我只断言了 IP,而那个"没被消费的 60h"恰好是 `PUSHA`,执行完 IP 还是 0x0104。 | 加了一条 SP 的断言 |
| `test keeps the destination and clears the carries` | `84 C3` 的 ModRM 里 `reg` 是 AL、`r/m` 是 **BL**,而"写回"写在 r/m 上。我只断言了 AL。 | 加了 BL 的断言 |
| `a string with a zero count...` 等 | 第一版里"删掉 CX=0 判据"的那个变异体会让模拟器在**一条指令内部**死循环(步数上限救不了,因为那一步永远不返回)。 | 换成"判据写错零值"的变异体,能终止 |

前三条是**典型的"测试全绿但测不到"**:三个断言都对,三个都没在测它以为在测的
东西。**这三处如果不做变异测试,会一直绿着。** 这正是任务书第一节要求"每个测试
都要证明它能失败"的理由,我按字面做了,结果它抓到的是我自己。

## 四、发现的问题

### 1. `PUSH SP` 的两条编码给出两个不同的答案 —— 需要 D 改一行

在基准提交上实测(`SP` 初值 8000h,执行后读 `SS:7FFE`):

```
    0x54      -> SP=0x7FFE  [SS:7FFE]=0x7FFE
    FF F4     -> SP=0x7FFE  [SS:7FFE]=0x8000
```

- **最小复现**:`FF F4`(=`push sp`),初始 SP = 8000h,执行后 SS:7FFE 处的字是
  **8000h**。同样的事用 `54` 做一遍是 **7FFEh**。
- **期望**:两条编码是**同一条指令**,应当给出同一个答案。`54` 按任务 B 坑 6 已经
  修成 8086 规则(压减**之后**的 SP),所以 `FF /6` 也应当是 7FFEh。
- **来源**:任务 B 坑 6 明写 8086 压减之后的 SP;手册没有单独描述 `FF /6` 的寄存器
  形式,但硬件上 PUSH 的微码只有一份,两个编码走的是同一条。
- **实际**:`ops_mov.c` 的 `op_push_pop_reg()` 对 `54` 单独处理(index == SP 时压
  `cpu->sp - 2`),而 `ops_ctl.c` 的 `op_group5` case 6 是
  `vm86_push16(cpu, vm86_operand_read(cpu, &mr.operand))` —— 先把 SP 读出来再交给
  helper,于是压的是减**之前**的值。**这正是任务 B 坑 6 描述的那个形状,只是它在
  另一个文件里又长了一遍。**
- **为什么两个独立来源都没抓到手**:任务 B 的测试钉的是 `54`,任务 I 的语料
  `chip_pushsp.asm` 也只用 `54`。这一套里唯一测 `FF F4` 的是我。
- **严重性**:**低。** 真实 DOS 程序做 CPU 探测用的是 `54`(那条是对的),`FF F4`
  基本上只有手工构造的字节才会出现。但"同一条指令两个答案"是一致性问题,而且这类
  不一致以后会被当成"两个编码语义不同"而去写文档解释它 —— 那才是真的代价。
- **修法建议**(由 D 的实现者定夺):在 `op_group5` 的 case 6 里对
  `mr.operand.kind == VM86_OPERAND_REGISTER && mr.operand.reg == VM86_REG_SP` 单独
  处理,和 `ops_mov.c` 保持同一规则;或者把这个特例提到一个共享 helper 里。
  **我没有改** —— 按任务书 §五.4,改动由实现者做,并且该由他们补一条用例。

### 2. `POP SP`(`5C` / `8F C4`)的行为与手册措辞不一致,且无人记录

在基准提交上实测(SP 初值 7FFEh,`SS:7FFE` 处是 2000h):

```
    0x5C      -> SP=0x2000    (手册的措辞读起来是 0x2002)
```

- **最小复现**:`5C`,初始 SP = 7FFEh,SS:7FFE 处是 2000h。执行后 SP = **2000h**。
- **期望**:手册 POP 条目的措辞是"把栈顶的字送到目的操作数,**然后** SP 加二"。
  照字面读,`pop sp` 应该是 2002h。
- **来源**:手册 POP 的正文措辞。**不是**标志位表 —— 这处没有任何表可以查。
- **实际**:2000h,即"对 SP 这个目的操作数来说,加二被最后那次写回吃掉了"。
- **严重性**:**极低**,没有程序依赖它。但它是一条"手册与实现不一致、而且没人写下
  来"的地方,属于任务书 §二.2 说的那类。
- **我做了什么**:没有改代码,也没有断言 2000h 是"对的"。用例
  `pop sp ends at the popped value` **钉住了当前行为**,注释里写明"这是本实现选的,
  手册措辞支持另一种读法,待定"。**这一条我无法判定,列在这里请有手册的人定夺。**
  (任务 I 的语料没有覆盖它,所以这是第二个只有一处来源提到的地方。)

### 3. 除法错误的向量号和 `cpu->fault` 的"无异常"值撞车 —— 接口层的问题

在基准提交上实测:

```
    div by 0  -> result=FAULT cpu->fault=0    (而 0 同时也表示"没有异常")
```

- **最小复现**:任何 `div` 除法错误(除数为 0,或商放不下)。
- **期望**:`ops.h` 里 `VM86_VECTOR_DIVIDE_ERROR` 是 **0**;而 `cpu->fault` 的约定是
  "刚执行的那条指令引发的向量,**0 表示没有**"(cpu.h)。两者冲突。
- **实际**:发生除法错误时 `vm86_step()` 返回 `VM86_FAULT`,`cpu->fault` 是 0 ——
  **和"没有异常"是同一个值**。只看 `cpu->fault` 的调用方分不出这两种情况。
- **严重性**:**中,而且是 M4 的。** 现在没有消费者(`ops.h` 说异常是"报告"不是
  "投递"),但 M4 写中断投递时,第一个要看的就是这个字段。这是一个**在没人读的
  时候就已经有歧义**的接口,而且它的表现是"除法错误看起来像什么都没发生"。
- **我没有改**(`ops.h` 是冻结接口,而且现在正在被其他人扩)。建议要么给 `fault`
  配一个"有效"标志,要么在 `ops.h` 里明确写下来"只有返回值是判据"。
- **顺带**:本套件里所有除法错误的用例都只能断言 `result == VM86_FAULT`,
  **断言不了 `cpu->fault`** —— 写 `vm86_expect_u16("vector", cpu->fault,
  VM86_VECTOR_DIVIDE_ERROR)` 和写 0 是同一件事,那条断言恒真。这也是为什么
  §三 里没有能弄红它的变异体。

### 4. 任务书里一处关于段边界的事实错误(F 自己的任务书)

- **位置**:任务 F §二.5 写着"16 位访问跨过 64 KiB 段边界(**8086 上偏移量会回绕**)"。
- **代码实际做的**:`mem.c` 的 `vm86_mem_read16()` 读 `linear` 和 `linear + 1` 两个
  线性地址,`vm86_linear()` 是 `段基址 + 偏移`,**偏移不回绕**。所以字访问在
  DS:FFFF 处读到的是本段最后一个字节和**下一个段的第一个字节**。
- **我认为代码是对的**:8086 的物理地址是 `段基址 + 偏移`,由二十位的加法器算出;
  字访问分成两次字节访问,第二次的地址是**物理地址 + 1**,而不是"偏移 + 1 再回绕"。
  回绕只发生在 20 位(1 MiB)那一次,而那一次 `mem.c` 用 A20 掩码正确地做了。
- **依据**:上面的物理地址模型;**不是手册原文**,我手上没有手册。
- **严重性**:这是**文档**问题,但它是本项目最怕的那种:一句写着"8086 就是这样"的
  话,会让后来的人去**实现**一个真实硬件上没有的行为(README §六 的原话)。
- **建议**:请有手册的人核一次;**如果代码是对的,任务书那半句要改掉**。我在
  `test_word_at_the_end_of_a_segment_crosses_into_the_next` 里把当前行为钉住了,
  注释里写明了两种读法都可能被误当成"正确",免得将来有人按文档"修"代码。

### 5. 那一轮"事实错误"清单的复核结果:哪些修在代码里,哪些只修在文档里

**先说一件容易看错的**:main 上关于 `0F` 的那次提交(`43c4771`)只动了**文档**
(`DESIGN.md`、README、任务书),**`dos/cpu/ops_alu.c` 里的那段注释一个字没改** ——
我核对时读的是文档,差点把自己骗过去。协调方说 `ops_*.c` 一直为我冻着,所以这是
**故意留着、等我交完再改**。我在基准提交上看到的代码注释仍然是错的:

```
   212:             * POP CS never existed. The 8086 left the encoding unused and
   213:             * the 386 took it for the two-byte opcode prefix, so on this
   214:             * processor it genuinely is not an instruction.
```

三处都不对:8086 上 `0F` 就是 **POP CS**;把它挪走的是 **80186**;两字节前缀是
**80286** 引入的。**行为(触发向量 6)本身是站得住的"选择",错的只是理由** ——
而按 README §六 的标准,一个编出来的理由比没有理由更糟。

| 项目 | 状态 |
|---|---|
| `0F` 的行为(拒绝) | **决定成立**,用例 `the undefined group encodings are refused` 钉住。 |
| `0F` 的**理由**(注释) | **代码里仍然是错的**,main 只在文档层改过。请改 `ops_alu.c` 第 211-215 行。 |
| `make test-<套件>` 打印 "Nothing to be done" 并返回 0 | **已在 main 修**(静态模式规则)。我独立复现了原因:`make` 对 `.PHONY` 目标**跳过隐式规则查找**,而模式规则 `test-%:` 正是隐式规则,于是文档里"跑单个套件"的办法静默地什么都不跑。 |
| 未声明的操作码表漏了 `64` | **main@43c4771 已在 README 记录**。 |
| 任务书里 `0F` 的芯片归属、D6/F1 的描述 | 同上一次提交,**文档层**。 |

### 6. 没有问题的部分(**这也是结论**)

下面这些我专门去攻过,**没有发现问题**:

- **共享算术核心** (`vm86_alu` / `vm86_alu_incdec`)。AF 的 `(dst^src^result) & 0x10`
  在加、减、带进位加、带借位减、两个宽度上都对(我按定义推了一遍,又在边界值上
  测了);OF 的两种形态、CF 在减法里是借位、INC/DEC 不碰 CF,都对。
- **`str_delta` 与 REP 循环**。CX=0 在第一次迭代之前判断;`F3` 在 CMPS/SCAS 上
  是"ZF 不再满足就停",`F2` 是"ZF 满足就停";CX 每轮减一包括最后一轮 —— 用
  `repne scasb` 找得到和找不到两种结局的 CX 都对了。
- **`ops_186.c` 全部复用 `vm86_str_repeat()`**,没有第二份 REP 实现 —— 任务书
  点名的那个协调点确实守住了。
- **`LEA` 不读内存**(用 `unmapped_reads` 计数器证的,不是靠肉眼)、`XLAT` 的
  BX+AL 在 16 位回绕、`XLAT` 不碰标志位。
- **`ENTER` 的非零层级**:层级 3 的链拷贝循环跑了两次,拷出来的两个字顺序正确。
- **`BOUND`**:有符号比较、两端都含在内、`mod=3` 拒绝。
- **`PUSHA` 压的是第一条 push 之前的 SP**,而 `POPA` 读到的 SP 被丢掉 ——
  两条规则和 `PUSH SP` 都不一样,实现没有把它们统一。

任务书要求把这些列出来。这些都是"代码选了某个行为、手册不承诺或两种都说得通"的
地方;我逐条核对了代码确实是这么做的,并且**都钉了用例**。

| 行为 | 谁做的 | 我核对了 | 用例 |
|---|---|---|---|
| `IN` 一律返回 `0xFF`,`OUT` 丢弃,都不触发异常 | D | ✓ | `in writes only the named half`、`the immediate port is consumed once` |
| `FF /7` 触发向量 6 | D | ✓ | `the undefined group encodings are refused` |

### M3 的三笔欠账(在 M3 里观察不到,只能读代码确认"没有建模")

1. **可中断的 REP 循环**。真实硬件每次迭代之间识别中断,所以搬一兆字节不会让
   键盘失灵几百毫秒。本实现整条指令一口气跑完。**M4 必须解决**,否则任何读大文件
   的 DOS 程序都会让定时器丢拍。我确认了代码里没有留半个机制。
2. **`STI` 之后一条指令内的中断识别延迟**。本实现立即置 IF。M3 没有中断投递,
   所以观察不到;M4 补齐之前,`sti` / `hlt` 空闲循环会在中断到达时丢失唤醒。
   我确认了 `struct vm86_cpu` 里**没有**那个"没人读的字段"—— 这是对的,写进去
   就是一个不可验证的状态。
3. **`mov`/`pop` 段寄存器之后一条指令内的中断识别抑制**。同上,同一笔账。

三条都不是 bug,是**在 M3 里不可验证**。我把它们列在这里,是因为**"读者读不出来的
偏差"和"没有偏差"在代码里长得一样**。

## 六、没有覆盖到的部分

按任务书 §四的要求,这一节和"发现了什么"同样重要。

1. **没有第二台模拟器,也没有手册原文。** 这是最大的缺口,重复一遍:本套件里
   **没有一条**是"对照硬件"。任务 I 的语料给了第二个独立推导(§一末尾),凡是
   重叠处两边一致 —— 但两个人的依据是同一份知识,一起错的可能性没被排除。所以
   如果我的某条期望值本身就是记错的,套件会**稳定地、自信地**通过,并且和实现
   一起错。§四.4 那条就是这种风险的实例 —— 我在那里写的是"我认为",不是"手册说"。
2. **未定义的标志位**一律用 `ignore` 跳过(逻辑运算的 AF、移位计数 >1 时的 OF、
   MUL/DIV 的其余标志、AAA/AAS 的 SF/ZF/PF)。手册对这些不承诺,所以**测试不能
   作为判据**;我只确认了实现"没有写它们",没确认它们应该是什么。
3. **20 位以上、1 MiB 以内的地址**。测试内存就是 1 MiB,所以"越界"只有 1 MiB
   这一个位置可测;显存窗口、ROM 区、扩展内存池的行为是任务 L 的范围,我没有重复。
4. **未实现的操作码**:`63`(ARPL)、`65`/`66`/`67`、`D6`(SALC)、`F1`、`D8`-`DF`
   (8087)。我只测了其中两个会被拒(`F1`、`63`),其余按 README §八 属于"故意不管"。
   `D6` 和 `F1` 现在**硅片其实是执行**的(main@43c4771 已记录),不实现是决定,
   不是事实 —— 这一点我不重复论证。
5. **性能**。不是本次范围。
6. **真实程序的行为**。我没有跑任何真实的 DOS 程序;`reference-msdos/` 里的源码
   我只用来判断某个差异"有没有实际影响",没有用它生成用例。M5 才能做这件事。
7. **不是我的范围的三个文件**:`decode.c`、`step.c`、`flags.c` 我只通过指令行为
   间接测了(前缀、IP 回绕、有效地址、ModReg 顺序、标志位计算),没有直接测
   `vm86_fetch_modrm()` 的每一种 mod/rm 组合,也没有测 `vm86_reg_get8/set8` 的
   八个寄存器各自。(任务 I/K/L 各自补了 `test_decode`、`test_step`、`test_mem`。)
8. **想过但判断为重复、因而没写的组合**(列出来,免得读者以为漏了):
   - `repe cmpsb` 在**第一个**字节就不同:`CX = N-1`。已有用例
     `repne scasb leaves the unscanned elements in cx` 在"第三个字节命中"上
     区分得开(错的实现会给 `CX = N`),所以没有另写。
   - `repne scasb` 在**最后一个**字节命中:`CX = 0` 且 `ZF = 1`,与"没找到"
     (`CX = 0`、`ZF = 0`)由同一条用例的两个半场区分开。
   - `rep movsb` 的 `CX = 1`:与已有的 `CX = 0` / `CX = N` 用例同型。
   - **嵌套的 INT/IRET**:帧逻辑是纯栈操作,单层往返已经钉住压/弹顺序和 FLAGS
     复原;嵌套多出来的是"第一次的 IRET 还没执行就再进一次中断",那测的是
     M4 的中断模型,不是这些指令。**这一条是真的没测。**
