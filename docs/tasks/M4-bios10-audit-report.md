## 二、发现的四条

### F1(缺口)**开机时没有人发布视频那一半的 BIOS 数据区**

> **后续(2026-10-01):这一条的性质被查明了,而且比 F1 当初描述的窄。** 协调方核对之后发现 `da036b2` **确实包含**他们的修复(`firmware.c` 在函数体里写那几个字段),那台机器**不会**报 mode 0。真正错的是**同一份文件的文件头注释**——它还写着"their resets fill them",而例外只加在了函数体里。**所以这是一处文档缺陷,不是行为缺陷**,已修。**保留在报告里的理由**:一个 reset 完、还没被问过的机器状态是对的,而**描述它的那段话是错的**;而**文件头是被读的,代码不是**。我是**读文档**时发现它的——这一点本身没错。

**这是这次审查最有价值的一条,而且它不是 B 一个人的问题——它是两个模块之间没人签字的接口。**

事实链:

1. `bios10_reset()` **一个字都不往 guest 内存写**。它的头文件说这是有意的("It does not touch guest memory, so it does not clear the screen"),理由只覆盖了**清屏**,没有覆盖**发布数据区**。
2. A 的 `dos/intr/firmware.c` 只写设备字和内存大小,并在注释里说其余的字段归各自的驱动:**"their resets fill them"**。
3. 而发布(`sync_bda`)只作为**服务调用**的副作用发生——不在 `reset` 里,也没有导出的发布入口。

**后果:** 一台 `install_firmware()` + `bios10_reset()` + 注册服务之后、**还没被问过任何问题**的机器,状态里是"mode 3、80 列",而 `0040:0049`/`004A`/`004C`/`0062` **全是 0**。一个开机就读 `0040:004A` 拿屏幕宽度(这是那个字段存在的主要理由,程序也确实这么读)的程序**读到 0**——除零、零长循环,或者更常见的"输出跑到屏幕外面去",而原因不在它的输出代码里。这正是 M4-README 的 M4-9 警告的那种失败:"一个 `INT 1Ah` 答得对、但计数是 0 的机器,会让一部分程序以没人猜得到的原因失灵"。

**用例钉住了它**,而且刻意钉成**当前的样子**(`test_the_data_area_is_empty_until_the_firmware_is_asked`):reset 之后三个字段是 0,问一次之后全部正确,未知功能号也会发布。**这三条断言今天不可能失败**——接口里根本没有"从 reset 发布"这条路——所以它测的不是代码,是**接口的形状**;它存在的意义是:**谁修好它,这条用例就会红,那时我们要被通知**。我在用例里写明了这一点,而不是把它写成一条假装在测代码的断言。

**修法(三选一,由协调方/B 定):**

- **(a)** 导出一个 `bios10_publish(struct vm86_cpu *, struct bios10_state *)`(`sync_bda` 从 static 变成公开的薄包装),E 在 `reset` 之后调一次。**改动最小,语义最干净**:发布和复位是两件事,各自有名字。
- **(b)** 让 E 的机器在跑 guest 之前先问一句(`AH=0Fh` 是最便宜的)。**今天就能用,零改动**,但这是一个**没人知道要做的仪式**——下一个人不会知道,而这条用例正是为了让这件事可见。
- **(c)** 让 `bios10_reset` 收 `cpu` 并就地发布。与它现在的头文件注释冲突(那条注释说要故意不碰内存),而且会打破"reset 是纯函数"这个性质。

**我倾向 (a)**,因为它把"谁在什么时候发布"从一个隐含的副作用变成一个可以指出来的调用。

### F2(与参考的差异)**`09h`/`0Ah` 在屏幕底部的行为**

`write_run()` 在行尾回绕到下一行,**到最后一行就停住**。参考(§1)没有写这两条中的任何一条,任务书也没写,所以这是一个**决定**。B 在代码注释里解释了"为什么"不动光标,但没有解释"为什么停住",也没有说出处。

**我把 B 自己引用的那份 vgabios 读了**:它在文本模式下**两者都不做**——地址只算一次(`(xcurs + ycurs*nbcols)*2`),然后 `address += 2` 一路写下去,既不看行尾也不看屏底。

**所以两者的差别比看起来小得多**:整页内存是线性的,B 的"回绕到下一行"和 vgabios 的"线性推进"**逐字节相同**;真正的差别只在**最后一行之后**——B 停住,vgabios 继续写进**下一页的内存**(在页 7 上就是写出视频窗口之外)。B 的选择更安全,而且是这台机器想要的("不要写到别人的内存里")。

**结论:建议保留 B 的行为,把它标成一个决定并写出处。** 它现在是一条没有出处、也没有说明的规则。

### F3(依据缺失)**`00h` 的 `AL` bit 7**

任务书坑 3 明确要求:这条**要么确认,要么在报告里写成"我们没实现"**。B 实现了它,并且在注释里断言"这是一条真规则,不是传说"——**但没有说这是从哪知道的**。这正是这个项目一直在抓的那种形态:一条读起来完整的理由,读者就不去查了。

**我查了:规则成立。** vgabios 原文里是

```c
Bit8u noclearmem = mode & 0x80;
mode = mode & 0x7f;
...
if (noclearmem == 0x00) { ...wipe the screen... }
```

掩掉、查表、按那一位决定清不清屏——和 B 的实现完全一致。**代码是对的,缺的只是那句话。** 建议在 `set_mode()` 的注释里补一行"依据:vgabios 的 `noclearmem`"。

### F4(加固建议)**一个全零的 `bios10_state` 不是一台安全的机器**

`reset` 没被调用时(结构体是零初始化的),`columns == 0`。而 `teletype()` 里有一句

```c
if (col >= st->columns)
    col = (uint16_t)(st->columns - 1u);      /* 0 - 1 == 0xFFFF */
```

于是列被夹到 **65535**,`cell_linear()` 算出 `row * 0 + 65535` 个单元——**离视频窗口 128 KiB 远的地方**,而那块内存是 guest 的普通 RAM(1 MiB 以内),所以**写成功、`dropped_writes` 不涨、屏幕没变化**。一个忘了 `reset` 的集成会得到一台"打字没反应、但内存莫名被改"的机器,而症状指向显示后端。

**这不是 B 的错**(契约是"先 reset"),但它是一处**没有守卫、失败方式又很隐蔽**的边界。建议:服务的入口加一句 `if (st->columns == 0) return;`——一行,把一个"静默写坏内存"变成一个"什么都不做"。或者更好:**把"必须先 reset"写进头文件的契约里**,并让 E 的集成代码显式地做这件事。

## 三、审查套件自己的三件事

审计别人的代码时,自己的工具也得接受同样的检验。变异测试暴露了审查套件自己的两处**不锋利**,以及一处**等价**。

### 3.1 第一版有两处抓不住东西,已修

- **N8(`09h` 用活动页)** 第一次**存活**:因为我的用例里 `09h` 被调用的那一刻 **BH 恰好等于活动页**(都是 0)——两条规则在那个输入下答案相同。修法不是加断言,是**换输入**:先把页 0 的光标挪到 (0,5),切到页 1,再调 `09h` 并且 BH 仍指页 0。**这正是我审 B 时用的那条标准,回头打在了自己身上。**
- **N14(未知功能号不发布)** 第一次**存活**:因为那条用例里 BDA 本来就是对的,"没发布"看不出来。修法是**先把 BDA 写坏**(`0040:004A = 0x9999`)再调未知功能号,要求它被修正。状态是真相、数据区是副本——**副本过期就该被纠正**,这本来就是 `sync_bda` 的意义。

两处修完之后两个注入都被抓住。我把它们留在报告里,因为"审查者自己的用例也可能不锋利"这件事,比结论本身更该被记住。

### 3.2 一条断言是"不可能失败"的,我把它标出来了

F1 那条用例的前三条断言**今天不可能红**——接口里没有能让它们失败的路。这是**故意的**,并在用例注释里写明:它测的是接口的形状,不是代码;谁要是给 `reset` 加上发布,它就会红,那时它提醒的正是我们。**把一条不会失败的断言混在会失败的断言里不说明,是这个项目一直在防的事**;说明它是另一种。

### 3.3 N4 是等价变异,不是漏网

`if (lines == 0 || lines >= height)` 改成 `> height`。这两者在**任何输入**下结果都一样:

- `lines == height`:走真正的滚动分支,但复制循环的条件 `row + lines <= bottom` 一次都不成立(top + height = bottom + 1),而填充循环 `bottom - lines + 1` 正好从 `top` 开始——**整窗填满**,和"清窗"完全一致;
- `lines > height`:两条分支都被 `>=`/`>` 判为"清窗",仍然一致。

所以这是一条**等价变异**(和 D 那边 `sector == 0` 那条同一个形状:边界放松了,但另一条分支退化成了同样的结果)。处置不是补用例——补不出来——而是**记录它为什么等价**。用例本身仍然有价值:它钉住的是**可观察行为**(整个窗口被填满),而不是某一条实现路径。

## 四、顺带回给 `docs/dos-refs.md` 的两条

审的过程里重读了参考引用的两份源码,有两条**参考自己需要复核**:

1. **§8 那条分歧里说"SeaBIOS 用固定的 `0x07`"** —— 与当前 master 不符。SeaBIOS 的 `write_teletype` 在滚动时传的是 `struct carattr attr = {' ', 0, 0}`,第三个字段是"属性有效"标志且为 0,**意思是不改属性**,不是"用 0x07"。
2. **vgabios 那一半,这次查实了**:`address = SCREEN_MEM_START(...) + (xcurs + (ycurs-1)*nbcols)*2; attr = read_byte(..., address+1);` —— 它读的是**光标上一行那一格**的属性。B 的实现读的是最底行那一格,而滚动发生在光标刚越过底边的那一刻,`ycurs-1` 就是最底行——**同一个格子,两者一致**。B 的注释和代码对得上。

   **所以 §8 那条"两份实现不一致"里,vgabios 的那一半现在是查证过的**,SeaBIOS 的那一半要改。

3. **§1 那条 TAB 规则("补空格到下一个 8 的倍数")** 引的是 vgabios。我重读到的循环条件是 `do { 写一个空格; 重读光标 } while (列 % 8 == 0)`——**读起来是反的**(在列 0 上只会写一个空格),而 SeaBIOS 干脆**没有 TAB 分支**(0x09 走可打印字符的默认路径,把它当字形打出来)。**B 实现的是 §1 写的那条**,与参考一致;但**参考这条规则的依据本身值得再看一眼**,因为两份源码在这一点上既不一致、其中一份还很可能是抄错了。
