**审查者:** B
**审查对象:** `dos/intr/firmware.c`、`dos/include/vm86/firmware.h` 里新增的三个字段(`0040:0084`/`0x0087`/`0x0071`),以及 `docs/tasks/M4-README.md` 第八节的缺口措辞。
**交付:** 用例加在 `dos/tests/test_intr_audit.c`(3 条)与 `dos/tests/test_bios10.c`(1 条)里 —— 见第四节说明为什么没有另开套件。本文件是报告。
**约束:** 没改 `dos/intr/`、`firmware.h` 或 `M4-README.md`。变异实验在 `/var/tmp` 的副本上做,基线先验。

## 〇、结论

**三个字段的值全对,上电组与第一次 `INT 10h` 之后的组逐字节一致,`0x0071` 没有任何写者。** 那部分可以放心。

两条要改的:

| # | 是什么 | 严重度 |
|---|---|---|
| 1 | `firmware.c` 的**文件头又一次和代码对不上** —— 这次是漏了两个字段,而它就贴在"文件头描述另一个程序比没有文件头更糟"那段话上面 | 低,但**是同一个文件里同一种失效的第二次** |
| 2 | `M4-README.md` 第八节把缺的东西说错了:它说本机缺"**服务内可以重新开中断**"这个概念,**而那个概念本机有** | 中:会让人去找一个已经实现的东西 |

## 一、要处理的两条

### 1(低,但形状重要)。文件头漏了两个字段

`firmware.c` 的文件头说这个文件打破 who-writes-what 规则**两次**,第二次是:

> The second is the video half of the area -- **mode, columns, page stride, active page, cursor.**

而函数体写的是**七个字段组**:mode、columns、page stride、active page、cursor shape、**rows(`0x84`)**、**video control(`0x87`)**、以及八个光标位置。**漏掉的是最后加的那两个。**

**这就是那段头文件自己在骂的事。** 就在这半句往上一段,写着:

> A header that describes a different program from the one underneath it is worse than no header, because it is read instead of the code.

上一次的失效形态是"函数体加了例外、头文件没回头改";这一次是"函数体又加了两个字段、头文件那句列举没跟着长"。**同一个文件、同一种失效、第二次。**

**影响**:一个拿文件头审"谁写什么"的人(协调方自己说,我上一轮的结论就是从文件头读出来的)会以为 `0x84`/`0x87` 不在这个文件写的范围内。

**建议**:把列举改成**不列举**的写法 —— "this file writes the display half as POST would" —— 因为每一次加字段都要回头数一遍的句子,第五次一定还会漏。或者如果保留列举,把它和代码放在同一屏里,让它改起来扎眼。

### 2(中)。README 第八节把缺的东西说错了

原文(还在树上):

> 真机 BIOS 做这个 `STI` 是有意的,而本机缺的是"**服务内可以重新开中断**"这个概念本身 —— 那要等中断投递和服务的边界重新划过之后才有地方放它。

**"服务内可以重新开中断"这个概念本机有。** `vm86_service_retry()` 就是干这个的:它设 `IF`,并把 IP 回卷到桩,让运行循环在**下一个边界**投递。C 的阻塞键盘读(`bios16_service` AH=00h)**依赖**它才能结束 —— 那是一条跑通了、有端到端用例的路径。

**真正缺的是"可抢占":** 一次 `vm86_step` 内部跑完才回到运行循环,而投递只发生在步与步之间。**所以服务在自己的代码里把 `IF` 打开也没用** —— 没有边界可以插进来。retry 之所以work,是因为它**返回**了,不是因为它当场被打断了。

**为什么值得改**:这句话会让人去找一个**已经实现**的东西。缺口的候选修法里会出现"给服务加一个能开中断的机制"——而那个机制在树里、有测试、且不能解决这里的问题。**而这句话的后半句("等中断投递和服务的边界重新划过")指的恰好是对的东西** —— 所以这条只需改前半句。

**建议**:

> 本机缺的是**服务可以被中断**(可抢占)。服务在一次 `vm86_step` 内部跑完,投递只发生在步与步之间,所以服务里打开 `IF` 也不会当场生效 —— `vm86_service_retry()` 之所以能等,是因为它**返回**给运行循环,让下一个边界去投递。

## 二、查过、没问题的

### 三个字段的值

- **`0x84` = 24** ✓ 行数**减一**。写 25 的机器会声称 26 行,留 0 的机器声称 1 行 —— 两个方向都在用例里钉住了(第二个方向由"1 行"这个说法单独值一提:协调方在代码注释里已经写了"a machine that leaves it at zero is a machine with one row")。
- **`0x87` = 0** ✓ bit 7 **是反着理解的**:清零意味着模式设置**会**清屏。代码注释("Modes do clear memory here, which is what bit 7 clear means")和 RBIL 的"do not clear RAM on mode set"对上了。
- **`0x71` 不种** ✓ 而且 **grep 全树确认没有任何写者** —— 这正是要的状态。`vm86_install_firmware` 不写它,`bios10` 的 `sync_bda` 也不写它。用例 `nothing seeds the Ctrl-Break flag` 会在有人开始写的时候红。

### 上电组 vs 第一次 `INT 10h` 之后:**逐字节一致**

逐字段对过 `vm86_install_firmware()` 与 `bios10.c` 的 `sync_bda()`:

| 字段 | install 写 | 服务(刚 reset 后)写 |
|---|---|---|
| mode | 3 | 3 |
| columns | `VM86_TEXT_COLUMNS` = 80 | 80 |
| page stride | `VM86_TEXT_PAGE_STRIDE` = **0x1000** | 4096 |
| active page | 0 | 0 |
| cursor shape | 0x0607 | 0x0607 |
| 八个光标 | 0 | 0 |
| rows | 24 | 24 |
| video control | 0 | 0 |

**是同一个答案,不是"被改成了另一个东西"** ✓

- 两个写者写的**字节集合也相同**(都是 `0x49,0x4A,0x4C,0x50–0x5F,0x60,0x62,0x84,0x87` 共 26 字节),没有一边多写、一边少写的字段。
- **用例 `the firmware seeds what the service would`** 是逐**字节**比较整个显示区(`0x49`–`0x62`),不是逐字段 —— 这样"一边加了字段、另一边没加"会落在它上面,而不是要等有人记得去补一条断言。它还顺带覆盖了 `0x4E`/`0x4F`:**两个写者都不碰那两个字节**,如果有一个开始了,这条会红。
- **变异验证**:把 install 的展开写成 `VM86_TEXT_PAGE_BYTES`(4000,那个"看起来对"的数)而不是 `VM86_TEXT_PAGE_STRIDE`(4096)→ **这条用例红** ✓。这正是它存在的理由:两个写者分歧的时候,它必须红。

### 文件头的其余部分

- "两次例外"的论证成立:设备字与内存大小**没有归属服务**(写得对,那是 INT 11h/12h 背后的值);视频字段**的 reset() 没有 CPU**,所以到第一次 `INT 10h` 之前没人发布 ✓
- "the first INT 10h overwrites every byte here with the same values or with better ones" ✓ —— 上面那张表就是这句话的证明
- 时钟计数与键盘队列**不在这里写** ✓ 它们有能写的复位 ✓

### README 第八节的另一条(键盘)措辞**准确**

三个组成部分我都核了:
- `SYS_GETKEY` 走 `kbd_getchar()` ✓(`kernel/console/kbd.c:259`,`SYS_GETKEY` 的处理在 `kernel/proc/syscall.c:269`),它确实会 `hlt` 等键 ✓
- 非阻塞的 `kbd_poll()` **存在**(`kbd.c:249`),且**没有系统调用出口** ✓
- 第三条(核心交出的是译好的键码,不是 set-1 原始扫描码)与 `kbd.c` 的实现一致,而 `key.asm` 只跑宿主套件 ✓

**这一条不需要改。**

## 三、变异测试

**7 个变异,全部被捕获**,在 `/var/tmp` 的副本上做,基线先验。

| 注入的错误 | 被哪些用例抓住 |
|---|---|
| 行数写成 rows(25)而不是 rows−1 | `install_firmware seeds the last row and the control byte` |
| 控制字节种成 `0x80` | 同上 |
| 固件顺手种了 Ctrl-Break 标志 | 2 条(含专门那条) |
| **页步长种成 4000 而不是 4096** | `install_firmware seeds a coherent display`、**`the firmware seeds what the service would`** |
| 固件不再种八个光标位置 | `install_firmware writes the table and the machine description`(它预先用 `0xA5` 填满内存,所以"少写一个字节"表现为该字节没变) |
| 服务不再发布行数 | `the BIOS data area is kept in step` |
| 服务不再发布控制字节 | `0Fh hands back the control bit with the mode` |

**第 4 行是这一轮的要点**:它证明那条跨模块一致性用例在**两个写者分歧**时真的会红,而不是一条"两边都从零开始所以恒过"的断言。

**顺带修掉我自己的一处弱断言**:`the BIOS data area is kept in step` 原来直接断言 `0x87 == 0` —— 而新机器上那个字节本来**就是** 0,所以"服务不再写它"抓不住。改法是**先把这个区涂成 `0xFF` 再叫服务发布一次**:这样每条断言都变成"这个字节必须被改过才能过"。(这条正是我这一轮学到的那个形状,又用到了一次。)

## 四、为什么没有另开一个套件

协调方要的是报告,没指定套件。**用例加进了两个已有的套件**,因为 `install_firmware` 的用例本来就在 `test_intr_audit.c` 里(它是中断核心的一部分:同一个函数装表、装桩、发布机器自述),而"两个写者是否一致"必须在能同时看到两边的文件里才写得出 —— 那是 `test_bios10.c`。

于是:
- `test_intr_audit.c` +3:行数与控制字节、`0x71` 无写者。
- `test_bios10.c` +1:上电组 == 服务组(逐字节)。

**没有为这三条另开文件**,因为那会让同一个函数被两个套件测,而它们迟早会分歧。

## 五、没覆盖的(记下来,不是缺陷)

- **`0040:004E`(真机的 CRT 起始地址 / 页偏移)不在图里、没有写者。** 真 BIOS 维护它(它记录当前显示页在显存里的偏移)。本机不维护 —— 这是**一条 stated gap**。
  **我故意没有为它写断言**:钉住"不写"会把一个缺口固化成规格,而它将来是要补的。
- **`0040:0085`(字符高度,字)同理**:RBIL 有,本机没有图形模式,所以没有字符高度可言。
- 两条都只在这份报告的正文里,不在代码或 README 里 —— **如果它们要有家,应该是有归属的那一份文档,而不是我的报告。**
