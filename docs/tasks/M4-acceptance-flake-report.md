## 一、timer 用例的**上界**是暴露给调度的那一个 —— **真机制,这次没咬**

**读出来的事实:**

- 那条断言是 `g_ms_advanced ∈ [274, 340]`(`vm.c` 第 1272–1273、1361 行)。
- **下界是结构性的**:`bios1a_advance()` 拿到的是**真实毫秒**,客人数到第 5 个 tick 之前不可能有 274.6 ms 的钟走过。所以下界不会假红。
- **上界不是结构性的**:它的余量是 **340 − 274.6 ≈ 65 ms**,而 `g_ms_advanced` 累加的是 `u_uptime_ms()` 的真实差值。同一份代码的注释里写着"**QEMU does not schedule this process on time**",并且记录过同一条 275 ms 的钟对应 **370–450 ms 的墙钟**。
- 也就是说:**这个进程只要被连续吊起 ~65 ms 以上,上界就红,而客人是对的、tick 数也是对的。**

**判别方法(已经在现有输出里,只是分不出来):**

失败时看那行

```
  clock  : 5 ticks out of <M> ms of real time
```

——那是**通过**分支打的。而失败分支打的是 `%u ticks came out of %u ms handed to the clock`。两者不同一,所以现在的输出形态是:

| 现象 | 结论 |
|---|---|
| `M > 340` **而** tick 数 = 5 | **上界红了**,客人是对的,机器被吊了 |
| tick 数 ≠ 5 | 客人真的少跑了(和时钟/中断投递有关) |
| `274 ≤ M ≤ 340` 而用例仍红 | **不是这一条**,问题在别处(例如 page 那几项) |

**建议(一行改动,收益很大):** 把上表的判别**写进失败信息本身**,例如在上界失败时同时打印 tick 数与"这是一次调度超时,不是客人的错"的判据。**两种失败现在同名(`timer: FAIL`),而它们指向完全不同的地方。**

**不建议**放松上界去"修"它——余量是一个 tick,是这件事的物理量;该做的是**让红的时候能读出红的是哪一半**。

## 二、跑脚本可能在落盘之前就 `kill` —— **不是机制。(我提过它,查完判掉。)**

**我原来的说法**:`run-vm-test.sh` 的循环一 `grep` 到 `nothing left to run` 就 `kill`,若标记行和它前面的断言不在同一次落盘里,`expect_present` 会对已经通过的用例报 missing。

**判掉它的两步(都查过):**

1. **标记打在输出的最后。** `kernel/main.c:664` 那行 `kprintf("\nThe kernel has nothing left to run, so it idles here.\n")` 在**进程退出循环之后**、进 `for(;;) hlt` 之前 —— 也就是客人的全部输出之后。
2. **控制台没有内核侧缓冲。** `kputc` → `console_backend_putc` → `serial_putc`,而 `serial_putc`(`kernel/console/serial.c:60`)是**直写 UART**:轮询 `UART_LSR_THRE` 然后 `outb(COM1_BASE + UART_DATA, ...)`。**没有环形缓冲、没有延迟刷。**

单一顺序写者 + 标记在末尾 ⇒ **看见标记就意味着它前面的每一个字节都已经写出去了**。QEMU 的 `-serial file:` 那层 stdio 缓冲也是顺序刷的,而标记之后内核不再打印任何东西 —— 所以没有"标记已落盘、断言还没"的窗口。

**这一条仍然值得留在文件里,因为它有一个前提**,而前提变了它就会重新变成机制:

> **只要控制台是"同步、顺序、单写者",标记就一直是可靠的输出围栏。**
> 将来内核要是给控制台加了缓冲(环形缓冲 + 中断驱动发送很常见),或者把标记挪到别的时刻打,这一条就要**重新判一次**。
