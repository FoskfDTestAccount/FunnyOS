## 一、【承重发现】服务无法把 CF / ZF 还给 guest

### 事实

`INT 13h` 用**进位标志**报错(`docs/dos-refs.md` 第四节),`INT 16h AH=01h` 用 **ZF** 报"没有键"
(第五节)。而在这个冻结接口里,**宿主服务没有任何通道把标志位还给 guest**。

原因:桩是 `FE 38 <向量> CF`,那条 `CF` 是 **guest 自己执行的 IRET**。IRET 从栈上弹 FLAGS,
而栈上那份 FLAGS 是 guest 的 `INT` 压进去的。服务里写 `cpu->flags` 会被这条 IRET **盖掉**。
`host.h` 又明确写着服务"**不得碰中断帧**",所以服务也不能去改那份保存的 FLAGS。

### 这是量出来的,不是推出来的

`dos/intr/trap.c` 的 `vm86_host_trap()` 在服务返回后**没有**把 `cpu->flags` 写回帧,我读过它。
在此之上我做了一个探针(一次性代码,不在树里):

```
guest:  clc / int 20h / jc +2 / hlt / hlt
        IVT[20h] -> 0x300
A  handler = 一条裸 IRET,C 代码在帧还在栈上时设 cpu->flags |= CF   -> guest 没看到 CF
B  handler 是 guest 代码,自己去改栈上那份 FLAGS                    -> guest 看到了 CF
C  对照,没人设 CF                                                  -> guest 没看到 CF
```

结论精确地说:**机制在这台机器里是存在的(guest 代码改帧就能回传),但宿主服务够不到它。**

### 用一个真实的 INT 13h 实现再确认一次

我在验证台里写了一个**完全按规范做**的假 `bios13`(失败时 `vm86_flag_set(cpu, VM86_CF, true)`
且 `cpu->ah = 错误码`)。跑 `disk.asm` 的结果:

```
--  disk: the sample printed FAIL ...
```

而**缓冲区里的数据是对的** —— 扇区真的读进来了(`0000:0600 = 4D 34 0D 0A`)。也就是说:
**数据通路是通的,只有"报告"这条通道不通。** 这正是这一条最危险的地方:一个只在 AH 里报错的
实现会让"读成功"的程序拿到一个没被填过的缓冲区,而调用方从 CF=0 判断它成功了。

### 两条修法(都在别人文件里,我没动)

**(A) 推荐:`vm86_host_trap()` 在服务返回后把 `cpu->flags` 合并回帧。**

```
frame_flags = (cpu->flags & ~(IF|TF)) | (frame_flags & (IF|TF))
```

- 服务没碰标志位时,这个式子**恒等于**原值(因为服务入口处 `cpu->flags` 就是帧值清掉 IF/TF),
  所以对现有服务是**零影响**;
- IF/TF 从帧里取,所以 IRET 仍然还原调用者的中断状态,`sti` 的语义不变;
- 之后服务只要 `cpu->flags |= CF` 就能报 CF,09h/0Eh 那一类不受影响。

**已知代价,必须一起写下来:** 陷阱分辨不出自己是被 `INT n` 叫来的还是被 TSR 用 `jmp far`
链过来的。真机的 BIOS 处理程序也**同样假设栈上有一个中断帧**(它们也改那份 FLAGS),
所以这个假设是符合真机的;但要在 `host.h` 里把契约写成"**栈上有一个中断帧**",
而不是现在这句"不得碰帧"。链式调用**正确的写法**是 `pushf; call far 旧向量`,那样帧的形状是对的。

**(B) 更窄:加一个 `vm86_service_return_flags(cpu)`,由需要它的服务显式调用。**

同样的帧假设,但不改所有服务的行为。13h 和 16h/01h 各调一次。

### 现在怎么办

`disk.asm` **按规范写**,所以它现在会印 FAIL,`bios programs` 套件会红一条。
**我没有把它改成只查 AH** —— 任务书第四节明说那样写是错的,而且那会把整条缺口藏起来。
失败的文案里直接写了原因和指向本文的一段,免得下一个人去查磁盘。

顺带:`INT 16h AH=01h` 的 ZF 是**同一个缺口**。语料里没有任何程序用 01h,所以它现在不红,
但 C 的套件测不到它 —— 因为 C 的服务同样回不去。

## 四、用例能红吗:变异测试

按项目的规矩,每条用例都要证明它能失败。我在验证台上把**别人的实现**故意改错
(只在 /var/tmp 的副本里),看我的断言是否报红:

| 注入的错误 | 谁报红 | 结果 |
|---|---|---|
| 页步长 `4096` → `4000` | `cursor` | ✅ 抓到 |
| 模式设置把整屏填成 `0x00` 而不是空格 | `hello/direct` + `cursor` | ✅ 抓到 |
| `06h` 滚动填入 `0x00` 而不是空格 | `scroll` | ✅ 抓到 |
| **`0Eh` 改写 BL 而不保留原属性**(即撤销那条勘误) | `scroll` | ✅ 抓到 |

最后一条最要紧:它证明**勘误是真的被测着的** —— 一个"用 BL"的实现会在
`scroll` 的 row 22 上留下 `0x0F` 而不是 `0x07`,而其它所有断言照样绿。

**第二轮(对着真正的 B/C/D 跑),四个变异全部再次被抓到**,同一条还包括
`disk`:它**也**变红了。查下去发现那**一半是运气**:`disk.asm` 在序言里设 `bl = 0x07`,
然后被 `mov bx, [say_text]` 冲掉 —— 它当时留下的 BL 值是一个文本指针的低字节。
也就是说那条用例在测勘误,但**没有任何一行代码表达这个意图**,谁"顺手整理"一下就会
把这份覆盖悄悄删掉。已经改成故意的:页号和颜色在指针装进 BX **之后**、调用**之前**放进去,
颜色用 `0x0F`(单元上没有的值),期望值不变还是 `0x07`。

## 五、【发现】上电时视频状态没有主,模式设置是必需的

B 的 `bios10_reset(st)` 只重置状态结构、**不碰 guest 内存**(它拿不到 cpu);
A 的 `vm86_install_firmware(cpu)` 只写设备字和内存大小两个字段。
**所以没有任何人在上电时清屏或写 `0040:0049/004A/004C/0062`。** 而 `vm86_mem_clear()`
把 guest 内存清零,于是屏幕上每个单元的属性是 `0x00` —— **黑底黑字**。

后果很具体:一个不设模式就直接 `0Eh` 打字的程序,**字符确实写进了内存,但没人看得见**,
而所有只看内存的断言都会绿。这是协调方在消息里点出过的那个坑。

**我的处理:语料里需要输出的程序都先设模式**(`mov ax,0003h` / `int 10h`),
`hello`/`cursor`/`timer`/`key`/`disk` 五个都加了。理由:

- 这是真实 .COM 的样子;
- 它让**验收程序自己就够用** —— `make test-vm` 不需要额外记得"先空跑一次模式设置",
  而 M4 的验收句子是"一个 .COM 打出了东西",不是"宿主做了准备之后一个 .COM 打出了东西";
- 顺带测了 `00h`。

`scroll.asm` **不设模式**,因为它自己把整屏(含属性)写满 —— 那正是它的主张:
屏幕就是内存,一个自己填屏的程序没什么要向固件要的。

**剩下的问题(要协调方定):** 上电时 `0040:0049/004A/004C/0062` 归谁写?
现在它们是 0,任何在调 `INT 10h` **之前**直接读 BDA 的程序会读到 0。
按 M4-9 的说法"引导时的固定字段归机器复位",最自然的地方是 `vm86_install_firmware()`。

## 六、【发现】语料的入口约定和中断向量表**重叠**

入口约定(从 M3 冻结下来的)是:**镜像装在线性 `0x100`,CS = 0**。
而固件把 IVT 建在 `0x0000–0x03FF`。**两者重叠**:

- 固件必须在**程序之前**装 —— 否则 IVT 会把程序自己的头 768 字节盖掉。
  我第一版的 `vm86_bios_load()` 就是错的(先装程序再装固件),症状是"机器在执行向量表的字节"
  然后 fault。已经改成先装固件。
- 反过来说:**语料程序的镜像会盖掉 IVT 第 64 号往后的表项**,因为程序就装在 `0x100`。
  这是约定本身的性质,不是谁写错了。本轮的语料只用 8/9/10h/13h/16h/1Ah/1Ch,
  **全在 64 以下**,所以它们不被盖到 —— 但这是**碰巧安全**。
- 真 DOS 没有这个问题,因为 `.COM` 装在**自己的段**里(PSP 在 CS)。M5 加 PSP 时这条会自然消失。
  在那之前,语料里**不要挂 64 以上的向量**。

> **这条已经改掉了 —— 见第十四节之后那一节。** 语料现在给程序一个自己的段
> (`CS=DS=ES=SS=0x1000`),重叠在结构上不再可能。本节留着,因为它是那次改动的理由。

## 七、入口约定那处偏离(IF=0):核实过了,而且有后果

任务书第二节写着:**约定给的是 `IF=0`,真 DOS 给的是 `IF=1`**。我在语料里的处理:

- `hello`/`direct`/`cursor`/`scroll`/`disk` **不用中断,也不开**;
- `timer`/`key` **第一条有效指令就是 `sti`**,并且文件顶上写明了为什么。

**核实结论:偏离是真的,而且是有后果的那一种,不是形式上的。**
在验证台上 `task` 那两条的 `sti` 是**必需的**:拿掉它,`hlt` 会变成真停机、重试永远等不到中断,
表现是"程序卡住不动"而不是报错。`key.asm` 的文件头把这一点写成了"忘了它不是装饰,是致命的"。

## 八、键盘那条路:查过了,答案是"内核有,但没开给用户态"

任务书第三节要求先查 `libu` 和内核给了什么系统调用、再决定做不做。**查完了。**

**内核里有什么:**

- `kernel/include/funnyos/kbd.h` 里有**两个**入口,而这正是问题的所在:
  - `kbd_poll()` —— "Next key, or KEY_NONE when nothing is waiting." **非阻塞。**
  - `kbd_getchar()` —— "blocking with hlt until one arrives",只有中断关着的时候才返回
    `KEY_NONE`。
- 系统调用表里只有一个:`SYS_GETKEY = 6`,`kernel/proc/syscall.c:269` 是
  `return kbd_getchar();` —— **走的是阻塞那个**。

**所以答案是:缺的不是"一个键的接口",是一个"看一眼"的接口。**

vm.c 的循环必须在**每个切片之间**回来看一眼键盘,不能停在那里等 —— 一个阻塞的
`SYS_GETKEY` 会让 guest 永远不再运行(宿主的循环卡在 `hlt` 里,而 guest 的时钟、
屏幕刷新、磁盘全都在那后面)。这正好是任务书要我写清楚的那种东西:

> **缺的是 `SYS_POLLKEY`(或给 `SYS_GETKEY` 加一个标志),它返回 `kbd_poll()` 的结果,
> 用一个哨兵值表示"没有键"。** 内核那一侧已经有了,只是没有出口。

半行就能写出来,但它**在 `g_current`/`process_run` 那条线上**,而任务书明说
**M4 不要为了键盘去改内核**。所以按任务书的第二条路走:`key.asm` 只在宿主套件里跑,
上面这段写进报告给 M5 之前的人。**M4 的验收只要求输出,这条不影响验收。**

**中间那次转换在哪(任务书要我问的):**

`kbd_decode()` 产出的是 FunnyOS 自己的 `KEY_*` 码(方向键那些大于 `0xFF`),
而 `bios16_key_arrived(st, scancode)` 收的是**扫描码**。所以顺序是:

```
8042(Set 2)→ kbd_decode → KEY_* →【宿主:KEY_* → Set 1 扫描码】→
    bios16_key_arrived → INT 09h 服务 → 队列里的 ASCII + 扫描码
```

**那张 `KEY_*` → Set 1 的表在宿主这一侧**(也就是第二段的 `user/vm/`),
不在内核里,也不在 C 的模块里 —— C 的模块只认扫描码。这是接上键盘时唯一要新写的东西。

**`timer` 那条路顺带也查到了:** `SYS_UPTIME_MS = 7` → `timer_millis()`,单调、不回绕的毫秒钟。
第二段拿它做差分喂 `bios1a_advance(&clock, 经过的毫秒)` 就行,任务书要的那个
"guest 数到的滴答和墙上时间对得上"的断言因此是**写得出来**的。

**`make test-vm` 的串口链:存在,不用新修。**

`tools/run-vm-test.sh` 已经在**抓串口日志做断言**(`expect_present`),而它生成的
`limine.conf` 里有 `serial: yes`。所以链路是:
显示后端画到控制台 → 控制台镜像到串口 → 脚本 grep。

**M4 的断言因此可以落在"那行字出现在日志里",不是退出码。** 现在脚本里那十条断言全是
M3 那两个硬编码 guest 的,第二段要加的是 `expect_present "M4 hello from the BIOS"` 一条,
以及把"解释器跑的是 `.COM`"这件事也断进去。

## 九、切片怎么选的

`struct vm86_bios_plan` 有三个旋钮,取值和理由:

| 旋钮 | 取值 | 为什么 |
|---|---|---|
| `steps_per_slice` | 2000(多数)、200(key) | 一个切片要长到能做完一段有意义的活,短到宿主能及时拿回控制权去推时钟/喂键盘。`scroll.asm` 的填屏循环要 4000+ 条指令,2000 让它两三个切片跑完;`key.asm` 用 200,因为它的"等待"就是重复重放陷阱,切片越短观察窗口越细 |
| `slices` | 400(多数)、60(timer)、5+20(key) | 这是**背靠步数上限**,不是节奏。跑飞的 guest 必须被报成"没结束"(`VM86_BIOS_UNFINISHED`),而不是让套件挂住 |
| `ms_per_slice` | 55(timer)、0(其它) | **55 ms 是一个刻意的数字**:18.2 Hz 一个滴答是 54.925 ms,所以每个切片正好产出一个滴答,`timer.asm` 数到 5 就是确定性的。取 54 会在第 5 次上丢一个刻度,取 60 会在第 9 次上多一个 |

**第二段(FunnyOS)的切片要小得多**:那里有真实屏幕刷新和键盘轮询,
几百条指令量级才够响应。宿主套件里没必要那么小,因为"设备"都由计划驱动、不看墙上时间。

## 十一、这三件事后来都签了字

1. **CF/ZF 缺口**:按本文推荐的修法 (A) 进的主干 —— `vm86_host_trap()` 在服务返回后把
   `cpu->flags` 合并回帧,IF/TF 从帧取。协调方用一个按 CF 分支的 guest 端到端量过
   (修前 guest 走"没有进位"那条,修后走另一条)。`disk.asm` 随之转绿,**程序一个字节没动**;
   `host.h` 那句"服务不能碰帧"改写成"帧是返回状态,服务通过 `cpu->flags` 改它"。
2. **上电的视频状态**:放进 `vm86_install_firmware()`,作为"机器复位"的**第二处有意的例外**
   (理由是"真机的 POST 就是干这个的")。`0040:0049/004A/004C` 现在读出来是 `03 / 0050 / 1000`。
   B 独立报了同一条。
3. **`VM86_ATTR_DEFAULT` 的注释**:已改,并注明"这一行是那次更正漏下的"。

**还欠着的一件**是键盘(第八节):内核交出的是译好的键码,所以缺的不是"一个非阻塞出口"
而是"原始的扫描码",两条出路都已记进 `M4-README.md` 第八节。它不影响 M4 的验收。

## 十四、第二段:它现在跑在 FunnyOS 里

**`make test-vm` 全绿,17 条断言,其中四条是 M4 的:**

```
  [ok]   the guest's line reached the screen
  [ok]   the page hello.asm left is the one expected
  [ok]   the same text with no interrupt at all
  [ok]   five ticks of a real clock, counted by the guest
```

### 接了哪些线

`user/vm/vm.c` 现在做两件事,不是一个:

1. **M3 那两个裸处理器的用例原样保留** —— 一个字节没删、没改。
2. **新增 `[8086 machine]` 一段**:装固件 → 装四个服务 → 装 .COM → 切片循环 → 断言屏幕。

循环的形状就是任务书第 6 步那几行:

```
  stop = vm86_run(&cpu, VM_SLICE_STEPS);     /* 250 条指令一个切片 */
  if (guest 真的执行了) 重画屏幕
  if (stop == HALT && IF == 0) break;        /* cli; hlt,终结 */
  把真的过去的毫秒交给 bios1a_advance(),它给回几个滴答就 raise 几次
```

"guest 真的执行了"用 `cpu.insn_count` 判断,不是猜哪个 stop 码意味着它跑过。一个停着的
CPU 不可能写过显存,而这个循环绝大多数时间都停在 `hlt` 上等滴答 —— 每一次都去比 4000 字节
的帧,差别就是"一台计时的机器"和"一台把时间花在看没变的屏幕上的机器"。

### 屏幕后端

**光标不画。** guest 的光标是一个单元索引,而这个控制台没有寻址,所以这个后端只显示文字
——`display.h` 把光标画成什么样交给宿主,这个宿主没地方放。`VM86_DISPLAY_NO_CURSOR` 因此
不需要分支。

**只在整帧变了的时候重画。** 不是逐单元差分(那会引入自己的 bug),是**整屏 memcmp** ——
所以它和"每次整屏重画"是同一件事,只是跳过了不变的那些。任务书说"如果做差分,要有一个用例
证明它和整屏重画的结果一样":这里比较的就是完整的 4000 字节,所以那句话在构造上成立,
不需要另一个用例。

### 时钟那条断言

任务书要求"guest 数到的滴答数和宿主实际经过的时间在容差之内"。做法是跑 **`timer.asm`**
(数 5 个滴答并把数字打出来),断言三件事:屏幕上是 `'5'`;`0040:006C` == 5(firmware 自己的
计数,直接读数据区);以及**宿主交给 `bios1a_advance()` 的毫秒总数 ∈ [274, 320]**。

下限 274 ms 是承重的那个:5 × 54.925。**一个"每个切片发一个滴答"的宿主要在微秒级跑完,
会撞在它上面。** 实测:`clock : 5 ticks out of 280 ms of real time`。

**容差为什么是这个形状,值得写下来。** 我第一版断言的是**包住整个循环的墙上时间**,
那一版**失败过**:一次 370 ms、一次 450 ms,同样 275 ms 的时钟。原因是 `u_uptime_ms()`
是 10 ms 量化、而 QEMU 不按点调度这个进程。所以断言落在**循环内部累加的那个数**上 —— 它是
宿主自己的、来自内核毫秒计数器的、真的过去的时间,而且不是从时钟的输出推出来的,所以
"五个滴答花了 275 ms"是关于**速率**的陈述而不是套套逻辑。墙上时间只留一个 2 秒的挂死检测,
注释里写明了为什么它只能当挂死检测。

**还有一次,是预算本身错了,而且这一条更值得记。** 验收测试曾经**三次里红一次**,
而失败的那几次**并不慢**(同样两秒),只是 timer 那条报**四个**滴答、交给时钟的时间
**270 ms** —— 比五个滴答需要的 275 ms 少,所以 guest 还差一个滴答时宿主就放弃了。

原因是**预算按"轮数"给**。但一个等滴答的 guest 等的是**墙上时间**,而一轮值多少墙上时间
取决于机器:两百万轮在这台机器上是 270 ms,比这条用例需要的还少;换台快的会更少。
**一个每台机器含义都不同的上限不是上限,是抛硬币** —— 而它是这个套件里唯一会自己红的东西。

改成**按毫秒**:五秒真实时间(需要的十七倍),在本来就每 512 轮读一次时钟的地方检查,
轮数只留作"时钟再也不前进"的兜底。**承重的那条断言没变**:一个"每轮发一个滴答"的宿主会在
微秒级跑完,撞在下限 274 ms 上。

顺带两件:

- **脚本改成"内核说跑完了就停",不是"耗满预算"。** 程序退出后内核空转,QEMU 永远不会自己
  停,所以旧的 `timeout` 每次都要耗满 —— 这让结果看起来像在和预算赛跑。它不是,但读起来是,
  而且**正是"一次通过只要两秒"这件事让那个四滴答的失败变得可查**。
- **包住用例的墙上时间只打印、不再断言**(370/450 ms 那两次就是它)。

改完连跑 10 次全过。

### 键盘:按计划没接

`key.asm` **不在**用户镜像里,只有宿主套件跑它。原因见第八节,而且协调方往下多查了一层:
内核交的是**译好的键码**而不是扫描码,所以只加一个非阻塞出口也是半个修法(方向键那类
"没有 ASCII"的键要靠 `AH` 里的扫描码)。

| 文件 | 改了什么 |
|---|---|
| `user/vm/vm.c` | 机器、屏幕后端、切片循环、三个用例 |
| `user/vm/corpus.h` | 新增:三个语料程序的声明 |

`dos/Makefile` 一个字都没动(那两条语料规则是协调方加的),`user/vm/vm.c` 里 M3 的自检

## 十五、语料约定改成"程序有自己的段":从碰巧安全到结构上安全

第六节报的那件事——**程序装在**线性 `0x100`、`CS = 0`,而中断向量表在 `0x0000–0x03FF`
——现在改掉了。改法是**给程序一个自己的段**,和真 `.COM` 一样:

```
CS = DS = ES = SS = 0x1000,  入口 1000:0100,  SP = 0xFFFE,  FLAGS = 0xF002
```

理由写在 `dos/corpus/bios/replay.h` 里(协调方要求的),这里说清楚**为什么四个段都改、
为什么 `0x1000`、以及为什么这件事值得写下来**。

### 之前为什么能跑

**碰巧。** 三个独立的巧合叠在一起:

1. 七个程序用的向量全在 `0x1C` 以下,而镜像只有一两百字节——它只盖到第 64 号往后的表项;
2. 固件装在程序**之前**,所以程序自己的字节是安全的(反过来的话,IVT 会把程序的头 768 字节
   盖掉,症状是机器去执行向量表的字节);
3. 没有任何程序去挂钩一个高向量。

B 独立补了后果:**挂钩 `0x60` 以上向量的程序会被自己的代码覆盖**,而 `0x60` 以上正是 TSR
私有 API 的惯用位置。D 的第一版**正是被这条咬过**——症状指向运行循环而不是装载地址。

**"我们没被咬"不是"这条路是通的"。** 三个巧合里任何一个变了(多挂一个向量、镜像长一点、
装载顺序调一下),症状都会出现在离原因很远的地方。

### 现在为什么不会

程序的镜像在 `0x10100` 起,向量表在 `0x000–0x3FF`,两者**结构上**不相交。

**四个段都改,不只 CS。** 程序的数据和栈也在镜像里:`mov si, message` 配 `DS = 0` 读到的是
向量表而不是程序。真 `.COM` 拿到的就是 CS=DS=ES=SS= PSP,所以这里照做。

**`0x1000` 是选择不是事实。** 任何能让镜像离开表、又给栈留出位置的段都行;`0x1000` 给出
线性 `0x10000` 起的一个 64 KiB 块、栈在 `0x1FFFE`、样例自己的暂存在 `0x10800` 往上。

**程序里仍然绝对的地址,是真正绝对的**:向量表在 `0x0000`、数据区在段 `0x0040`、
显存在 `0xB8000`。它们显式带段——真机就是这么要求的。**只有一处要改代码**:
`timer.asm` 的 IVT 挂钩现在写成

```
        xor     ax, ax
        mov     es, ax
        mov     word [es:0x1C*4], tick
        mov     ax, cs
        mov     word [es:0x1C*4+2], ax
```

其余六个程序的**代码一个字没动**——它们只是从此运行在自己的段里,
而宿主套件读暂存地址时加上了段基(`VM86_BIOS_LOAD_LINEAR`)。

### 这条断言真的会红

新增一条用例 `vectors`:程序跑完之后,向量表第 64 号和第 128 号**必须仍指向固件装的桩**。

把段改回 `0` 跑一遍(`/var/tmp` 的副本,仓库没动):

```
      FAIL  vectors: entry 64 holds CD00:03B8, which is not the firmware's
            stub -- the program's image is lying on the vector table
  --  vectors
```

`CD00:03B8` 就是 `hello.asm` 的开头四个字节(`B8 03 00` = `mov ax,3`,`CD` = `int` 的首字节)
被当成一个远指针读出来。**而其余六条用例照样全绿** —— 这正好是"碰巧安全"的定义:
旧约定下,只有这条断言看得见问题,别的什么都看不出来。

### M5 继承它

装载器开始造 PSP 之后,程序会落在 `PSP:0x100`、四个段寄存器指向 PSP —— 那时这个约定
**自然成立,一行都不用改**。现在写下来比 M5 重新推一遍便宜。

### 改完之后

`cd dos && make test` 全绿(7 条用例 + 16 个套件);`make test-vm` 连跑 6 次全过,
每次 1–2 秒。

## 十六、C 的复核:验收测试没有读它声称读的那个屏幕

C 审 `make test-vm`,找到**一个不读 guest 显存的显示后端,20 条断言全绿**。
两条都真,两条都修了。

### 一、同一根指针,只有一半被验

`screen_present()` 拿到 guest 的活动页之后做了两件事:

- 拷进 `g_screen.frame` —— **所有断言看的是这个**;
- 交给 `draw_frame()` 去画 —— **没有任何断言看这个**。

于是 `the guest's line reached the screen` 只证明了"**有什么东西**打出了那个字符串":把
`draw_frame` 换成"不管 `cells` 是什么都打那行字",四条 M4 断言全过。

**修法**:后端**记下它真正画出来的行**,`check_drawn()` 拿这些行和 guest 的页比对——
而那页是**从内存里独立读出来的**,不是后端自己那份拷贝。一个"是 guest 显存的一张画"的屏幕,
必须能从 guest 的显存重算出来;没有读它的后端重算不出来。

### 二、整屏的声明,一行都不到

让"设置模式"只填第一行(`row < 1`)—— **也全绿**。2000 格里只查了 22 格,而
`hello.asm`/`direct.asm` 的**头注释里写的是整屏**。

**修法**:`check_page()` 查**整屏 2000 格**,按每个语料自己的头注释。顺带修了
`direct.asm` 头注释里那句现在已经不成立的话("the 4000-byte page identical to the one
hello.asm leaves")—— 模式设置落地之后两页在消息之外本来就不同,而头注释是最后还那么说的地方。

### 三、两条断言各自挡得住,而且只挡自己那一种

重新注入(在 `/var/tmp`,仓库没动):

```
===== baseline (unmutated) =====
====> 8086 interpreter test PASSED (bios)
===== injection 1: a backend that never reads video memory =====
  FAIL  hello: row 1 column 0 was drawn as 4D and the guest's memory holds 20
  FAIL  direct (M4-8): row 1 column 0 was drawn as 4D and the guest's memory holds 00
  FAIL  timer: row 0 column 0 was drawn as 4D and the guest's memory holds 35
===== injection 2: the mode set clears one row =====
  FAIL  hello: cell 80 is (00, 00), expected (20, 07)
  FAIL  timer: cell 80 is (00, 00), expected (20, 07)
```

**每一个注入只让为它写的那条断言报红**,另一个注入的那条完全不响。这比"都抓到了"更有用:
它说明两条断言各自在测不同的东西。

### 四、第一次注入验证是**假的**,原因值得记

我第一次跑这两条注入时,"两个都抓到了"。**那是跑在同一个旧二进制上的。**

验证脚本每次用 `tar` 从源树重新解出一份 —— 而 **tar 恢复的是文件的原始 mtime**,比上一份
构建出来的 `.o` 还**旧**,于是 `make` 判定无事可做,**两次跑的是同一个二进制**。
把两次的输出并排看才发现:injection 1 里出现了只有 injection 2 才会有的 `cell 80` 失败。

这条正是项目里已经记着的"变异实验一律用 `make -B`" —— 我记着它,但**换了个外壳的同一件事**
(不是"改完立刻 make",而是"重新解包了一份更旧的源")又踩了一次。现在脚本每次一个独立的
构建目录,并且 `make -B`。

**它也是"跑在旧二进制上的一次验证,看起来和一次有效验证一模一样"的具体例子** ——
结果值是两个 PASS/FAIL,而它们其实什么都没测。

### 五、顺带查出来的一个真的悬空指针

新断言**独立去读 guest 显存**,于是踩出了一个原来看不见的错:
`run_corpus()` 里的 `struct vm86_mem mem` 和 `struct vm86_cpu cpu` 是**局部变量**,
而它把 `cpu` 拷贝给调用方用 —— `cpu.mem` 指向一个已经失效的栈帧。
表现是 **Ring 3 的 #PF**,读在 guest RAM 下面 35 KiB 的地方。

旧断言读的是 `g_screen.frame`(一份拷贝),从不碰 `cpu->mem`,所以它一直没露出来。
**"把断言改成独立读内存"这件事本身,把这个 bug 挖了出来** —— 那是它该有的副作用。
机器现在放在文件作用域(`g_mem`/`g_cpu`),注释里写了它为什么不能待在栈上。

### 六、时钟下界的算术,写在断言旁边

C 另外指出:下界 274 是"**贴着可达读数**"的,不是留有设计余量。
`timer_millis()` 是 `g_ticks * 1000 / TIMER_HZ`,而 `TIMER_HZ = 100` → **读数只能是 10 的倍数**;
五个滴答要 274.627 ms,第一个可达的 ≥ 它的值是 **280**;而四个滴答读 **270**。
**274 夹在 270 和 280 之间** —— 它成立,但成立的原因是 274.627 不是 10 的倍数。

**这段算术现在写在 `VM_TICKS_MIN_MS` 旁边**(不是这里),因为**改 `TIMER_HZ` 的人只会读那里**。
注释里还写了它在什么情况下会失效:`TIMER_HZ` 降到 10 时读数是 100 的倍数,四个滴答就读 300,
这条下界就再也分不出四和五 —— 那时这些数得重算,而**这个文件不会告诉任何人**。

### 改完之后

`cd dos && make test` 全绿;`make test-vm` 连跑 3 次全过(每次 1–2 秒),
`clock : the firmware counted 5, the guest counted 5`。
