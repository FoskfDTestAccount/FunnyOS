## 二、陷阱

桩是四个字节,`FE 38 <向量> CF`。`vm86_host_trap()` 要做的是:

1. **读一个字节**——服务号。读的时候 IP 已经指在那个字节上(FE 组的处理器已经消费了 ModRM)。
2. **调用** `service[服务号]`(没注册就什么都不做)。
3. **返回 `VM86_CONTINUE`,IP 停在 `CF` 上。** 下一步执行的就是那条 IRET。

**这里最容易做错的是"顺手把中断帧弹掉"。** 不要弹。栈上的帧是 guest 的 `INT` 压的,或者是 TSR 链接过来之前压的,**只有 guest 自己的 IRET 知道怎么正确弹开它**。宿主服务只管做事,弹帧是那条 `CF` 的活。

**第二容易做错的是"服务返回后自己改 IP"。** 也不要。让 IP 自然停在 `CF` 上。

## 三、运行循环(`vm86_run`)

形状在 `host.h` 里写了,这里把**顺序**说死,因为顺序就是正确性:

```
循环:
  1. 影子(cpu->intr_shadow):
       非零 → 递减、跳过投递(但仍然执行下一条指令)
       为零 → 若 vm86_interruptible(),取**编号最小的**挂起向量,
              清挂起、清 halted、vm86_interrupt(),continue(不消耗预算)
  2. halted 且没有可投递的东西 → 返回 VM86_STOP_HALT
  3. 预算用完 → 返回 VM86_STOP_STEPS
  4. 记 cpu->insn_ip、vm86_step()、预算 +1
```

几点必须做对的:

- **投递中断不消耗预算。** 预算数的是"退休了几条指令",中断不是指令。
- **`HLT` 的返回不是立刻。** `vm86_step` 返回 `VM86_HALT` 之后**继续循环**,让第 1 步去决定是"有中断可以唤醒"还是"真的停下了"。`sti; hlt` 的唤醒路径全靠这个顺序:STI 置影子 → 下一个边界吃掉影子并执行 HLT → 再下一个边界投递并清 halted。**这个顺序错了,空闲循环会永久挂起。**
- **取编号最小的挂起向量**,不是随便取一个。真机上低向量优先级高。
- **异常的投递策略**(M4-README 的 M4-5):`vm86_step` 返回 `VM86_FAULT` 时,查 `vm86_vector_is_stub(cpu, cpu->fault)`。是 → 返回 `VM86_STOP_FAULT`(**`cpu->fault` 要留在那里**给调用方看);否 → `vm86_interrupt()` 投递给 guest 的处理程序,continue。
- `VM86_INTERNAL_ERROR` → 返回 `VM86_STOP_BROKEN`。
- **`steps == 0` 是合法的**:意思是"看看有没有什么该跑的,但一条指令都别执行"。这要求第 1 步在预算检查**之前**——把预算检查放在循环顶部就会连投递都跳过。

## 四、三条 M3 的欠账

M3 的 README 第五节末尾把这三条列成了"在 M3 里观察不到"。现在能观察到了。

### 1. `REP` 可中断(`dos/cpu/ops_str.c`)

真机在**每次迭代之间**识别中断。所以 `vm86_str_repeat()` 的循环里,在**每一次 body 跑完之后、下一轮开始之前**检查 `vm86_interruptible()`;要中断就:

```c
cpu->ip = cpu->insn_ip;   /* 回卷到第一个前缀之前 */
return VM86_CONTINUE;     /* 让运行循环去投递 */
```

**回卷必须回到 `insn_ip`。** 回卷到操作码之后会**静默地**把 `rep movsb` 变成 `movsb`——搬一个字节而不是一整个缓冲区,而且机器看起来在正常工作。这是这一条里唯一会让你在 M5 栽跟头的地方。

> **勘误(2026-10-01,由任务 A 提出后改):检查要放在"迭代之间",不是"每一轮的开始"。**
>
> 这份任务书原来写的是"每一轮的**开始**检查一次"。**那句话有两个问题。**
>
> 一是**它和自己后面那句矛盾**:同一节又说"回卷之后 `CX`/`SI`/`DI` 不回退,重放的是**剩下的**次数"。如果检查点在第一次迭代**之前**,而它在那里就命中了,那么一次都没搬过,重放的当然是**全部**——那条要钉住"不回退"的用例就什么都没证明。
>
> 二是**它问的是一个刚刚被回答过的问题**:运行循环**只在**投递不了的时候才走进这条指令,所以在第一次迭代之前再问一次 `vm86_interruptible()`,问的是运行循环在同一个边界上刚问过、而且答案是"不"的那件事。真机也不会在第一条之前识别——**第一个元素一定搬完**。
>
> 放到迭代之间之后,中断那一刻 `CX`/`SI`/`DI` 才必然和开头不同,那条用例才真的在测东西。**三条理由都由任务 A 给出并写进了它的报告。**

`vm86_str_repeat()` 的契约说它"总是返回 `VM86_CONTINUE`";仍然成立。

**顺带核对一件事:** 循环体每轮都改了 `CX`/`SI`/`DI`,回卷之后这些**不回退**——真机也不回退,重放的是剩下的次数。这一点要有一个用例钉住(比如 `rep movsb` 搬到一半被打断,处理程序 IRET 回来之后**剩下的字节被搬完**)。

### 2 和 3. `STI` 和写 `SS` 之后的那一条指令

同一个机制:`cpu->intr_shadow = 1`。

- `dos/cpu/ops_ctl.c` 的 `op_set_flag()`,`case 0xFB`(STI)。**那个 case 的注释里现在写着 "M4 OWES THE DELAY"** —— 就是这段,把它还掉,并且**把那段注释改写成现在的事实**。
- **`MOV SS, r/m16`**(`8E` 的 `/2`)—— 在 `dos/cpu/ops_mov.c` 的 `8E` 处理器里。
- **`POP SS`**(操作码 **`0x17`**)—— 在 **`dos/cpu/ops_alu.c` 的 `op_alu_block()`** 里。**两个入口在两个不同的文件。**

> **勘误(2026-10-01,由任务 A 核对操作码表后改):`POP SS` 不走 `8F`。**
>
> 这份任务书原来写着"`POP SS` 走的是 `8F` 的路径"。**那是错的。**
>
> - `8F /0` 是 **`POP r/m16`**,而它的 r/m 在 `mod=11` 时寻址的是 `AX/CX/DX/BX/SP/BP/SI/DI` —— **段寄存器不在其中**。所以 `8F` 永远写不到 `SS`。
> - `POP SS` 的编码是 **`0x17`**,落在 `0x00`–`0x3F` 那一段,归 `ops_alu.c` 的 `op_alu_block()`。
>
> 所以入口确实是**两个**(`8E /2` 和 `0x17`),只是第二个不在我写的地方。**这处错误的代价是"写 `SS` 抑制一条"会只做一半**,而那一半的症状是"大多数程序没事,少数程序在设置栈的时候被中断打进来看见半个栈"。
>
> 记下来的理由:`8F` 和段寄存器之间的联想很自然(旁边就是 `8C`/`8E` 的段寄存器传送),而我当时**靠联想写下了路径、没有去查操作码表**。这类"路径"断言和"某某已经是对的"一样承重,一样要查。

**被延迟的是"识别",不是 IF。** `STI` **立即**置 IF;被推迟的只是"这条指令之后紧接着的那一个边界上不投递"。**这个区分在 M3 里已经被写错过一次**,代价是两份任务书重写——注释里要写清楚。

## 六、坑清单

1. **`vm86_interrupt()` 的 IF 清除时机。** 现在的实现是"压 FLAGS → 压 CS → 压 IP → 清 IF/TF"。压进去的那份 FLAGS 带着调用者的 IF(所以 IRET 能还原),是**对的**。别改成先清后压。
2. **`INS`/`OUTS` 的 REP 循环和 `MOVS` 是同一个 `vm86_str_repeat()`。** 改一处两条都改到了,这是**要的**;但也意味着你的 REP 用例至少要有一条走 `IN`/`OUT` 的路径,否则"改坏了另一条"不会被发现。
3. **`vm86_step` 在开头清 `cpu->fault`。** 所以运行循环处理 `VM86_FAULT` 时要**当场**用 `cpu->fault`,不能等到下一轮。
4. **`intr_shadow` 是"还要过几个边界",不是布尔。** 递减的逻辑写在运行循环里;**没有别的地方递减它**。如果将来有人加了第二条递减路径,`STI` 的延迟就会变成两条指令或者零条,而且只在密集中断下看得出来。
5. **`vm86_install_ivt()` 写的是 guest 内存**,所以 `cpu->mem` 必须先挂上。`vm86_install_firmware()` 里也一样。
6. **`vm86_vector_is_stub()` 在 guest 把向量改回 `F000:(v*4)` 时会说"没被挂钩"。** 那是**对的**——它确实又指回我们的桩了。

## 七、测试要求

`dos/tests/test_intr.c`。至少覆盖:

- **陷阱的往返**:装一个服务,写一小段 `FE 38 <v> CF`,确认服务被调到、IP 停在 `CF`、IRET 之后回到 guest 的调用点、**栈完全复原**。
- **服务号**:两个不同的服务注册在不同向量上,确认 `FE 38 <v>` 打的是对应那个,不是"第一个注册的"。
- **未注册的向量**:一样走到桩上,什么都不做,IRET 之后 guest 继续跑。**不是**异常。
- **`intr_pending` 的位图语义**:同一个向量投两次 = 一次;两个不同向量都在,先投小的那个。
- **影子**:`STI` 之后那条指令的边界上不投递;`MOV SS` 之后同样;`POP SS` 之后同样。
- **`sti; hlt` 的唤醒**:挂一个中断在向量 8 上,跑 `sti; hlt`,确认**没有**返回 `VM86_STOP_HALT` 而是投递了。
- **`cli; hlt` 是终结**:确认返回 `VM86_STOP_HALT`。
- **异常的两种去向**:一个 `div` 除零,向量 0 还是桩 → `VM86_STOP_FAULT`;把 IVT[0] 改成 guest 自己的地址 → 投递给 guest 的处理程序。
- **`REP` 被打断**:见第四节。
- **预算**:`vm86_run(cpu, 0)` 一条指令都不执行,但仍然会投递挂起的中断。

**每条用例都要证明它能失败**:写完把实现**故意改错**(改一个比较方向、删掉一次递减、把回卷目标改成操作码之后),确认用例真的报红,再还原。M3 的经验是三处独立的变异活动**第一轮各自都抓到了永远不会红的用例**,那些用例比没有更糟。
