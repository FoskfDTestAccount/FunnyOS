## 一、范围:你和任务 F 不重叠

任务 F 正在验证**操作码处理器的语义**(算术、移位、标志位、十进制调整那类)。**那部分不是你的。**

你要验的是它底下的那一层 —— 每条指令都要经过、但没有任何一个操作码套件真正测过的东西:

| 文件 | 是什么 |
|---|---|
| `dos/mem/mem.c` | guest 内存模型:线性地址、未映射区域、浮空总线、A20 |
| `dos/cpu/decode.c` | ModRM 解码、有效地址计算、段基址解析、前缀 |
| `dos/cpu/step.c` | 取指、前缀循环、五张表合并成一张分发 |

这三个文件加起来决定了**每一条内存访问落在哪里**,而落了位置就往回改的 bug 是最贵的一类:**它能被一千个通过的测试掩盖,只在某个特定寻址方式下错。**

这一层现在没有任何独立验证,而任务 G / K 正要把它接到内核上。所以现在验,成本最低。

## 二、攻击面

按"哪里错得最安静"排序。**发现任何一条都要给一个能复现的最小输入**(具体的寄存器初值和字节序列),不要只给结论。

### 1. `D5` 里那句关于 20 位环绕的话,可能自相矛盾

`docs/DESIGN.md` 的 D5 写:

> **段:偏移 → 线性地址**:`(seg << 4) + off`,按 20 位环绕(A20 逻辑)。

而 `dos/include/vm86/mem.h` 写:

> The 8086 has twenty address lines, so a linear address wraps at 1 MiB. The 286 and later have more, and the 21st line was gated to keep old software from wrapping into the top of memory by accident... **It defaults to on here** [A20].

**这两句放在一起读,是要打架的**:20 位环绕是 8086 的行为,而 A20 打开的意思恰恰是"**不**再环绕"。D5 用"(A20 逻辑)"给一个 20 位环绕的说法做注解,而 A20 的语义正好相反。

**先把这件事查清楚,再去看代码是不是照哪一边实现的。** 具体要确定:

- `(seg << 4) + off` 这一步,溢出 20 位时到底绕不绕?这和 A20 是不是同一个问题,还是两个不同层次的问题?
- `mem->a20` 这个字段**在代码里有没有被任何地方读**?(用 `grep` 确认,不要凭印象。一个没人读的字段本身就是一条结论。)
- 一个具体的输入:`CS=0xFFFF, IP=0x0010`,下一条被取的指令落在哪?按 8086 和按 A20 打开分别是多少?
- `IP` 自己的 16 位回绕(在同一个段内从 `0xFFFF` 走到 `0x0000`)和上面那件事是不是同一个机制?**如果不是,代码里有没有区分?**

这是本次任务里最值钱的一条,因为它要验的是**文档和代码的一致性**,而不是某个函数的某个分支。

### 2. ModRM 的两处经典陷阱

- **`mod=00, rm=110` 是 `disp16`,不是 `[BP]`。** 这是 8086 编码里唯一一处"rm 字段的值不按常规解释"的地方。有测试吗?没有的话写一个最小的。
- **基址寄存器是 `BP` 时,默认段是 `SS` 而不是 `DS`。** 这条只对**默认**生效 —— 加了段覆盖前缀仍然覆盖。两个方向都要验。

### 3. 段覆盖前缀:哪一侧可覆盖,哪一侧不可

- `DI` 永远在 `ES` 侧,**任何段覆盖前缀都不能改变它**。`ES:` 前缀对 `movsb` 的目标侧应当是**无效**的。
- `SI` 在 `DS` 侧,可覆盖。
- 一个具体的检查:`decode.c` 里解析有效地址时,**有没有地方让 ES 侧走了一个可以被前缀改写的路径?** `dos/include/vm86/ops.h` 里 `vm86_str_repeat()` 的契约注释特意写了"ES side must never go through `vm86_effective_seg`" —— 去看那条约束是不是真的成立,以及**它成立是因为代码禁止了,还是因为碰巧没人写过**。

### 4. 前缀循环

- 多个前缀连着写(`F3 26 A4` 之类)时,解析顺序和最后一个生效的吗?
- `F3` 既是 `rep` 又是段前缀 `DS` 的编码 —— 解析器怎么决定它是哪一个?这个决定正确吗?
- `F0`(LOCK)、`0F`(286 转义)在这台"8086"上应该是什么行为?代码里是怎么处理的,**理由是什么**?
- 前缀出现在指令**末尾/被截断**时(比如二进制在 `F3` 处结束)会怎样?会不会读越界?

### 5. 五张表的合并

`vm86_ops_build()` 把五组各 256 项的表合成一张,并报告重复认领。要验:

- 合并之后,**每一个**非空槽位的处理函数都来自正确的组吗?(不要只看"没有冲突",要看归属。)
- 冲突报告器**真的会报**吗?`dos/tests/harness.c` 里现在装了一个;如果它被摘掉,一个刻意的冲突会不会静默通过?
- `tools/check-opcode-coverage.py` 报"没有操作码没人认领"—— 但**"没人认领"和"不需要认领"是两回事**。去看那个脚本把哪些槽位算作"不需要认领",**每一条的理由是否成立**。这份清单是有人写下来的,写下来就可能写错。

### 6. 内存访问的边界行为

`mem.h` 的契约:

> 16-bit accesses are performed as two 8-bit ones, so an access that straddles the end of the region gets the same answer an address near the boundary would -- half real, half floating bus -- rather than reading past the end of the host's array.

验:

- 一个 16 位读**恰好跨在区域末尾**上:低字节是真的,高字节是 `0xFF`。**不能读越界**(用 ASAN 或者把缓冲放在 mmap 的边界页上试)。
- 未映射区域读返回 `0xFF`,**写被丢弃**(而且 `dropped_writes` 计数增加了)。
- `vm86_mem_offset()` 在越界时返回 `VM86_MEM_UNMAPPED` —— 有谁在用它?用错了会不会把 `0xFFFFFFFF` 当成一个合法偏移?
- `vm86_mem_clear()` 之后计数器和内存都归零了吗?**区域和 A20 设置保持不变吗**(契约这么说)?

## 三、规则

### 1. 判据是"**这是哪颗芯片的行为**"

README 第六节那张表是这个项目最贵的一课:任务书自己错过的那几处,全都是**把 186/286 的行为当成了 8086 的**。你在这里也会遇到同样的岔路 —— 比如 `0F` 转义、移位计数截断、`mov` 到段寄存器的加载时机。

**按 8086 那一列判。** 拿不准就去查手册,不要按"我记得后来的 CPU 是这样"下结论。

### 2. 标注查证还是推测

报告里凡是出现外部世界的事实断言 —— "手册是这么写的"、"真实程序不会这么用"、"后来的 CPU 都这样" —— **标明你是查过还是推的**。推测不是错;把推测写得像查过才是。

### 3. 假阳性

如果你要报的是**别人的文件里的问题**,先确认你读到的是最新版本:

```bash
git -C /c/FunnyOS log --oneline -3 main -- <那个文件>
git merge-base --is-ancestor <它最新的提交> <你的起点>
```

2026-09-30 已经有过一次:任务 E 在自己落后的 worktree 副本里报了一个 `push sp` 的 bug,而 main 上早就修好了。**判定依据必须是 main 上的代码,不是你 worktree 里的。**

### 4. 没发现问题也是结论

如果你逐条查完什么都没找到,**那是一个有价值的结论,但要能被检验**:每一条要说清楚"我用什么输入验的、期望什么、实际什么"。**"我读了代码,看起来是对的"不是证据。**
