## 一、你的工作不是"确认它能用"

任务 A–E 的每一份都要求作者写自己的测试。那些测试回答的是"我写的代码做了我以为它做的事吗"。

**你的工作回答另一个问题:"有没有什么事,所有人都以为它做了,但它没做?"**

这是不同的问题,需要不同的做法。具体来说:

- **你的期望值来自手册,不来自代码。** 去查《8086 Family User's Manual》第 3 章对应条目的标志位表,把表里的值抄成测试用例。不要读 `ops_*.c` 然后"照着它写测试"——那样只会测出作者已经想到的东西。
- **你要找的是边界,不是主干。** 每条指令的"正常用法"已经被作者测过了。你测的是:计数为 0、溢出、借位、符号边界、未定义的编码、跨页的地址、段边界。
- **每个测试都要证明它能失败。** 写完一个测试之后,故意把某个地方改错(或者手工构造一个错误期望值),确认测试**真的报红**。一个永远不会失败的测试是负资产:它占着位置,还让人以为这件事被覆盖了。

## 二、从哪下手

### 0. 先查这一类:这是**哪颗芯片**的行为?

这不是假想的风险。这一轮**实际发生了四次**,形状完全一致:**把后来的处理器(186、286)的行为当成 8086 的**。其中两处已经进了代码,不是停在文档里。

先说清楚这种错为什么特别难自己发现:

- **它读起来是对的。** "段寄存器延迟更新"、"移位计数被截断"都是真实存在的硬件行为,只是不属于这颗芯片。
- **测试抓不住它。** 段寄存器全为 0 的套件区分不出"LEA 把段基址折进了结果"和"没折";栈指针从不被回读的套件区分不出两种 `PUSH SP`。
- **注释会和代码一起错。** 有一处是骨架实现了 186 行为、而任务书把骨架描述成 8086 行为——**注释同意代码,两者一起不同意芯片**。所以只读代码、或者只读文档,都会得到"一致"的结论。

已确认并修好的四处,以及你要复核的地方:

| 位置 | 曾经的说法 | 8086 的实际行为 |
|---|---|---|
| 任务 B 坑 1(`8E`) | 段寄存器延迟更新,下一条指令读到旧值 | **立即**拿到新值。被延迟的是**中断识别**一条指令,而且据 errata 作用在**所有** `mov` / `pop segreg` 上,不只 SS |
| 任务 D 坑 4(`STI`) | 需要往 CPU 状态里加一个"中断延迟"字段 | 立即置 IF。被延迟的同样是中断识别,而 M3 没有中断投递,所以观察不到 |
| 任务 B 坑 0(`LEA`) | 段超越让结果包含段基址 | **纯偏移**,段基址从不进入结果 |
| 任务 B 坑 6(`PUSH SP`) | 现有实现就是 8086 行为,不要动 | 8086 压**减之后**的 SP。骨架压的是减**之前**的,那是 186 |

**所以你要做的第一件事**:把代码里每一处"这样写是因为 8086 就是这样"的说法找出来,**去手册里查 8086 那一列**——不要查 186 那一列,也不要问"哪个更合理"。哪颗芯片是判据。

已知属于这一类、但还没有结论的地方:

- **`shl ax, cl` 在 CL 较大时是否截断。** 8086 用完整计数值,186 起截断到 5 位。任务 A 已按 8086 处理——**去确认实现和测试真的是这样**,别只看注释。
- **`C0`/`C1`(186 的立即数移位)归任务 A**,但 A 的政策是"按 8086 行为不截断"。**186 自己的指令要不要按 186 截断**?这条当时没有结论,值得单独查清楚并写进报告——两种答案都能自圆其说,所以它是一个**决定**,需要有人明确做出来。
- **`MOV CS, ...`(`8E` `/1`)**:8086 硅片据多方记录会执行这条编码,手册不承诺任何行为;286 起非法或被挪用。本实现选的是触发向量 6。**这是一个选择,不是一条事实**——报告里要这么写。

### 1. 每份任务书里的"坑"清单

那是作者写下的已知难点。**逐条验证作者真的按自己说的做了。** 特别是那些作者"决定"了什么的地方——决定意味着有人选错的可能。

比如任务 B 的坑 1:作者选了 `mov cs, ax` 的行为。去读代码,然后测它。作者选的行为和实际行为一致吗?

### 2. 手册里标着"未定义"的地方

未定义不等于可以随便。它的意思是**真实硬件的行为可能是确定的,只是没写进文档**——而 DOS 程序可能依赖它。至少要把这些地方列出来,说明本实现选了什么。

### 3. 边界值

对每一条算术指令:

- 结果正好是 0 / 0x7F / 0x80 / 0xFF(或字的对应值)
- 进位刚好发生和刚好不发生
- 有符号溢出刚好发生和刚好不发生
- 操作数是 0

**左移/右移**尤其要测**计数为 0**——那是一个"什么都不发生"的路径,最容易被漏掉。

### 4. 组合

单条指令正确,组合起来不一定正确:

- `push` / `pop` 配对时 SP 的往返
- `REP` 里的 `CX` 和 `ZF` 的相互作用
- 段超越前缀加上**隐含使用段的指令**(串操作的写侧、栈操作)
- `INT` / `IRET` 往返之后 FLAGS 和 SP 是否完全复原

### 5. 内存边界

- 16 位访问**跨过 64 KiB 偏移边界**。
  > **勘误**：这一行原来带着一个括注"8086 上偏移量会回绕"——**那是错的**（由任务 F 提出、任务 L 的测量支持）。16 位**数据**访问跨过偏移边界时，第二个字节来自 `linear + 1`，也就是**下一段的第一个字节**；偏移量本身不回绕。会回绕的是 16 位的**寄存器在自增的时候**（`IP`、`SI`、`DI` 从 `0xFFFF` 走回 `0x0000`）—— 那是寄存器行为，和寻址是两件事，而那个括注把它们混成了一件。真正该在这里被怀疑的是：**代码有没有把"寄存器自增的回绕"错误地也施加到寻址上**。
- 16 位访问**跨过 1 MiB**(A20 关闭时回绕到低端)
- 访问 `0xFFFF` 处的字
- 栈指针在 `0x0000` 附近时的 push

这些是最容易错、也最少被作者测到的。

### 6. 和真实实现对照

如果条件允许,**用另一个模拟器(DOSBox 等)跑同样的字节序列,对比寄存器和标志位**。这是唯一能真正独立验证"手册读得对不对"的办法。

如果做不到,就在报告里说明哪些测试是"按手册推导"、哪些是"对照验证"——**读者需要知道这个区别**。

## 三、报告格式

每发现一个问题,写清楚四件事:

1. **最小复现**:能直接贴进一个测试函数的字节、初始寄存器状态
2. **期望**:值是多少,**以及这个期望来自哪里**(手册哪一页/哪张表)
3. **实际**:跑出来的值
4. **严重性**:会不会影响真实 DOS 程序?还是只在手工构造的字节里出现?

**第 4 条很重要。** 一个只在不合法编码里出现的差异,和一个会让 `repe cmpsb` 比较错的差异,优先级差得很远。资源有限,先修后者。

## 四、如果一切正常

**"没找到问题"也是一个有效结论**,但要有说服力:

- 报告你**测了什么**、**怎么选的**
- 报告你**没能测什么**、为什么(缺少什么工具、缺少什么信息)
- 报告哪些地方**手册本身是含糊的**,所以你的测试不能作为判据

**不要为了让报告看起来有价值而编造问题。** 一个可靠的"这些地方我验证过了"比十个含糊的怀疑有用得多。
